# Part A — Creating Relations Between Entities

## A.1 — What Is an Entity Relation?

An Entity Relation tells the Klobase server how two entities are connected to each other. Without a relation defined in the Procify Data Studio, the platform has no way to automatically load child records when a parent record is selected — and no way to bundle the BO for save/delete operations.

There are two types of relations in Klobase:

| **Relation Type**                 | **What It Means**                                                                                                                                                                                                              |
|-----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Primary Relation                  | Tight parent-child bond WITHIN the same Business Object (BO). A child entity is dependent on the parent. Prefixed pr\_. Used for d_complaint_item, d_complaint_voices, d_complaints_attachment — all children of d_complaints. |
| Non-Primary (Aggregated) Relation | Looser link BETWEEN BOs. Used to reference standalone master entities. Prefixed r\_. Used for d_customers and d_resp_team which are independent master entities.                                                               |

| **📘 Why Relations Matter in the UI**                                                                                                                                              |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| When a relation is defined and referenced in a TransNode in the Page Builder, the platform automatically fetches the child/linked entity records when the parent record is loaded. |
| Without a relation, you would have to write manual queries and wire up the data fetch yourself.                                                                                    |
| The TransNode type 'Relation' in the Page Data Model uses the relation name defined here — this is why naming the relation correctly matters.                                      |
| Naming convention (from Procify Data Studio 7.0 User Guide — Best Practices): pr\_ prefix for primary relations, r\_ prefix for associated/aggregated relations. Always lowercase.          |
|                                                                                                                                                                                    |

## A.2 — Relations to Create for d_complaints

You will create 5 relations on the d_complaints root entity — one for each related entity.

| **Relation ID**    | **Type**                 | **Return Entity**       | **Cardinality**                                     |
|--------------------|--------------------------|-------------------------|-----------------------------------------------------|
| r_complaint_item   | Non-Primary (Aggregated) | d_complaint_item        | 1:n (One complaint → Many items)                    |
| r_complaint_voices | Non-Primary (Aggregated) | d_complaint_voices      | 1:n (One complaint → Many voices)                   |
| r_complaint_attach | Non-Primary (Aggregated) | d_complaints_attachment | 1:n (One complaint → Many attachments)              |
| r_customer         | Non-Primary (Aggregated) | d_customers             | 1:1 (One complaint has one customer)                |
| r_resp_team        | Non-Primary (Aggregated) | d_resp_team             | 1:1 (One complaint has one responsible team member) |

## A.3 — Step-by-Step: Creating a Primary Relation

Primary Relation will be automatically created with the creation of child entity and requires no manual action

## A.4 — Step-by-Step: Creating a Non-Primary (Aggregated) Relation

Non-primary relations link d_complaints to standalone master entities (d_customers and d_resp_team). Follow these steps for r_customer

| **\#** | **Action**                     | **Detail**                                                                                                                                                                    |
|--------|--------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1**  | **d_complaints Relations tab** | click d_complaints in the tree and go back to the Relations tab.                                                                                                              |
| **2**  | **Click Add**                  | Click the Add (+) icon to add a new relation row.                                                                                                                             |
| **3**  | **Fill Relation Details**      | Relation Name: r_customer \| Description: Aggregated relation — customer master data \| Return Entity: d_customers \| Relation Query: d_customers \| Cardinality: 1:1         |
| **4**  | **Configure Mapping**          | Click Mapping. Add: Source Property = customer_id \| Mapping Type = ON QUERY \| Target Property = customer_id. This join fetches d_customers data when a complaint is loaded. |
| **5**  | **Save**                       | Click Save.                                                                                                                                                                   |

| **💡 Mapping Type — BOTH Explained**                                                                                                                                                                                   |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ON CREATE: When a new d_complaint_item is created under a d_complaints parent, the platform automatically copies the complaint_id value into the ticket_id field of the new item. You never have to set this manually. |
| ON QUERY: When you query d_complaint_item records for a given complaint, the platform uses ticket_id = complaint_id as the WHERE condition automatically.                                                              |
| BOTH: Use this for standard parent-child relations — it handles both the create and the fetch scenarios.                                                                                                               |
|                                                                                                                                                                                                                        |

Now repeat the same steps to create the remaining relations:

| **Relation ID**    | **Return Entity**       | **Mapping (Source → Target)**                                           |
|--------------------|-------------------------|-------------------------------------------------------------------------|
| r_complaint_voices | d_complaint_voices      | complaint_id → ticket_id \| Cardinality: 1:n \| Mapping Type: BOTH      |
| r_complaint_items  | d_complaint_item        | complaint_id → ticket_id\| Cardinality: 1:n \| Mapping Type: BOTH       |
| r_complaint_attach | d_complaints_attachment | complaint_id → complaint_id\| Cardinality: 1:n \| Mapping Type: BOTH    |
| r_resp_team        | d_resp_team             | responsible_team → emp_id \| Cardinality: 1:1 \| Mapping Type: ON QUERY |
