# Session 3 — Security, Permissions & Data Access

**Date:** Wed, 09 Sep 2026 **Duration:** Full day

## Session Objectives

- Enforce CRUD restrictions server-side using design-time Permissions.

- Restrict IT Team visibility to their own team's complaints using Row Wise Auth.

- Scope customer data by region using Data Access Rules.

- Audit a user's effective access using User Access Summary.

- Grant, use, and revoke a temporary elevated Role Permission, and confirm it in Permission Logs.

| **What This Session Builds On**<br/>Level 1 Session 7 hid or disabled buttons per role using Vienable — a UI-level control only. This session enforces the same rules at the platform/security level so they hold even if a user calls the API directly. |
|---|

**Scenario**

An IT Team member who left last month still has delete rights if they call the API directly, even though the button is hidden in the UI. A regional manager can see every customer's complaints nationwide instead of just their region, and after an override was granted during an incident, nobody can say who approved it or when it was revoked.

### **Part A — Design-Time Permissions**

**Steps of implementation of CRUD restrictions :**

### **Step 1 — Enable restriction flags at the entity level**

1.  Open **Procify Data Studio**, select the relevant flavor, then select the entity you want to restrict.

2.  Go to the **Security & Permissions** tab on that entity.

3.  Click **Edit** and toggle on the flags you need: **Create**, **Read**, **Update**, **Delete** (Download is enabled for all entities by default and has no flag).

4.  Click **Save** to commit the change to the DB.

### **Step 2 — Understand the auto-generated permissions**

For each flag turned on, the system auto-generates one permission per operation, following this ID pattern: \<entity_name\>=\<Action\>

- CR_ACC — Create

- RD_ACC — Read

- UP_ACC — Update

- DL_ACC — Delete

- DW_ACC — Excel download

### **Step 3 — Assign permissions to users**

- **In DEV landscapes:** assign permissions directly via the **Permission modeler** screen (App Builder menu).

- **In QA/Production:** control assignment via the **Role Permissions** screen (Security & Permissions menu) — permissions are grouped and assigned to users through permission groups there, not edited individually.

### **Step 4 — (Optional) Apply row-level restrictions on top of entity-level CRUD**

If you need to restrict *which rows* a user can see/edit rather than just which operations:

1.  Enable the **Row Wise Authorization** flag on the entity in Procify Data Studio.

2.  Add a new access-token line item, filling in the primary key and access key.

3.  Add the properties that should participate in the row-level check.

4.  Reorder properties via drag-and-drop if sequencing matters, then confirm.

### **Step 5 — Enforce visibility/behavior in the UI (optional, not a security boundary on its own)**

- **Recommended:** use **Vienable** in Procify Page Builder to bind a permission ID to a control — if the user lacks the permission, the control is hidden.

- **Advanced:** bind directly to the permission proxy path \$M\>/perm/\<permission_ID\> (e.g., \$M\>/perm/d_issues=DL_ACC) for finer control than Vienable allows.

- **Custom logic:** call hasCRUDPermission() / hasPermission() APIs in a controller to branch logic based on whether the user holds a permission. Both work client- and server-side.

### **Step 6 — Follow best practices**

1.  Enable permissions on all entities that need restriction, and grant only the necessary permissions per user — avoid blanket "admin has everything."

2.  **Always enforce restrictions server-side.** Any client-side (screen/controller) restriction is for UX only and is not a security boundary — the actual check happens when the request hits the server.

3.  If using OData, remember users also need the **ACCESS_ODATA_SERVICE** permission on top of entity CRUD permissions, or the service returns "Access denied for requested resource."

### **Part B — Row Wise Auth**

*Restrict IT Team to only the complaints assigned to their own team.*

| **#** | **Action** | **Detail** |
|---|---|---|
| **1** | **Configure the rule** | Row Wise Auth on d_complaints: IT_TEAM role only receives rows where responsible_team = current user's team.<br/>*For more details about the Row Wise Auth , see the* <a href="https://docs.google.com/document/d/1P7tZZMgIySIxgkiEWIOFUyvq36MP5yUXi-mfZ2KzTn8/edit?tab=t.0">*Row Wise Auth*</a> *documentation* |
| **2** | **Test** | Log in as it_&lt;prid&gt; — confirm only assigned complaints appear, even via direct navigation to a different complaint's URL. |

Row wise authorization can **only be enabled on root entities**, never on child entities. If a BO (root) has it enabled, all its child entities automatically inherit the same restriction — a user with access to the root record gets access to all its children.

### **Step 1 — Enable the flag**

Turn on the **Row Wise Authorization** flag on the entity's Security & Permissions tab.

### **Step 2 — Create a line item (access token template)**

Click **Add** to create a new line item. Each line item you create here defines one **access token template** — a rule the system uses to auto-generate a token for every record in that entity.

### **Step 3 — Fill in the ID, access key, and select properties**

- **ID** — the entity's primary key.

- **Access key** — a custom alphanumeric string you choose (e.g., wc, pg_pl, flagged). This becomes the prefix of the generated token.

- Click the property-column icon to attach the **access properties** — the entity fields whose *values* will be pulled into the token.

**How the token gets built:** \{access key\}=\{property1_value\}#\{property2_value\}...  
Example: an access key of wc bound to work_center generates a token like WC=ELEC for a row where work_center = ELEC. A multi-property key like pg_pl bound to planner_group + plant generates PG_PL=\<planner_group\>#\<plant\>.

### **Step 4 — Add properties in the dialog**

A dialog opens listing all properties already added to the entity (empty by default). Click **Add** to bring up the selection list.

### **Step 5 — Select the properties to include**

Choose every property that should feed into that token, then click **Add** to confirm.

### **Step 6 — Reorder if needed, then confirm**

If the order of properties matters for the token structure (recall: order determines the \#-separated sequence), drag and drop to resequence, then click **OK**.

### **Part D — Role Permissions (Runtime) & Permission Logs:**

### **Runtime Role Permission (formerly Role Permissions)**

This is managed at runtime via the **Role Permissions** screen (formerly "Role Permissions") under the **Security & Permissions** menu (formerly Security & Permissions) — separate from the DEV-time **Permission Designer** (formerly the Permissions screen in App Builder/App Builder).

#### **How runtime assignment works**

- Permission groups configured in **DEV** get pushed to QA/PROD on transport. Once there, they're **read-only for structure** — permissions can't be added/removed from a DEV-sourced (**SYSTEM**) group, only enabled/disabled.

- Admins in QA/PROD **can** create new groups (marked **USER** source) and freely add permissions to those.

- On rollout, existing users get permission groups auto-assigned based on their application role; new users get them assigned at first registration.

- **Versioning behavior:** on a major version transport, the newer version's permission groups/permissions overwrite runtime config, and users on the new version get permissions re-adjusted based on role. On a **minor** version deployment, users still on older versions are *not* auto-adjusted — permission changes only apply when something version/role/assignment-relevant changes for that user.

#### **Implementation steps**

1.  **Navigate:** Security & Permissions menu → **Role Permissions**.

2.  **Advanced Search (mandatory):** select an **App** (required field) — you'll only see groups for apps where you're assigned as Manager. Optionally filter by **Enabled** and **Source** (SYSTEM vs USER).

3.  **Create a group:** Click **Create**, enter a name (uppercase/lowercase/\_/-/numbers/spaces, ≤28 characters), then **Save** to open its detail screen.

4.  **Assign roles:** Go to the **Roles** tab → **Add** → pick an application role → **Add**. Any user holding that role inherits this group's permissions at runtime.

5.  **Assign custom permissions:** Go to the **Custom Permissions** tab → **Add** → select the permissions to include → **Add**.

6.  **Assign entity (CRUD) permissions:** Go to the **Entity Permissions** section → search for the entity → check the CRUD permissions to grant → confirm.

7.  **Save** the group from the detail header to commit roles + permissions together.

8.  **Enable/disable as needed:** toggle the group's **Enabled** flag to turn its effect on/off without deleting it (this is the only lever available for SYSTEM-sourced groups).
