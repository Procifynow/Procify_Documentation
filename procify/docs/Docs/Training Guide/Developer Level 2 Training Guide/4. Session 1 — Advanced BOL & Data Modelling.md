# Session 1 — Advanced BOL & Data Modelling

**Date:** Mon, 07 Sep 2026 **Duration:** Full day

## Session Objectives

- Configure Network Modes so offline-relevant properties sync correctly to field devices.

> **Network Mode Types**

| **Mode**                 | **How it works**                                                                                                                                                                     | **Best use case**                                                                                                                                                 |
|--------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Online**               | The app talks to the server for every operation — network connectivity is required. Data is read from and written directly to the transactional database; nothing is cached locally. | Standard business apps with reliable connectivity — real-time dashboards, approval workflows, anything where data must always reflect the server's current state. |
| **Offline**              | The app stores data locally (web SQL) and syncs with the server whenever connectivity is available. Users can keep working through weak or no network.                               | Field service, warehouse, or mobile scenarios where users regularly lose signal (e.g., technicians on-site, drivers, remote inspections).                         |
| **SAP Online**           | All transactions route through SAP via the gateway server; data is read from and written to the SAP server itself, not a local Klobase DB.                                           | Apps acting as a front-end to SAP where SAP must remain the system of record for every transaction.                                                               |
| **SAP Preferred Online** | Transactions pass through SAP but land in the local web SQL rather than being held only in SAP.                                                                                      | Hybrid cases where you want SAP validation/processing but still want a local cache for offline reads or faster access.                                            |

- Build a BOL Transaction that commits two entities atomically.

> A. **Get a transaction object** — either the one already active in your controller context, or create a fresh one:
>
> let txn = await this.createTransaction(); // or use existing this.txn
>
> B. **Create the first entity** using createEntityP(entityName, entityJson?, deepClone?, mappingRule?). This adds the object to the transaction as a "dirty" (uncommitted) object — it isn't written to the database yet:
>
> let ent_1 = await txn.createEntityP("d_no_hdr", \{
>
> short_text: "Header entity",
>
> description: "First entity in the transaction"
>
> \});
>
> C. **Create the second entity** on the **same transaction instance** (txn), not a new one — this is what makes both creates part of a single atomic commit:
>
> let ent_2 = await txn.createEntityP("d_no_work_order",
>
> \{ short_description: "Related entity",
>
> description: "Second entity in the transaction" \});
>
> D. **(Optional) Lock entities** if you need to prevent concurrent edits during the transaction:
>
> await txn.trylock('d_no_hdr', 1000);
>
> E. **Commit both entities together** with a single commitP() call. Since both ent_1 and ent_2 are dirty objects on the same txn, one commit persists both to the database as a single unit:
>
> await txn.commitP();

### **Part A — Network Modes — Offline-Ready Apps** 

## Setting Up and Executing Offline Apps

### **How offline works**

In offline mode the app stores data locally and syncs the local cache and server data whenever it finds connectivity. Browsers and installed mobile apps both support it. Values are read from and written to web SQL.

### Online mode goes to the transactional database instead.

### **Setup**

1.  Create the app as Offline.

    - In Procify Workspace Hub → App Management, create the app and set the Network Mode. The default is ONLINE.

    - Choose Device, Browser or Both under App/Portal Support.

2.  Set entity App Mode. In Procify Data Studio, open the entity's Detail tab and set App Mode to Offline.

3.  Set Persists On (Null, Both, Client Only or Server Only) on each entity. With Null, an offline flavor creates the entity in both the server and client DB, and an online flavor only on the server.

4.  Create the queries that will sync.

    - Use a Saved Query or Modelled Query. Both can drive Initial Sync.

    - In beforeQuery, call setLoadAll(true). The training guide lists offline apps and Initial Sync as use cases, because all data must load during registration.

5.  Configure Initial Sync (Platform Settings → First-Run Sync).

    - Initial sync queries run during registration, and the results are stored in the local (browser) cache.

6.  Add archive rules (Platform Settings → Data Sync Settings) so old data doesn't pile up on the device.

    - Select the flavor, click Add, choose the entity or query, then add params (key, operator, value) and save. Rules are stored in m_archive.

    - Value rules: IS_NULL and IS_NOT_NULL take no value, IN and NOT_IN need an array, and LIKE uses %value%.

    - If you archive by query, the properties you add must also appear in the query's WHERE clause, or archiving won't work.

7.  Build and publish. The Local Archive guide says to create the saved query, then Initial Sync, then the archive rule, and then build.

### **Execution**

1.  Do a fresh registration on the device or browser. Initial sync runs and populates the local store.

2.  The app then runs against local data, and changes sync with the server when connectivity returns.

3.  Open the screen that has an archive rule and wait about 3 minutes. Archiving runs in the background when the app opens.

*Not every app needs the same connectivity behavior. Configure Network Mode at the app level so field teams can keep working when connectivity drops.*
