### **Part A — Local Archive**

*Keep a working slice of data on the device for offline use.*

### **Local Archive — Overview & Use Case**

**What it is:** Local Archive lets you remove data from a client application's **local data store** (the on-device/browser database, i.e. web SQL) based on defined criteria. It does not touch the server-side database.

**Use case:** Primarily for **offline applications**. Since offline mode caches data locally so users can keep working without connectivity, that local store can accumulate old, stale, or unused records over time (completed transactions, historical notifications, etc.). Local Archive lets developers define rules so this data is automatically cleaned from the device/browser in the background — preventing unbounded local storage growth and keeping the offline app performant.

### **Pre-requisites**

- Understanding of **query parameters** (where-clause style conditions).

- Understanding of **Initial Sync** and **Saved Query** concepts — you typically need a saved query and an initial sync set up before the archive rule will behave as expected, since the archive can piggyback on a query's WHERE clause.

### **How it's enabled**

Local Archive isn't a flag you flip — it activates automatically as soon as an archive rule exists for an entity/query. Once created, the rule is checked in the background whenever the app opens.

### **Implementation Steps**

#### **1. Navigate to the screen**

- Go to **Application Settings** (formerly Platform Settings) menu header → **Data Sync Settings**.

#### **2. Select the flavor**

Choose the flavor you're configuring the archive rule for from the dropdown.

#### **3. Add an archive entry**

Click **Add**. A new line item is created in the m_archive entity with an auto-filled **Archive ID** (editable if you want a custom value).

#### **4. Select the entity or query**

Click the value help in the **Entity/Query Name** column and pick the target.

- If you pick a **Query** (modeled query), its SQL WHERE clause is also factored into what gets archived.

- ⚠️ If you pick a query and then add property filters via the Local Archive tool that **aren't part of that query's WHERE clause**, archiving will silently fail to apply those filters — the query's own WHERE logic takes precedence.

#### **5. Select properties / define filter parameters**

Click the value help icon in the **Properties** column to open the parameter dialog, then click **Add** to create a parameter row:

- **Key** — the property (from the selected entity/query) to filter on.

- **Operator** — the comparison operator. Special cases:

  - IS_NULL / IS_NOT_NULL — no value needed; automatically set to true.

  - IN / NOT_IN — value must be an array, e.g. \["abc","pqr",9\].

  - LIKE — value must be wrapped as %value%.

- **Value** — the comparison value (not needed for null checks).

If you leave properties unselected entirely, **all data** for the chosen entity will be deleted rather than a filtered subset.

#### **6. Add the parameter**

Click the **Add** footer button to attach the parameter to the archive rule.

#### **7. Save**

Click the **Save** icon to commit the new rule into m_archive.

#### **8. Trigger and verify**

After saving, do a **fresh registration** and navigate to the screen tied to the archived entity. Wait about **3 minutes** — the archive job fires on app open, and matching records are deleted from the local store in the background.

### **Part D —** **KloSectionXlsx — Bulk Customer Import**

**KloSectionXlsx** is a UI control (extends sap.ui.core.Control) that lets developers configure **Excel upload and download behavior** for a grid/cardlist section — controlling things like the downloaded file's name, a downloadable template, and which columns participate in upload/download. It works hand-in-hand with the **Download Excel** and **Upload** buttons exposed by KloSectionToolbar (showDownloadExcel, showUpload properties) — those buttons trigger the behavior; KloSectionXlsx is where you configure *how* that behavior works.

#### **Properties** :

| **Property** | **Type** | **Default** | **Description** |
|---|---|---|---|
| **fileName** | string | DataDownload | Name of the downloaded Excel file. |
| **templateFileName** | string | — | Name of the template file to be downloaded (used for guided uploads). |
| **downloadSectionTemplate** | string | — | Section name the download template applies to. |
| **uploadSectionTemplate** | string | — | Section name the upload template applies to. |
| **allColumnsUpload** | boolean (documented as string) | false | If true, all entity columns are considered during upload — not just visible ones. |
| **allColumnsDownload** | boolean (documented as string) | false | If true, all entity columns are included in the downloaded file — not just visible ones. |

### **How to configure it**

1.  In **Procify Page Builder** (Procify Page Builder), open the context menu on the grid/cardlist section and **Add the Excel Config** — this attaches a KloSectionXlsx instance to that section.

2.  Set fileName to control the downloaded file's name.

3.  If you want users to download a **pre-built template** rather than an auto-generated one:

    - Place the actual .xlsx file at kloTouch/resources/ExcelTemplates (you'll need to hand this file to the **infra team** — they place it in that path; it's not something you upload from the UI directly).

    - Set templateFileName to point to it.

    - If no template is found at that path, the system falls back to auto-generating a template based on the columns currently visible on screen.

4.  If the template (or download) should include **every column on the entity**, not just the visible ones, set allColumnsUpload / allColumnsDownload to true as appropriate.
