# Best practices

## 13.1 Data security

1.  When using getResult / setResult on the server side for row wise authorized entities, make sure not to send back non authorized data. The data set on to the query using setResults are directly returned as query results, no more filtration is applied.

2.  When changing callback from client side to server side always consider row wise authorization if involved.

3.  Avoid logging sensitive data.

4.  Native query doesn’t support row wise authorization, so don’t select sensitive data via native query.

5.  Use “me” token only if all users of applications can access the data, else don’t use me token, use a different access key and add User Access Keys in callback.

6.  ValueHelp where row wise authorization is turned off should not have any sensitive data as key or description.

7.  The data based on which User Access Keys are generated, should be protected. **For example :** If Access to issues is based on projects assigned, then, only authorized users should be able to assign or un-assign projects.

8.  Query fired on server side will not have row wise authorization / permission applied on it. To apply row wise authorization on server side queries, use [<u>applyRowWiseAuthorization</u>](#applying-row-wise-authorization-in-server-side-queries).

## 13.2 Performance and others

1.  The feature is for restricting unauthorized access. Only implement on entities with sensitive data. For non-sensitive data, consider using query filtrations.

2.  In the User Access Keys callback, make sure to batch queries based on user, as it can be called for 1 - many users.
