# Transport — Navigate to Transport Screen

Transport works on a pull mechanism where the target system asks for the latest update from the source system. All the below activities needed to be done on the target system.

**NOTE : Branch flavors cannot be transported or moved to any system. For doing so, create a new version, merge that branch to the new version and then move the new version to any system.** 

**Step 1:** Go to the menu options and select App Lifecycle**.**

**Step 2:** Transport has **two screens.  App Transport** and **Script Repository.**



1. **App Transport \-** This screen will display all the apps in the selected source system, as well as any apps that are already installed in the current system.It allows you to see which apps are available for transport and which ones are already installed.



2. **Script Repository \-**  In this screen, we can get all the scripts that are maintained in the current system.



### 3.1 Read-Only vs. Writable Installation 

When you install an app in a DEV landscape, App transport asks whether to install it **As Readable** or **As Writable**. The choice decides what is copied to the target landscape and what you can change there afterward.

|  | As Readable (Read-Only) | As Writable |
| :---- | ----- | ----- |
| **What is moved** | The built application package (zip) only | The app’s full metadata from the source DEV landscape |
| **Can the app be developed in the target?** | No | Yes |
| **Can App Dependencies be maintained?** | No (see below) | Yes |
| **Typical use** | Consuming an app as-is, e.g., in QA/PROD or as a parent app | Continuing development in another DEV landscape |

**Why App Dependencies can’t be maintained for a Read-Only app**

A Read-Only app has no metadata in the target landscape. It only has its built package. Maintaining App Dependencies writes a generated sequence to the database, and the app must be built again afterward. A Read-Only app can’t be built in the target landscape, so its dependencies can’t be changed there.

*Example:* VP depends on OHR (VP ← OHR). If the dependency configuration has to change on the OHR side, OHR must be installed **As Writable**. Alternatively, make the change in the source landscape and migrate it again.

**Note:** If you might need to change an app’s dependencies in the target landscape, install it **As Writable**. **\[Confirm\]** Whether a Read-Only app can be switched to Writable later, or must be reinstalled.
