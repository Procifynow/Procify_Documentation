# Transaction (txn)

> Transaction is the transmission of one or more changes in the database. For example, if you are creating a record updating a record or deleting a record from the table, then you are performing a transaction on that table. To maintain the consistency of the data, the transaction ensures that all of the operations it contains are applied to KloBase Datastore as a single unit or, if any of the operations fail, none of them are applied.

Once a *commit*P or *rollback*P is called on the transaction, the transaction is frozen from accepting any new object until commitP or rollbackP is completed with the only exception that the call is initiated inside rule execution. Transaction Object instances may switch hence avoiding sharing across, UI, BO local method and in the rule.

**The life cycle of transaction:**

Transaction will be alive until it is held by an application, or any query (including *query tree*), or any dirty entity. Hence Transactions, Query and Entity, all three are interconnected with each other and will be released only when all of them are freed. It is the application's responsibility to ensure that all three are free. Please note that the transaction does not hold the query reference, query to the transaction is single direction reference. Dirty Entity holds the transaction. Non-dirty BO (entity) does not hold transactions. Entity holds the query reference.

**Inter-mixing Objects in transactions:**

- Any number of Query, getObjectByID, or Query tree can be associated with a single transaction.

- Any type of Query or any query ID can be intermixed together within a transaction.

- Any number of entities can be added in a single transaction. However, one entity/query can participate in one transaction only.

- Queries with different network modes can be intermixed in a single transaction.

- Entity and Query of different flavors can be intermixed in a single transaction.

- When an entity is getting edited it gets associated with the query transaction itself. The application can reassociate with the transaction for the given query or BO (entity) at any time before the commit call.

- Changing the entity transaction changes it for the BO instance, technically it is BO which is associated with the transaction not the entity.

- Changing the query transaction changes it for the query tree, technically it is the Query Tree which is associated with the transaction not the query.

- Entity Stub loaded with page fault also follows the query’s transaction.

- Transaction Objects that we see from outside BOL, inside the BOL rule and on the server are three different instances.

- Entity caching is done by the query tree, hence, ensuring entity instance consistency (one entity is represented by two or more instances) is the application developer's responsibility.

- Changing the network mode of the entity is permitted.

- Info Object and entity can not be intermixed in a single transaction. Transactions must have either dirty entities or dirty info objects only.

- Transaction by name is no longer supported.

*Deprecated**:*** TransactionManager::getTransaction(txnName:string): Transaction use Transaction.getInstance(txnName: string) instead.
