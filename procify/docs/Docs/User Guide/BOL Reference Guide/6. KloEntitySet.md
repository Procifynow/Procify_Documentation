# KloEntitySet

EntitySet is a collection of Entity objects. KloEntitySet extends the Array prototype.

KloEntitySet has three behaviours.

- Query result: direct result of query execution.

- Part of primary relation: by accessing primary relation on entity returns KloEntitySet.

- Part of non-primary relation: by accessing non-primary relation on entity returns KloEntitySet.

## Business Object

Business Object (BO) is a logical unit used in a business. It is made up of one or multiple entities. E.g. If we take an invoice (bill of purchase) it consists of a header and purchased items. Header and item entities (tables) are required to store this information. Either item or header alone does not make any sense. So invoice header and invoice item entity together make the invoice BO.

BO is a hierarchical tree of entities. Each entity must belong to one and only one BO definition. BO has only one root entity (top-level). The rest of the entities (child entities) are aggregated into root or other entities to construct the entity tree.

kloBroker always transmits the full BO in the Message. When any entity becomes dirty it also pulls the root entity instance in the writeset. Deletion of any entity instance deletes all the cascaded aggregate entity instances.

In authorization, all the authorization upon parents up to root are also applied except the middleware message process.

Example:

- d_order (root entity/BO)

  - d_order_item (child entity)

    - d_order_conditions (child entity)

## Entity

The data object in KloBase is known as Entity. An entity has one or more named properties, each of which can have one or more values. Each entity in the KloBase Datastore has a key that uniquely identifies it.

In simple words, we can say Entity is a database table. In DBMS, we store data in the form of a table containing information about entity types like order, address etc. In an order database, a table containing information about all the orders. For example, orders have properties like customer, amount, products, etc these are attributes which combine to make a table.

One entity must be part of only one BO.

Types of Entity:

- **Persistent:** Entity which physically exists/ stored in a database as a table. Fields in Persistent Entities could be either Persistent or Transient.

  - Persistent Entity by default Tenant Dependent can be made Tenant Independent

  - \<roadmap\> Persistent Entity by default are User Dependent can be made User Independent

- **Transient:** It is an in-memory entity that doesn’t exist in a database. All fields in Transient Entity are Transient only. It can be constructed out of query results or by code to hold the value at runtime. Messages can’t be communicated through Middleware using a Transient entity.

- **Config:** The application can create a config entity that holds the fixed values provided at design time . It can be accessed with a key only. Query does not work on these entities.

- FW only- Types:

  - Metadata

  - \<roadmap\> Archive

  - \<roadmap\> History

##### Entity Naming convention and length

- Entity names should use only English lowercase alphabets (a-z), digits (0-9) and underscore (\_) and up to 31 chars max length.

- The first char must be d/t/c based on type. Transactional (‘d’), Transient (‘t’), Config (‘c’). The following are auto-generated

  - Status config starts with ‘s’

  - Custom Status starts with ‘u’

  - Framework entity starts with ‘m’

  - \<roadmap\> Archive entity starts with ‘a’

  - \<roadmap\> Union or archive and transactional entity starts with ‘v’

  - \<roadmap\> History entity starts with ‘h’

Each entity has one or more properties. Each entity property has one property type. Each property type has a domain assigned.

- Entity

  - Entity Property (1-n)

    - Property Type (1)

      - Domain (1)

Provide a unique entity name and mark if it is a root entity. The root entity is considered a BO. To define an entity you need at least one entity property, It could be either transient or regular (persisted in DB).

## kloRelation

Entity relation relates one entity with another entity. Relation has a unique name within the Entity. Relation name is used for accessing the result of the relation. Assessing getter of relation as property returns entitySet object which gets filled on ES.fetch() resolve and also triggers data change events. Relations are categorised as primary relation, aggregate relation and association.

- **Association:** An association is a structural relationship which connects one entity with another. Given an association between two entities, one can navigate from one entity to the other entity and vice versa. Association relations can be across BOs. By default, each relation is of type Association if it is not marked as Aggregated or Primary.

> Example1:

- d_order_item (source)

- d_material_master (Related)

> Create a relation to show the material description, LOB, or other properties of the material.
>
> Example2:

- d_order_item (source)

- d_order (Related)

> If you want to navigate from the order Item to the order header. Define a relation between the Item as Source and Header as Related entity.

- **Aggregated Relation:** Aggregation is a type of association where two entities(tables) are tightly bound. In some cases, we might come across “whole-part” relationships between two Entities, in which one entity is a part of another entity. Such a relationship is known as an aggregation. An aggregation relationship can be described in simple words as "an object of one class can own or access the objects of another class. Aggregate relations can be across BOs.

- **Primary Relation:** This is a special kind of aggregate relation within the BO boundary. All entities in a BO are navigable from the root entity once unidirectional and only once. Below are the use cases of a primary relation:

  - Message processing

  - Keymapping

  - Find Parent

Example:

- d_order ( root entity)

  - d_order_item

    - d_order_conditions

Here d_order is the root entity and the other two are child entities in Order BO. Hence relation has to be defined between these entities.

Create a relation on d_order entity with d_order_item of type “Primary” and query property is “order_id”.

Create a relation on d_order_item entity with d_order_conditions of type “Primary” and query properties are “order_id” and “order_item”.

**Define Relationship:**

Let’s create a relation between two entities using the Data Studio. To create a relation go to the source entity where you want a relation with another entity. Provide a unique Relation name. JOIN is constructed based on the defined relation.

**Extends:** extend the existing property type to access the parent attributes and overwrite if needed. You can only extend one propertytype in your child propertytype. In the extended property type fill only the attributes which you want to overwrite, all other attribute values are inherited from the parent. Domain type, length, precision can not be changed in extended property type.

Extend property type if:

- Data type, length, precision are same as these are not allowed to change in extended property type.

- One or more properties are different from the list below:

  - Authorization

  - Value help

  - Text ID

  - UI Formatting

  - Min/Max value

How to remove an attribute value in extended property type? Set null or empty string

For example, you have created one property type called ‘customer’ and Text is provided as ‘Customer Name’. But in some scenarios you want to show the text as ‘Sold To Party’, in this case extend the ‘customer’ property type and create a new property type as ‘sold_to_party’ and change the text.

A extends B. B extends C. All attributes of C are extended to A if not overwritten in B.

**Reuse**: To define the common behaviour of multiple Entity/Query Properties, Property type can be reused across entities.

It should be reused if entity properties are logically the same.

- Ordered Qty and Del Qty - not to use the same property type. But Ordered qty in two diff tables should share the property type.

- Property type should be different for Vendor and Customer fields in the same or diff entity. Both should be extended from BP ID because the data type should be the same for all.

- It is recommended to use the same property type for a field which is used in multiple tables as foreign keys. To understand this better let’s take an example of the Material Code field which is part of Material master as a primary field but also part of other tables like Order and Logistics items.

**Authorization:**

Authorization restricts the access of data(rows) valid for current logged-in users. Authorization on any entity of a BO is applied on the whole BO. Authorization is defined on Property Type and applied for all queries to the Entities wherever that Property Type is used.

Do not apply Authorization on Query Property.

For example, logged in users should be able to see only the Orders that belong to them. Below is the Entity definition:

| **Entity** | **Entity Property** | **Property Type** |
|------------|---------------------|-------------------|
| d_order    | order_id            | order_id          |
| d_order    | order_date          | order_date        |
| d_order    | customer_id         | cust_id           |
| d_order    | net_amount          | amount            |

Here apply the authorization on “cust_id” Property Type to filter the orders of particular customers. If the same Property Type is used at other places, authorization will be applied on those entities also.

In case you do not want to apply the authorization at all entities or apply the authorization at only one place, then extend the base property type and create a new Property Type.

Variables Supported:

- \$Variable

- Constants

  - Syntax: const1, const2

In case authorization is applied on more than one property or multiple values in one property. Below is the behaviour:

1.  AND Operator: If authorization is applied on multiple properties in the same BO with different property types, all parameters will be ANDed.

    1.  Example1: There are two properties in d_order entity customer and sales_person both have different property types. If authorization is applied on both, this will be ANDed.

2.  OR Operator: Used a property type with multiple entity properties in the same entity, all parameters will be ORed. (Reuse property type within entity). At the same time it will be ANDed with other parameters.

    1.  Example2: There are two properties in d_order entity: customer and vendor both have the same property type, in this case both parameters will be ORed.

3.  IN Operator: If Multi values qualify for one property, all values will be considered with the IN operator.

    1.  Example3: Authorization is set on the state field in d_order entity and multiple values passed at runtime, in this case all values will be passed with IN operator.

**TypeScript Class:**

TypeScript is a typed superset of JavaScript that compiles to plain JavaScript. TS is an object oriented programming language with classes, interfaces and statically typed like C# or Java. This supports Inheritance, Abstraction, Polymorphism and Encapsulation.

**Import:** to access any other typescript class you need to import the class in the declaration section of the class. Maintain the import class in metadata. Framework will generate the import statement with a full class path. Only current flavor and shared flavor classes can be imported.

- EntityName (Current flavor or shared flavor) or

- BO Util Class Name: Full file path of Import class

Syntax:

**Inheritance**: inherit a class or interface by using **extends** keyword. All actions, variables in parent class are available in child class and can be overridden. Parent class has to be imported in Child class.

Framework will generate the *extended* statement in file. Developers can not define inheritance.

Typescript supports Multilevel inheritance but not Multiple inheritance.

Syntax:

> class child_class_name **extends** parent_class_name

***this*** keyword: ***this*** refers to the current instance of a class.

***super*** keyword: ***super*** refers to the current instance of the superclass in the child class.

**Regular Action:** On creation of an entity, Framework provides a \<entityname\>\_gen.ts file which contains pre delivered setters and getters of all Entity properties, Relations, VH, etc. Framework also provides a class \<entityname\>.ts which inherits the generated class(\<entityname\>\_gen) and developers can write their own action inside this class. These are reusable actions and accessible with EntityInstance in any Controller or Rules or Middleware and returns the desired result.

- On update of Entity/ EntityProperty the generated file will get adjusted by Framework.

- Can add the Import in \<entityname\>.ts class in metadata.

- Can not add additional imports in \<entityname\>\_gen.ts class

Naming conventions:

Generated Class: \<entityname\>\_gen.ts

Entity Class: \<entityname\>.ts

Regular Action: public \<actionName\>(parameters) : \<return type\>\{ \}

It is recommended to follow the camel casing in Action names.

File Path: *flavor_version \>\> BO \>\> Class.ts*

Syntax to call Function: *\<entityInstance\>.\<function name(parameters)\>*

- Define any number of Regular Actions in a class.

- Regular Actions are always public.

- \<entityname\>.ts class extends the generated class(\<entityname\>\_gen). The ***Extends*** statement is generated by the framework.

- You can access the related entities object of BO’s using *‘this.\<relation name\>.fetch()’ *in the entity class . *‘this.\<relation name\>’ *returns the EntitySet of the related entity instance. For example, Order BO has the order_item as a child entity, accessing the item entity object using *‘this.rel_order_item.fetch()’.* The result set of the relation has to be type casted in relevant class objects. It is recommended to use a variable and store the return value in a temporary variable.

> *let order_items : Entityset\<order_item\> = await this.rel_order_item.fetch();*

- Regular Actions of Entity class are available as a help on Entity instances while writing code.

For Example, you want to check the stock of a material. Define a function called ‘*checkStock(materialId:String)*’ and write your business logic. Now this Regular Action is accessible wherever Entity Object is available.

**Rule Subscription Actions:**

Rule subscription actions are defined in the Entity Class(Developer Defined) or Utility Class and receive *EventContext* as a parameter. The defined actions can be subscribed only against that Entity. It is recommended to define rule subscription functions in the Root entity class.

- Define Rule action in metadata.

- Multiple ‘Rule Actions’ can be defined in one Entity class.

- Rule action should be public.

- Can call Regular and Private actions inside Rule actions.

- Syntax: *public \[async\] \<rule action name\>(event: EventContext)*

- This should generally return Promise\<Any\>. Promises should be resolved with Success or Error. If resolved with Error, the error code returns to the caller and this error results in a rollback and the whole transaction will get rolled back.

- Inside an Action if Promise is not returned then it is assumed to be a synchronous action.

- At a time only one rule is getting executed and other Rule actions are in waiting state. Promise has to be resolved ‘Success’ before executing the next Rule. If it is a synchronous action and does not return the Promise, immediately after finishing one rule execution it moves to the next action for execution.

- Can not change Rule action signature. Otherwise it will be considered as ‘Regular Action’.

- Can not subscribe to other Entity Class’s Rule subscription Action.

- Call Regular Action in Rule- Regular actions defined in Entity class \<entityname\>.ts can be accessed in the Entity Rules actions.

  - Syntax: *this.\<actionName\>(parameters)*

- *Call regular action in BO Util class’s Rule action*

  - *eventContext.getObject() will return the Entity instance on which the rule has been subscribed. Call the Regular action on the returned instance.*

**Entity Remote Action**: This is to execute an action on the server side from Client. If there is a requirement where you want to execute an action on the server side irrespective of whether the application is running ONLINE or OFFLINE. In case if the server is not reachable due to any reason, it will end with an error.

Syntax: *\<entityInstance\>.remoteActionP(\<action name\>, …..args, commitClient, commitServer).*

- Define Remote action in metadata.

- Do not use Remote action as Regular action and vice versa.

- Can not call Private remotely.

- In case if remote action is called from the server side, the behaviour is the same as Regular action.

- Whatever modified on the client side is available on the server also(only the BO remote action called).

- Anything modified inside the Remote action, the modified state of the BO will reflect back on the client side.

- Dirty BO Commit on server and client side(save data in client DB) is based on the parameters ‘*commitClient’, ‘commitServer’* passed. TRUE means commit and FALSE means do not commit.

- Default value: *commitClient: FALSE, commitServer: FALSE*

- All subscribed Rules get executed in case of commit.

- Middleware message: remote action save on client side should not generate the middleware message to sync to server because it is already saved on server. This can be controlled by the application developer.

- Exception handling:

  - In case any error occurred on server side commit, remoteActionP(..) will return the reject.

  - If the server side commit is successful and the client side is failed, the application has to handle this.

  - Network error: Server side commit is successful but due to network error client did not get the success in response. In this case, remoteActionP(..) will return an error. Assume that remote actions can be executed multiple times so do not write any code which may create problems in case of multiple commits. Write this type of calculation logic on the client side.

&nbsp;

- This returns what actual action returns with promise and Promise has to be resolved. This also modifies the BOs participating in the transaction and modified BO is available at client side.

## Rules

A Rule is a program containing business logic written by a Developer as per the application's needs. It works with the event bus, any change in entity triggers the event, all the rules hooked to the event bus are executed sequentially. Rules are reusable objects across client, server and middleware. Based on subscription it is executed in the given environment.

**Define the Rule:**

- Define ‘Rule Subscription Action’ in Entity/Query/Util class as a rule

- Define a rule with below inputs

  - Rule ID - unique ID across all entities and queries.

  - Class name: provide a class name it creates a new instance of a given class. Class could be Entity, Query, Util.

  - Method: enter Rule subscription action name without signature.

  - Mime Type: TS / JS

  - Description

**Subscribe Rule:**

You can subscribe to a Rule for any Entity which can be executed based on the Event type assigned. Rule subscription is part of kloIDE. To subscribe to a Rule you need to provide below details.

Recommended to subscribe to the rules on the root entity of BO.

Rule should generally return the Promise\<Any\>. Promises should be resolved with Success or Error.

- Rule ID(PK): select existing rule on BO.

- BO Event Subscription ID: this is auto generated id.

- Event Type:

> ON_CREATE : execute on creation of Entity.
>
> CREATE_NEW_FROM_TEMPLATE : execute only if executeCreateFromTemplate() method called from application. ( deprecated)
>
> ON_UPDATE : execute only on update entity.
>
> ON_DELETE : execute only on delete entity.
>
> \<roadmap\>BEFORE_MAPPING
>
> \<roadmap\>AFTER_MAPPING

- Some additional Event types on Root Entity(BO)

> ON_SUCCESS : execute only after the successful transaction of a BO.
>
> ON_ERROR : execute only if the transaction failed for a BO.
>
> ENDPOINT_RESOLVER : this is to get all the endpoints to push the kloBroker message. This gets called on every create/update/delete of a BO.

- Object Group: This is optional and If Object Group is not specified, it will get called for all objects of that entity.

- Channel Type: there are different input channels to perform a transaction on an entity, channel type selection decides when to trigger the Rule.

  - **All**

  - **Endpoint/Device to Klarion Server**

  - **Endpoint/Device to Klarion Server---ALWAYS ON CLIENT**

  - **Endpoint/Device to Klarion Server---ALWAYS ON SERVER**

  - **Endpoint/Device to Server/Client---NETWORK CONTEXT SWITCH**

  - **Klarion Server to Klarion Offline Server**

  - **Klarion Server to Klarion Server**

  - **Legacy to Klarion Server**

- Sequence No(Mandatory): Decides in what sequence Rule to be executed. In case multiple Rules subscribed, sequence of rule execution is followed. All positive numbers(1-n) excepted. It is recommended to maintain the sequence like 10, 20, 30 and so on. So that any new Rule can be maintained in between without disturbing the other rule’s sequence.

Rules are reusable hence can be subscribed multiple times with different Channel types or other combinations.

Qualification of rules for execution:

### Channel Type

1.  Offline Mobile Application.

    1.  On offline Network mode dirty entity is saved rules are filtered based on

        1.  All

        2.  Endpoint/Device to Klarion Server---ALWAYS ON CLIENT

        3.  Endpoint/Device to Server/Client---NETWORK CONTEXT SWITCH

    2.  When message received on server from mobile following rules qualifies

        1.  All

        2.  Endpoint/Device to Klarion Server---ALWAYS ON SERVER

    3.  When Message is received from Server to mobile client

        1.  Klarion Server to Klarion Offline Server

2.  Online Application

    1.  On online Network mode dirty entity is saved rules are filtered based on following on client

        1.  All

        2.  Endpoint/Device to Klarion Server---ALWAYS ON CLIENT

    2.  On online Network mode dirty entity is saved rules are filtered based on following on server

        1.  All

        2.  Endpoint/Device to Klarion Server---ALWAYS ON SERVER

        3.  Endpoint/Device to Server/Client---NETWORK CONTEXT SWITCH

3.  Tenant to tenant

    1.  On receive on server

        1.  All

        2.  Klarion Server to Klarion Server

4.  From Legacy to Tenant

    1.  On receive on serve

        1.  All

        2.  Legacy to Klarion Server

How to choose channelType:

For Tenant to Tenant (K2K) there is nothing much to choose. Same for Legacy to Tenant (L2K)

When it comes to core processing, we are talking about interoperability of network mode. Selecting event types for part of code becomes critical.

### Execution sequence of rule

If any change in the DataSet of an Entity at any level of BO. Root entity is also set to WriteSet.

- Rules will be executed for all dirty objects one by one. Each record in an entity invokes the Rule.

- Execution is from Leaf Entity(of BO) Rule till Root Entity Rule for all WriteSet .

  - First call all rules of the lowest level( Leaf Entity in a BO) Entity.

  - If multiple BO changes are there in one WriteSet, first execute the rules of the lowest level entity in all BOs then next up… then next up.

  - Within one BO if multiple entities are dirty but Root entity rules will get called only once for one BO.

- At the same level rule execution is as per sequence number( smallest is the top priority).

- Execute rule is based on Channel Type.

- Again jump to Child entity Rule if any modification by parent entity Rule.

  - Example: For a BO all child entity rules are executed and now executing the Root entity rules, in that one child entity object is updated by root. Now only the updated child entity rules will get executed and root entity rules will not get called again.

### Control Transaction in rule

- Rollback Transaction: This cancels the full transaction and refreshes the Changeset/Writeset.

- Stop Rulechain only for the current entity Instance.

- Stop Rule chain only for the current BO instance.

- Eliminate the object from the writeset (refresh entity/BO using *‘refresh(deepRefresh)’*) :

- Flush Changeset (commit) : *Flush current transaction* with intermediate commit. - Deprecated. Use the parallel transaction getTransactionParticipatingObjectsAtLevel();

- **Note**: Developers should **not use commitP() by using the same transaction at the rules callbacks**. e.g., get the transaction from oEvent (function parameter) and use that for commitP() later on in the rules callback.
  > Validation added in case the same transaction is being used for commitP() from callbacks throwing an error as “**Transaction commit is already in progress. Please wait for the current commit to finish before calling commit again.**“.

- Rule callbacks are now triggered on every transaction commit, even after a previous commit failure. This ensures consistent callback execution on the client side and also on the server side.
