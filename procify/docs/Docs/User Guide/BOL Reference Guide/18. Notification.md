# Notification

Notification is an alert message like sms, email and notification in an app([*fcm*](https://firebase.google.com/docs/cloud-messaging)). Notification can be sent whenever it is required. This will work similarly like an endpoint resolver, it can send notification for multiple receivers.

Types of notifications:

- Email notification

- SMS notification

- Application Notifications (fcm)

**API in javascript -**

var notificationEP = event.addNotificationEndpoint (**Template_id, Channel,Object**);

Possible receiver ID can be for email TO and CC

To persons can be set using setTO

notificationEP.setTO(\[**“userid1”,“userid2”\]**);

To keep CC for emails use To setCC

notificationEP.setCC(\[**“userid3”,“userid4”\]**);

These API are available in all type of exits(i.e ON_CREATE, ON_UPDATE, ENDPOINT_RESOLVER)

**Template Maintenance:**

Notification information should be maintained in the **m_notification** table entity so that notification mapping can be maintained in this table. This has a column for enabling different types of notification (i.e enable_email,enable_sms,enable_app) Template that has to be maintained in m_notification_template table and template can maintain channel type combination (i.e template id same but content is different for channel type). In this table we can maintain content.

**Exits while sending Notification:**

Notification exit can register, this exit is similar to normal exits but in this exit **event.getObject()** will return json object, not entity instance. Here, the json object can be modified at the end this json will take to manipulate the template.

In this exit, all features are available like getEntityQuery, getQuery, getBOQuery, loadEntity can create a new entity at the end it will commit.

**Notification working flow:-**

This is similar to an endpoint resolver, it will collect entity, sender details, channel and template id at the end of the transaction it will put to queue. After that scheduler will take this data from the queue and it will send notification to the respective receiver.

**SUCCESS** log goes to the **dmqp_tenant_log_q** table and **FAILURE** log goes to the **dmqp_tenant_error_q**.

**Sender Details:-**

Multiple sender details can be maintained, it will take sender details in a round robin algorithm.

Sender details have to be maintained in the config.json.

**Template Details:-**

Template details has to maintain **m_notification_template** table:

| **Template Details** | **Functionality**                                                                                                                                |
|----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| **template_id**      | It is the ID set by the caller.                                                                                                                  |
| **body**             | It is the actual detailed content of the notification that is required to be shared.                                                             |
| **channel**          | The channel or mode through which the notification is to be sent. This can be SMS, Email or Applications.                                        |
| **setURL**           | For Notification type APP config value URL can be specified using the following method:notificationObect.setURL(“index.html#work_order/detail”); |
