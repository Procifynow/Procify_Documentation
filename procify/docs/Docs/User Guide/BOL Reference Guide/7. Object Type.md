# Object Type

Object Type defines the possible behaviour of an BO/Entity. Object type has a unique key and description. Object type key is unique across all entities and can not be reused across entities. One entity can store multiple objects data if behaviour of the objects are different then define multiple object types. On the Entity Config, role based filters can also be enabled. Once the role is enabled, config picks the row from *klotuner* where object type and role both match. Works when has_object_type is marked TRUE for an entity. Do not add any Entity property to add object type field, this will be taken care of by kloBase based on the Object type flag on Entity level.

- Possible object types for an entity have to be defined at design time and maintained via kloIDE.

- Data type is **int(11)**. Max value is 2147483648.

- Supports merging based on user relations.

- s_object_type holds the object type key.

- Descriptions are part of value help definition.

Constants for Object Type.

- If the object type is false for an entity then -1 is a reserved value.

**Abbreviation :** define object type abbreviation like ‘i’ for invoice and ‘o’ for order. This abbreviation can be used in ID series as a prefix. Syntax: \$objecttype.abr

Variable to be used:

- Constants

- \$VARIABLE

Object Group to Object Type

Object Type to abbreviation

Object Type to Object Type text

**Display Messages:** Object type description supports translatable description use as substitute in title, message, etc with \$objecttype.dec. Define language dependent text to support multilocal.

**Create Entity:** while creating an Entity, Object Type has an important role to load the configuration, assign ID from ID series, Rule to be executed, VH to be loaded.

**Tuner**: configurations are maintained on object type to control the behaviour of the application. For more details please visit the *Config* section.

**Rule subscription:** rules are subscribed on Entity and Object Type.

**ID Series:** ID series can be defined on object type or common for all object types.

**Middleware** Message processing can be controlled in an endpoint resolver.

Create operation (in UI-action or Rule) decide which object type to be used. From UI you can pass only the Object types which are part of the Object Group of that screen.

UI elements behaviour can be defined like editable, visibility, mandatory, etc.

**Not supported:**

- Authorization is not applied on object type.

For example there are different types of orders. Object types in Order can be defined like:

- Normal Order

- Emergency/Fast Track Order

## Object Group

Collection of Object Types is Object Group. Screen usage Object Group which defines the behaviour of a particular screen/object. Object types of similar kind of behaviour and going to be used in one screen has to be bundled in one Object Group.

- Object Group to Object Type mapping(m:n): One object type can be part of multiple Object Groups.

- One screen can have only one Object group.

**Abbreviation :** define object group abbreviation like ‘i’ for invoice and ‘o’ for order. This abbreviation can be used in ID series as a prefix or some other cases where you want to differentiate the object.

Usage:

- Screen

- Rule execution

Example:

> Object groups in Order:

- Sales Order

- Purchase Order

- Stock Transport Order

## Status

The Status of an object represents the current state of a particular object. Possible status of transactional objects is maintained in a meta model using kloIDE which has Key and Description.

Based on the current status of the object, screen behaviour can be controlled like Visibility, Read-only, Actions, other behavioural decisions, etc.

- Work when has_status is marked true for an Entity. s_status column is created in all the entities where Has Status is marked as True which holds the status key.

- Supports merging based on user relation.

To understand Status usage let's take an example. There is an Order placed on any online web portal. Order has the status like

- Order Placed

- Dispatched

- Delivered

- Cancelled

- Returned

Here the first three status are sequential but order can be cancelled only with the status “Order Placed”, “Dispatched”.

Also “Dispatched” and “Delivered” status can be changed by Delivery Boy or Backend team but “Cancelled” status can be set by Customer, Supplier Backend team and Customer Care Executive.

Status Types:

- None

- Single

- Multi valued

Custom status

- Customization of status as per account/rollout.

- Works when status is marked true for an entity.

- Possible mapping between status as per implementation is maintained in m_status_custom table as metadata.

- Supports merging based on user relation.

- Used in the implementation phase.

- s_status_custom holds the value of the custom status key.

- Description, icon or additional properties will be part of value help definition.

- Object type will have -1 if the entity does not have object types.
