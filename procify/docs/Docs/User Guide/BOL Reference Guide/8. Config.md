# Config

kloConfig is application data defined during application development and embedded together with code.

kloConfig data is maintained using kloTuner. kloConfig behaves like a read only entity, columns/property/fields called config property is defined by the application developer. Developers can specify multiple rows/ value set/ entityset for the particular configuration. Klobase selects and returns the qualified row at runtime.

kloConfig is used to customise the application flow by using the variable value in code for decision making , or in UI for enabling disable/ controlling visibility of UI controls.

All kloconfig except \$Role are customizable per flavor, although best practice does not advise to change values across flavor.

Broadly config needs below three parts to be completed to work:

1.  kloConfig Definition: modelling kloconfig by defining config properties with its type and Value Help if required. It follows a similar approach as entity definition. Providing default value is must for each config entity property, Default value is used for returning the value until real object values are loaded, hence default value must be most restrictive.

2.  Maintaining ValueRow per unique key. It should be done using kloTuner. Each row should be self-sufficient, it does not borrow values from other rows.

3.  Using the value: filtered row is returned by API, these APIs are async. To ensure value is loaded use fetch() to resolve. Until fetch resolves, the config object returns the default config property value.

Configuration controls or changes the behaviour of the application. Below are the different type of configuration supported:

1.  Entity Config

2.  \$Role Config

3.  Entity Status Config

4.  App Global Config

## Entity Configuration

Possible set of configuration for an entity by which the application process flow or behaviour is controlled.

- Works when an entity is marked with ‘Has Config’ TRUE and configuration entity properties are maintained.

- Entity Naming convention: Framework creates a Configuration Entity.

  - It is calculated from the entityname by replacing the first character to ‘c’. For example the main Entity is ‘d_order’ then configuration Entity gets created with the name of ‘c_order’.

  - Entity names should use only english lower case alphabets (a-z), digits (0-9) and underscore (\_) and upto 31 chars max length.

- Configuration is Object Type and Flavor based. In case of no object type applicable to an Entity, default Object Type is -1.

- Configuration can be defined on any entity in a BO but it is recommended to define at root entity level. In case a child entity does not have an object type but the root entity has the object type, it does not consider the root entity object type.

- Metadata definition(Entity properties) for configuration entities is to be filled using Data Studio. Each config has to be defined as Entity Property in Config Entity.

- Possible values for a Config have to be maintained through kloTuner.

- Configuration is accessible throughout the application including Rules and middleware.

- \<entity instance\>.configP will return you with a single row of the configuration maintained for this entity with respect to the current object this holds. If no object type is found / has an object type that is false, the framework will try to find a default configuration with -1 as the default object type.

- If no configuration is found, return an empty object.

- Define the configuration structure in Entity owning flavor only. Not customizable in other flavors.

- Configuration values are customizable across flavors.

**Steps for configuration:**

- Mark ‘Has Config’ for the entity (d_order) in Data Studio.

- Framework creates a Configuration Entity.

- Add the properties in Data Studio with new Entity for all configurations.

- Run Update *schema* to create/update a database table. One Entity has only one Config table and one value per Object Type in a flavor.

- Define the possible values allowed for a configuration property in kloTunner. Each possible value has some meaning and definition or implication of that value also to be explained in detail. This helps consultants to change/maintain the configuration.

- Write business logic based on possible values of each configuration. Application behaviour can be controlled on client side or APIs/Backend based on the configured value.

For Example, Sales Order has few configurations like:

- Credit Limit Check

- Free Goods

- Order Approval

- Order Close

- ATP Check

- Expected Delivery Days

- Part Delivery Allowed

Configuration Entity name: **c_order**

| **Field Name**     | **Data Type**        | **Possible values**      |
|--------------------|----------------------|--------------------------|
| s_object_type      | int(11) **(pk)**     | All object types         |
| s_role             | varchar(32) **(pk)** |                          |
| credit_limit_check | boolean              | TRUE/FALSE               |
| free_goods         | boolean              | TRUE/FALSE               |
| order_approval     | boolean              | TRUE/FALSE               |
| order_close        | boolean              | TRUE/FALSE               |
| atp_check          | boolean              | TRUE/FALSE               |
| expected_del_days  | int(11)              | Only Numeric values \>=0 |
| part_del_allowed   | boolean              | TRUE/FALSE               |

APIs:

| *\<entityinstance\>.config*                                                              |     |     |     |
|------------------------------------------------------------------------------------------|-----|-----|-----|
| Returns config values of an object.This returns only one record for a given object type. |     |     |     |

## $Role Config

If application behaviour differs on user role based, use role based configuration.

- Define Role configuration in Account “shared” flavor only. Not allowed to customise in other flavors.

- Config values can not be customised across flavor.

- Role and Designation of a user are two separate things. Example:

  - One user can have only one designation.

  - One user can have multiple roles assigned combined with ROT (Role+ROT is unique).

- Use for UI binding and business logic in controllers. Not available to use in server side Rules, MW because the role is not known in case of MW message processing, upload, etc.

- oController.getEnveronmentMap(\$role) will return you with a single row of the configuration maintained for logged in user’s role.

- Entity Naming convention:

  - Entity name is ‘env_role’.

**Steps:**

- Add the properties in Data Studio with new Entity for all configurations.

- Framework will take care of loading the config values. No need to write additional queries.

- Run Update schema to create/update a database table.

- Define the possible values allowed for a configuration property in Data Studio. Each possible value has some meaning and definition or implication of that value also to be explained in detail. This helps consultants to change/maintain the configuration.

- kloTunner facilitates the maintenance of the configuration. Maintain the config values for each configuration using kloTunner.

- Write business logic based on possible values of each configuration.

**Examples:**

- Manual header discount in order.

- Manual Item discount in order.

Configuration Entity Name: **env_role**

| **Field Name**     | **Data Type**        | **Possible values** |
|--------------------|----------------------|---------------------|
| role               | varchar(32) **(pk)** | All roles           |
| manual_hdr_dis_so  | boolean              | TRUE/FALSE          |
| manual_item_dis_so | boolean              | TRUE/FALSE          |

APIs:

| **Command**                           | **Description**                                                                             | **Example**                             |
|---------------------------------------|---------------------------------------------------------------------------------------------|-----------------------------------------|
| oController.getEnveronmentMap(\$role) | Returns config values of the user logged in. This returns only one record for a given role. | *o*Controller.getEnveronmentMap(\$role) |

## Entity Status Config

In case application behaviour differs based on custom status and object type, use status config.

- Define the configurations in account owning flavor. Not recommended to customise in other flavors even though it is supported.

- Config values are bindable to UI elements and can be used in UI and backend both sides.

- For a selected object only one row(set of configuration) is qualified. If no configuration is defined it will return an empty object.

- If the status value is not known and trying to get the status config, it will return an empty object.

- \<entityobject\>.statusconfig will return you with a single row of the configuration maintained for the selected record.

- Entity Naming convention:

  - It is calculated from the entityname by replacing the first character to ‘u’. For example the main Entity is ‘u_order’ then configuration Entity gets created with the name of ‘u_order’.

  - Entity names should use only english lower case alphabets (a-z), digits (0-9) and underscore (\_) and upto 31 chars max length.

**Steps:**

- If an entity is marked ‘Has Status’ TRUE, Framework creates an status config entity where object type and status fields are part of the primary key. Entity type is ‘Configuration Entity’.

- Framework will take care of loading the config values. No need to write additional queries.

- Add the properties in Data Studio with new Entity for all configurations.

- Run Update schema to create a database table.

- Define the possible values allowed for a configuration property in Data Studio. Each possible value has some meaning and definition or implication of that value also to be explained in detail. This helps consultants to change/maintain the configuration.

- kloTunner facilitates the maintenance of the configuration. Maintain the config values for each configuration using kloTunner.

- Write business logic based on possible values of each configuration.

Configuration Entity Name: u_status_config

| **Field Name**     | **Data Type**        | **Possible values**            |
|--------------------|----------------------|--------------------------------|
| s_object_type      | int(11) **(pk)**     | All object types               |
| s_status_custom    | varchar(32) **(pk)** | Status of selected object type |
| s_role             | varchar(32) **(pk)** |                                |
| flavor_version     | varchar(32) **(pk)** |                                |
| manual_hdr_dis_so  | boolean              | TRUE/FALSE                     |
| manual_item_dis_so | boolean              | TRUE/FALSE                     |

## App Global Config

App config is a complete custom config decided by the application team. Use Global config in case of common or across BO scenarios or the scenarios where Entity, \$Role and Status config do not fulfil the requirement.

- Define global configuration entities in any flavor. Customisation is allowed only in entity owning flavor.

- Depending on business requirements, multiple config entities can be created.

- Entity Naming convention:

  - Entity name starts with ‘cg\_’.

  - Entity names should use only english lower case alphabets (a-z), digits (0-9) and underscore (\_) and upto 31 chars max length.

**Steps:**

- Create a configuration entity. This entity should be a type of ‘Configuration Entity’. This is a completely customised entity.

- Framework will take care of loading the config values on demand and filter the config at application side. No need to write additional queries.

- Add the properties in Data Studio with new Entity for all configurations.

- Run Update schema to create a database table.

- Define the possible values allowed for a configuration property in Data Studio. Each possible value has some meaning and definition or implication of that value also to be explained in detail. This helps consultants to change the configuration.

- kloTunner facilitates the maintenance of the configuration. Maintain the config values for each configuration using kloTunner.

- Write business logic based on possible values of each configuration.

**Example:**

Need a configuration to sync the objects to SAP with the restriction of BP ID and object type.

Configuration Entity Name: cg\_sync_to_sap

| **Field Name** | **Data Type**     | **Possible values** |
|----------------|-------------------|---------------------|
| flavor_version | char(32) **(PK)** |                     |
| s_object_type  | int(11) **(pk)**  | All object types    |
| bp_id          | char(32) **(PK)** | BP ID or ALL        |
| enable_sync    | boolean           | TRUE/FALSE          |
