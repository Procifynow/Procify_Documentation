# Attachment

An attachment is any file or document that you upload against any object. Attachment component is used for uploading and downloading the mime (**images, videos, audio, pdf etc**). This is an entity level flag and it indicates that attachment is allowed to store against the entity. If enabled, the attachment link entity becomes part of the BO. Users can only add/edit/delete attachments when the component is in edit mode.

1.  Framework adds primary relation with attachment link entity and the Entity where attachment is enabled. The name of the relation is ‘attachments’. Within one BO, Attachment Entity can have relations with multiple Entities like order_hdr and order_items both are attachment enabled.

2.  Uploads a file in a common folder(local) and also maintains a link with the object.

3.  Mime gets pushed to the server repository via middleware.

4.  If the parent object is deleted, it deletes the attachment also but not the mime. Mime might have a reference with another attachment.

5.  Attachment with new entity: as attachment is part of the same BO, commit and rollback works like other entities in a BO. Mime upload to the local folder is separate and it does not rollback if the transaction is cancelled or failed.

6.  To upload or display the attachment UI controls are part of kloTouch.

Steps to enable the attachment for an entity:

- Import kloAttachment in Account flavor/s.

- Attachment config.

- Enable attachment in the entity definition.

- Define attachment type.

- Define attachment subtype.

- Call the APIs to upload and download the attachment.

Attachment config:

- Account

- Landscape

- Attatchment_upload_class: Fully qualified name of the attachment class which implements AttachmentHandler interface which has two methods upload and download. This class is to be written by an application developer. These methods are available in controller or Rule. Sample code is provided below.

  - Content repository: Location(base path) to store the mime on the server side is part of this upload class.

- min_battery: minimum battery required for upload and download. If the battery level goes down and the user tries to upload/download, it ends with an error/warraning.

Define Attachment Type: once “Has Attachment is marked TRUE, the attachment section in Data Studio will be enabled where you can define the attachment type. Below are the attributes:

- Attachment type: this is to categorise the attachment. Like Product, Equipment, Invoice, Profile pic, etc.

- Doctype: indicates that document type of attachment like user manual etc

- Max Files: max number of files allowed to upload.

- Download Type/Sync Type: WIFI, Battery Level, Always. Mime type: This specifies the accepted mime types of the mime. One mime type is mandatory. Multiple mime types are allowed with comma(,) as separator.

  - Allowed mime types are .jpeg, .png, .mp3, .3gp, .wav, .mp4, .pdf, .xls, .xlsx, .doc, .docx, .zip, .RAR

  - Application has to decide the mime types. There is no exclusion from the framework side.

- Size per file: Define the max allowed size (in KB) of a file to upload. If file size exceeds, it ends with an error. Size is defined per attachment type.

- Source: There are different sources from where media files are allowed to capture. Multiple sources are allowed with comma(,) as separator. If only one source is selected, it directly opens Camera or Gallery or Mice otherwise this gives the option to users to select a source for upload.

  - Camera

    - Take Photo

    - Record Video

  - Gallery/Folder

  - Mice

- Need Location: Capture GPS location while adding the attachment.

- Upload endpoint/location: location where attachment has to be dumped on the server. ( folder path, mount etc.)

- Entity Name: name of the transaction entity for which attachment to be allowed. Attachment should be enabled in Entity definition.

Define Attachment Subtype : subtype is just a categorization to store the

- Sub Type: it is a sub categorization(child) of attachment type and it is optional. For example, uploading images of type equipment with subtype as front side, back side, etc.

- Entityname:

**Attachment link:** This stores the entity attachment info. This link table has a primary relation with the transaction entity that means it is part of every BO attachment that is enabled. Table name is *‘dcatt_attachment_link’*.

- Attachment ID: GUID generated for attachment. This gets generated at the client side. Attachment ID is a unique id across all the endpoints.

- Attachment Type: passed from UI as parameter.

- SubType: passed from UI as parameter.

- File name: Input from application and this is displayed on the UI.

- Entity Key: This is a unique key with a combination of entity name and primary key set.

- Mime Type: mime type(file extension) of the attached mime. Only one value is allowed.

- GPS Location : If enabled in setting, it captures the GPS coordinates.

- Is default: This is input from UI at the time of upload. Default marked attachment is considered for preview or thumbnail in UI.

- Sequence: Sequence in which attachment is displayed in UI.

**Attachment APIs:**

- Update: update attachment info like file name, is_default, etc.

- Delete: Use the Entity delete API. This deletes only the attachment link and does not delete the mime.

&nbsp;

- Common folder : Common folder is used to store the mimes locally. This is hardcoded in the framework. While uploading the file it first copies the file to a local folder which might be different for mobile and desktop. Attachment id gets generated after the source of the image is copied to the common folder.

- Message processing: note that attachment entity and the mime are separate messages. Attachment entity message flow is similar to other entities and part of the parent entity’s BO.

  - Upload: Mime messages get stored in \_attachments table at client side and processed separately. From the device it is a direct Ajax call to the server for all the messages in \_attachments table. Once it is synced to the server it makes an entry in the d_attachment_log table.

  - Download: First check if mime is available in local storage. If not, a request is made from the device and mime gets downloaded to the local storage. This request is through middleware.

- Object cloning: attachment link is also cloned with the BO. This points to the same mime.

- Convert Object Type: attachment and mime does not get copied to the target object even though it is part of BO.

- Initial sync: write initial sync queries for attachment link.

  - Download all: for all attachments, it loads the mime immediately after initial sync is completed.

  - Download on demand: mime is loaded only on user request from UI.

- Send attachment with email: separate notification API. This is part of the Notification component.
