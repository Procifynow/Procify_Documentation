# How to enable Role Permissions

## 7.1. CRUD Permissions

- When an entity is created, CRUD permissions are enabled by default.

- These permissions are available to the **TESTER** role by default.

- The permissions are grouped under the default flavor-level permission group: **flv_master_grp**.

- Whenever a new flavor is created, the **flv_master_grp** group is automatically created for that flavor.

- You can verify these settings under **Page Builder** → **Permission Designer** → **Permission Groups** tab.

- Select **flv_master_grp**, then open the Entity Permissions tab to view all CRUD permissions.

- 

- **Refer** [<u>Permissions - User Guide</u>](https://docs.google.com/document/d/1LrdiK4cKTTItwJZRUUyfu9sO744EfMzW7vYsbTj4zss/edit?tab=t.0) **for detailed explanations.**

## 7.2. Flavor Master Permission(Permissions by default)

- When a new flavor is created, a master permission group named **flv_master_grp** is generated by default.

- This group initially contains only the **“TESTER”** role by default.

- To assign default permissions to any additional roles, add them to the **flv_master_grp**.

- Within this group, there is a custom permission called **flv_master_perm**.

- Any group having the **flv_master_perm** permission automatically inherits all permissions, regardless of what is configured in the Entity Permissions tab.

- The **flv_master_perm** is not exclusive to the **flv_master_grp**; it can be used in other groups as well, and the behaviour will be the same.

- Upon entity creation, permissions are automatically assigned to the **flv_master_grp** for that entity.

- To disable the impact of **flv_master_grp** permissions, simply remove all roles from that group.

## 7.3. Developer permissions

- Users with the **“DEVELOPER”** system role have all permissions by default, irrespective of entity-specific configurations.

## 7.4. Overriding Flavor Master Permission (Default Permissions)

- By default, all roles assigned under **Flavor Master Permission** have full access to all entities and menus within a flavor.

- If you need to **override the default permissions** or implement **custom Access Management**, follow one of the approaches below.

#### **Option 1: Modify Permissions for an Existing Role**

- Remove the role from default permissions (permission group) for whom permission changes are required.

- Create a new permission group with:  
  > **Entity-specific access** (e.g., restrict Create, Update, or Delete)  
  > **Menu-specific access** (e.g., hide or allow certain menus)

- Assign the newly created permission to the role.

#### **Option 2: Create New Roles and Permissions**

- Create a **new role** based on your access requirements.

- Define a **new permission group** with limited or customized access.

- Assign the newly created permission to the role.

- Remove the role from the old permission group (**default permissions**) and assign the new permission group.

> **Note:** Flavor Master Permission provides **full CRUD (Create, Read, Update, Delete) access** to all entities by default when assigned. Custom permissions are required to restrict or control access.

### **Example**

**Scenario:  
** A user with the **Inspection role** should only be able to **view** Data but should not be allowed to **create, edit, or delete** them.

**Steps:**

- Remove the role from the **default permissions** role.

- Create a new permission:

- Create a new role (e.g., *Flavor Viewer*).

- Assign the new permission to the *new (**Viewer**)* role.

- Assign the ***Viewer*** role to the user.

This ensures the user has restricted access while maintaining system security.
