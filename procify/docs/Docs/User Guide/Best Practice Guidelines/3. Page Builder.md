# Page Builder

## 2.1. Page

### Do’s

- Naming convention needs to be followed for page id’s.

  - Page id should start with

    - p\_

      - Example : p_orders, p_notification

<!-- -->

- The page should have only small letters.

## 2.2. Page Layout

### Do’s

- Naming convention needs to be followed for page Layout id’s

  - Page Layout ids should start with

    - Pl\_

      - Example: pl_desktop, pl_mobile

<!-- -->

- Page Layout should have only small letters.

## Page Area

### Do’s

- Naming convention needs to be followed for page Area id’s

  - Page Area ids should start with

    - pa\_

      - Example: pa_no_header_detail.

<!-- -->

- Page Area should have only small letters.

## 2.3. Section

### Do’s

- Naming convention needs to be followed for section id’s

  - Section ids should start with

    - s\_

      - Example : s_no_header_list

<!-- -->

- The section should have only small letters.

## 2.4. Embedded Section

### Do’s

- Naming convention needs to be followed for embedded sections

  - Embedded section id’s should start with

    - es\_

<!-- -->

- The Embedded Section should have only small letters.

## 2.5. Action

### Do’s

- Only use kloAction control as action buttons.

## 2.6. TransNode

### Do’s

- Naming conventions should be followed for transNode’s

  - Transnode name should end with

    - \_detail for entity type

    - \_list for entityset type

    - \_query for query type

    - \_other for other type

<!-- -->

- TransNode should have only small letters.

## 2.7. Controls

### Do’s

- Use kloInput control for

  - F4 - By providing vh_type as f4.

  - Combobox - By providing vh_type as combobox.

  - Autocomplete - By providing vh_type as autocomplete.

  - Input - By providing vh_type as none.

### Don'ts

- Don’t change the control’s class unless it is necessary.

## 2.8. Controller File

### Do’s

- Only UI related logics should be written in controller file

  - Example: formatter functions, navigation function.

> public navToDetail(oEvent){
>
> this.navToByEventss(oEvent,'s_header_detail');
>
> }

- Create a variable only if it is necessary

- While declaring a variable in Ts file make sure to maintain the type of the variable

  - Example:

    - let isValidItem: boolean = true;

    - let item:KloEntitySet\<d_order_item\> = this.tm.getTN("/item").getData();

### Don'ts

- Model properties should not be altered in the controller file(can be done in that \<entity_name\>.ts file). Only in case of any special scenario it is allowed.

  - Example: Functions like setting property based on another property change should be ignored, it should be written in entity file setter.

- Nested functions should not be used in the controller file.

- Don’t use deprecated API.

## 2.9. Entity File

### Do’s

- Only business logic functions should be written inside the entity file.

  - Example: The name property needs to be changed when first_name or last_name is getting changed

public set firstName(new_value:string){

if(new_value == this.firstName) return;

this.name = new_value+" "+this.lastName;

this.s("firstName",new_value,"string",false,false);

}

### Don'ts

- UI logic should not be written inside an entity file.

- Don’t use deprecated API.

### Examples:

#### Getter functions

public get name():string{

return this.Firstname +" "+this.lastName;

}

#### **<u>Setter</u>** functions:

public set firstName(new_value:string){

if(new_value == this.firstName) return;

this.name = new_value+" "+this.lastName;

this.s("firstName",new_value,"string",false,false);

}

#### **<u>onValidate</u>** functions:

public async OnValidate(){

if(this.priority === "1"){

this.errors.push(new ValidationError(this,"priority","11","Priority should not be High"));

}

#### **<u>onDelete</u>**

onDelete method will be called once the entity is deleted.

public onDelete():Promise\<any\>{

console.log("on deletion of entity");

return;

}

#### **<u>onAfterCreate</u>**

onAfterCreate method will be called once the new entity is created.

public onAfterCreate():Promise\<any\>{

console.log("on creating a new entity");

return;

}

## 2.10. CSS File

If CSS files are committed in a parent flavor, it's important to commit the same files in child flavors to maintain consistency and avoid discrepancies. If any updates or bug fixes are made to the CSS in the parent flavor, the child flavors will benefit from those updates if they share the same files.If a child flavor doesn't have the CSS files, it might result in missing or incorrect styling due to the lack of inherited rules.
