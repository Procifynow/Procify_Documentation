# Practical Examples

## Authentication

Obtain bearer token before making OData requests:

POST [https://\{customer\}.procifynow.com/p6/\{landscape\}/getToken](https://maven90.com/api/login)

Content-Type: application/x-www-form-urlencoded

**Request Body:**

username=\{user_id\}&scope=offline_access&password=\{your_password\}&grant_type=password&client_id=multi-tenant

Note : OData POST API supports bulk record creation by accepting an array of JSON objects

**Example:**

“username=john.doe&scope=offline_access&password=mypassword%401234567890&grant_type=password&client_id=multi-tenant”

**Response:**

\{

"access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",

"token_type": "Bearer",

"expires_in": 3600,

"refresh_token": "dGhpc2lzYXJlZnJlc2h0b2tlbg..."

\}

### Request Body (With Relational Data)

To send relational (child) data along with the parent entity in a single request, include the relation name as a key and pass an array of JSON objects.

\{

"FirstName": "John",

"LastName": "Doe",

"Email": "john.doe@example.com",

"Age": 30,

"Status": "Active",

"Department": "Engineering",

"RelationName": \[

\{

"Field1": "Value1",

"Field2": "Value2"

\},

\{

"Field1": "Value3",

"Field2": "Value4"

\}

\]

\}

### Request Body (With Relational Data)

To send relational (child) data along with the parent entity in a single request, include the relation name as a key and pass an array of JSON objects.

PATCH [https://fwtest.procifynow.com/odata/UT/odata_test_1-0-2/d_e1('01332d8cc3913b2f8848462c095e1e37')](https://fwtest.procifynow.com/odata/UT/odata_test_1-0-2/d_e1('01332d8cc3913b2f8848462c095e1e37)

\{

"descr\_": "UPDATED",

"boolean\_": 0,

**// 1::1**

"d_e1_d_child_aggregate_1": \{ "my_key": "fddd08b8cf723625a0737926af22a125", "descr\_": "UPDATED - PATCH", "boolean\_": **false** \},

**// 1::N**

"d_e1_d_child_primary_1": \[

\{ "auto_no": "1", "descr\_": "UPDATED - PATCH", "boolean\_": **false** \},

\{ "auto_no": "6", "descr\_": "UPDATED - PATCH", "boolean\_": 0 \}

\]

\}

Important Points:

1.  Primary Key Handling:

    1.  If the Primary Key value is provided in the request payload, the existing record will be updated.

    2.  If the Primary Key value is not provided or not matched, a new child record will be created under the respective parent entity.

2.  Relationship Cardinality Support:

    1.  For **1::1 relationships**, the related entity must be provided as an object. **Array or null values are not supported** for 1::1 navigation properties.

    2.  For **1::N relationships**, the related entity must be provided as an array having the object(s)

3.  PUT Method Behavior:

    1.  When using the **PUT** method, missing non-mandatory, non-primary properties will be populated with their **configured default values**.

    2.  **If no default value is configured**, the property will be set to null.

    3.  **Previous Behavior:** it was directly setting the value to null for the missing non-mandatory, non-primary properties.

4.  Transaction Handling:

    1.  Parent and child entity operations are executed within a single transaction. If any validation or processing error occurs, **all changes are rolled back**.

5.  Invalid relation IDs or property names in the request body are silently ignored with a warning logged, allowing the valid parts of the update to proceed.

6.  \$expand in URL:

    1.  GET with \$expand returns parent along with nested child entities in response.

    2.  URL Exmaple: [https://fwtest.procifynow.com/odata/UT/odata_test_1-0-2/d_e1('01332d8cc3913b2f8848462c095e1e37')?\$expand=d_e1_d_child_aggregate_1_1,d_e1_d_child_primary_1](https://fwtest.procifynow.com/odata/UT/odata_test_1-0-2/d_e1('01332d8cc3913b2f8848462c095e1e37)

    3.  If \$expand with the required relation IDs is/are not specified in the URL, the child entities will not be included in the response. However, the deep update operation will still complete successfully, since \$expand only controls the response representation and does not affect the update operation itself.
