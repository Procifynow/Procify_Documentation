The image: key selects the Docker container used for all steps in this pipeline. In our case, an AWS CLI image (such as atlassian/aws-cli or the newer amazon/aws-cli:2 ) provides the AWS CLI environment. The pipelines: and default: keys tell Bitbucket to run the steps on every push to the default branch. Each step: defines a set of shell commands to run sequentially. Bitbucket Pipelines executes in Docker containers, so we must pick an image with the AWS CLI installed to run AWS commands. The script: block under each step lists the actual shell commands. - Syntax notes: YAML is indentation-sensitive. image: is a top-level key (must be at root of file) . Each step has a name (optional label) and a list of commands under . It defines four named pipeline groups: 'run-public-master1', ‘run-public-master2’, ‘run-private-master1’ and 'run-private-master2', each containing a 'Run EC2 Instances and Setup' step and a manual termination step. This split allows separate network/security setups for public & private provisioning flows and master1 containing automations of editors and master2 containing tools and other components.

These export commands set AWS CLI environment variables in the pipeline shell. AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY are the IAM user’s credentials, and AWS_DEFAULT_REGION sets the region for CLI commands.The AWS CLI reads these environment variables for credentials and region. Setting them lets the pipeline authenticate to AWS. Bitbucket repository or workspace variables (configured in Settings) usually hold the secret key values, preventing them from appearing in code or logs. Securing these as “protected” or “masked” variables ensures they won’t be exposed in logs . In Bash, export VAR=\$VAR makes the variable available to all subsequent commands. The left-hand side ( AWS_ACCESS_KEY_ID ) is recognized by the AWS CLI to override any profile setting . The use of \$AWS_ACCESS_KEY_ID on the right assumes Bitbucket has provided those values from secure pipeline variables.

**Launching EC2 Instances (Windows)**

**\# Run Windows instance**

**- WINDOWS_INSTANCE=\$(aws ec2 run-instances --image-id ami-0eb8b40a83af1375b --count 1 --instance-type c6a.8xlarge --key-name "\$WINDOWS_KEY_NAME" --security-group-ids sg-03e9820e8626df68d --subnet-id subnet-61d33f2c --tag-specifications "ResourceType=instance,Tags=\[\{Key=Name,Value=\$instanceName\}\]" --iam-instance-profile \{\\Name\\:\\RSAGAR_CENTOS\\} --query "Instances\[0\].InstanceId" --output text)**

**- echo "Found instances \$WINDOWS_INSTANCE"**

\# Note: Linux nodes are no longer used in the new architecture

\# All automation runs directly on Windows systems with headless Chrome browsers

\# The commented Linux instance code has been removed from active pipelines

This command uses aws ec2 run-instances to launch a single high-performance Windows EC2 instance. The system launches using the updated Windows AMI ami-0eb8b40a83af1375b with instance type c6a.8xlarge for public networks (or c6a.4xlarge for private networks), applying parameters such as the Windows key pair (--key-name "\$WINDOWS_KEY_NAME"), security group sg-03e9820e8626df68d, subnet subnet-61d33f2c, a Name tag (\$instanceName), and the IAM instance profile RSAGAR_CENTOS. The --count 1 ensures only one Windows instance is created per pipeline run. The command returns JSON with details of the instance, and --query "Instances\[0\].InstanceId" --output text extracts the instance's ID and stores it in the WINDOWS_INSTANCE variable.

Why it's needed: In the new parallel execution architecture, each Windows system is capable of running 15+ automation suites simultaneously using headless Chrome browsers. The c6a.8xlarge instance type provides 32 vCPUs and 64 GB RAM, sufficient resources to handle multiple concurrent test executions without performance degradation. This eliminates the complexity of managing Selenium Grid hub-node connections while maintaining high throughput. Parameters like --image-id, --instance-type, and --key-name define the OS, compute resources, and login method, while tagging (--tag-specifications) makes identification easier.

**Key Architecture Changes:**

\- Single Windows instance per pipeline (no Linux nodes required)

\- Direct WebDriverIO to Chrome browser communication (no Selenium Grid)

\- Parallel execution managed by the operating system's process scheduling

\- Headless Chrome browsers for optimal resource utilization

\- Master1 and Master2 pipelines distribute workload across different automation categories

**Extracting Public and Private IP Addresses**

**- WINDOWS_IP=\$(aws ec2 describe-instances --instance-ids \$WINDOWS_INSTANCE --query "Reservations\[\].Instances\[\].\[PrivateIpAddress\]" --output text)**

**- WINDOWS_IP_PUBLIC=\$(aws ec2 describe-instances --instance-ids \$WINDOWS_INSTANCE --query "Reservations\[\].Instances\[\].\[PublicIpAddress\]" --output text)**

**- echo "windows public ip \$WINDOWS_IP_PUBLIC"**

These commands use the aws ec2 describe-instances CLI command to retrieve the private and public IP addresses of the EC2 instances that were just launched. For the Windows instance stored in \$WINDOWS_INSTANCE, the first command queries the PrivateIpAddress and stores it in the variable WINDOWS_IP. The second command retrieves the PublicIpAddress for the same instance and stores it in WINDOWS_IP_PUBLIC. Both values are extracted from the full JSON response using the --query parameter with JMESPath expressions, and the --output text option ensures they are stored as plain strings. The script then prints the Windows public IP address for logging or debugging purposes.

**Why it’s needed:** Retrieving IP addresses is essential for subsequent automation steps that require connecting to the instances — whether via RDP for Windows. By storing these IPs in variables, later commands in the pipeline can use them dynamically without hardcoding values. Logging the public IPs also helps with troubleshooting and verifying that the instances are accessible.

**Waiting for Instances to Be Running**

**\# Wait for Windows instance to be running and in a healthy state**

**- aws ec2 wait instance-running --instance-ids \$WINDOWS_INSTANCE**

**- aws ec2 wait instance-status-ok --instance-ids \$WINDOWS_INSTANCE**

These commands use the aws ec2 wait CLI feature to pause execution until the newly launched EC2 instances reach specific states. For the Windows instance stored in \$WINDOWS_INSTANCE, aws ec2 wait instance-running waits until the instance transitions from the pending state to running. After that, aws ec2 wait instance-status-ok ensures the instance has passed both system and instance status checks, meaning it is healthy and ready for use. These waits are blocking operations — the script will not proceed until AWS reports the desired state, ensuring subsequent automation steps don’t fail due to the instances not being fully ready.

Why it’s needed: Waiting for instances to be both running and healthy ensures reliability in automation workflows. Without this step, the script might attempt configuration or deployment actions on instances that are still booting, causing errors. This is especially important in CI/CD pipelines, where timing issues can break automated tasks.

**Configuring the Hosts File via SSM**

**\# Send SSM command to configure hosts file on Windows instance**

**- aws ssm send-command --instance-ids \$WINDOWS_INSTANCE --document-name "AWS-RunPowerShellScript" --comment "IP configs" --parameters "commands=\[\\Add-Content -Path C:\\Windows\\System32\\drivers\\etc\\hosts -Value '\$WINDOWS_IP \$WINDOWS_HOST'\\ \]" --output text;**

**\#**These commands use AWS Systems Manager (SSM) to remotely execute scripts on the launched EC2 instances, updating their hosts files so that the Windows host name can be resolved to its private IP address. The first command targets the Windows instance (\$WINDOWS_INSTANCE) and uses the AWS-RunPowerShellScript document to run a PowerShell command that appends a line to C:\Windows\System32\drivers\etc\hosts containing \$WINDOWS_IP \$WINDOWS_HOST. This effectively maps the private IP of the Windows instance to a hostname, enabling other applications or scripts to reference it without relying on DNS. The --output text parameter ensures the SSM command responses are returned in a plain text format.

Why it’s needed: Updating the hosts file allows both Windows instances to communicate using a hostname rather than a raw IP address. This is particularly useful when the private IP might change across instance restarts or when multiple services need a stable, name-based reference. Performing this configuration via SSM avoids the need for direct RDP, enabling automated, secure, and consistent setup from within the pipeline.

**Packaging and Uploading Project Files**

**echo "Zipping the project files"**

**- yum install zip -y**

**- yum install openssh-clients -y**

**- cd allAutomation; zip -r ../allAutomation.zip ./ ;cd ..;**

**- export BUCKET_NAME=klarion-openui5**

**- export S3_FILE_PATH_OPENUI5_CDN=openui5_cdn.zip**

**- export S3_FILE_PATH_OPENUI5=openui5.zip**

**- export LOCAL_FILE_PATH_OPENUI5_CDN=C:\Users\Administrator\Desktop\automation\openui5_cdn.zip**

**- export LOCAL_FILE_PATH_OPENUI5=C:\Users\Administrator\Desktop\automation\openui5.zip**

**- aws s3 cp s3://\$BUCKET_NAME/\$S3_FILE_PATH_OPENUI5_CDN .**

**- aws s3 cp s3://\$BUCKET_NAME/\$S3_FILE_PATH_OPENUI5 .**

**- zip -r build_output.zip .**

This sequence of commands prepares and packages project files, retrieves required dependencies from Amazon S3, and creates a final build archive. It starts by printing a log message (echo "Zipping the project files") for visibility, then installs the zip utility and openssh-clients via yum to ensure the environment has the required tools for compression and secure communication. The script navigates into the allAutomation directory, compresses its contents into a ../allAutomation.zip file, and then returns to the parent directory. Several environment variables are set for reuse, including the S3 bucket name (BUCKET_NAME) and both the S3 and local file paths for two OpenUI5 archives (openui5_cdn.zip and openui5.zip). Using these variables, the script downloads the two zip files from S3 using aws s3 cp, ensuring the automation environment has the necessary frontend resources. Finally, it creates a build_output.zip archive containing the current directory’s contents, packaging everything needed for deployment or transfer.

**Copy build zip to windows**

**- scp -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null build_output.zip Administrator@\$WINDOWS_IP_PUBLIC:"C:\Users\Administrator\Desktop\automation"**

After packaging the automation project and its dependencies into build_output.zip, the pipeline securely transfers this archive to the target Windows EC2 instance. This is accomplished using the scp command, which copies the zip file to the C:\Users\Administrator\Desktop\automation directory on the remote system. The use of -o StrictHostKeyChecking=no and -o UserKnownHostsFile=/dev/null ensures that the transfer is non-interactive and suitable for automated pipelines, bypassing host key verification prompts. This step ensures that all necessary automation code, configuration, and resources are available on the Windows instance for subsequent extraction and execution.

To securely provide sensitive credentials to the automation environment, the pipeline uses AWS Systems Manager (SSM) to remotely create a password.json file on the Windows instance. This is achieved by sending a PowerShell command that creates the required directory (if it does not exist) and writes a JSON file containing the user password, which is injected from Bitbucket pipeline variables. By leveraging SSM, credentials are delivered securely and are never exposed in the repository or logs. This approach ensures that the automation scripts have access to necessary secrets without compromising security or requiring manual intervention.

This batch file orchestrates the parallel execution of all automation suites, leveraging the freshly extracted code and configuration. Each automation runs in its own command prompt window, enabling concurrent execution and real-time logging. This step is critical for initiating the actual test runs and ensuring that all automations are executed as intended in the AWS environment.

**Cleanup: Terminating the Instances**

**- step:**

**name: "terminate windows instances"**

**image: amazon/aws-cli \# Using AWS CLI Docker image**

**trigger: manual**

**script:**

**- source set_WINDOWS_INSTANCE_env.sh**

**- aws ec2 terminate-instances --instance-ids \$WINDOWS_INSTANCE**

This step defines a manual trigger in the Bitbucket pipeline for shutting down both the master (Windows) EC2 instances once they are no longer required. Then it uses source set_WINDOWS_INSTANCE_env.sh to load the \$WINDOWS_INSTANCE variable from a previously saved environment file. With these variables in place, the script executes aws ec2 terminate-instances commands— Windows instance in \$WINDOWS_INSTANCE. This action schedules the EC2 instances for termination, freeing up AWS resources and preventing unnecessary billing charges.

Note: However, if this step is **not performed manually**, an automatic **termination policy is defined in AWS** to shut down all the systems **after 2.5 hours**, regardless of whether the automation processes have finished. This ensures that orphaned instances do not continue consuming resources indefinitely, though it may cut off long-running automation jobs if not completed within that timeframe.
