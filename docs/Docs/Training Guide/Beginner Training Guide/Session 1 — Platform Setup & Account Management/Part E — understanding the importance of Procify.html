Part E — understanding the importance of Procify

Every application starts the same way: someone hands a developer a requirements document and says 'build this.' The Customer complaints Application Business Requirement Document (BRD) you read in Session 1 defines exactly what data needs to be stored — 3 data objects, their fields, and their relationships. The first job as a developer is to turn those definitions into a working database schema.

Before opening any tool, it is worth understanding what that process looks like — and how much of it Procify eliminates. The rest of this part walks through the traditional process step by step, then shows exactly which steps the data studio replaces.

What Is a Schema?​

📘 Schema — The Blueprint of Your Application's Data • A schema is the complete definition of the data your application stores: what tables exist, what columns each table has, what type of data each column holds, and how tables relate to each other.
The schema is the foundation of every application. Without it, there is no database. Without a database, there is no data. Without data, there is no application.
Building the schema is always the first development task after reading a BRD. Everything else — APIs, Pages, logic — is built on top of it.
In our BRD, the schema is already defined in Section 4 (Entity Relationship Overview). The 4 entities, their properties, and their relationships are all there. Our job today is to implement that schema.

The Traditional Way of Building a Schema​

🏗 How developers build a schema without a low-code platform • Step 1 — Write SQL scripts: A backend developer writes CREATE TABLE statements for each entity. For the Delivery table alone, that is 12 columns — each with its SQL data type, constraints, default values, and indexes.
Step 2 — Write an ORM model: For every SQL table, the developer writes a model class in the backend language (Node.js/TypeScript, Python, Java). This class mirrors the database table and handles object-relational mapping.
Step 3 — Write REST API endpoints: For each entity, the developer writes GET, POST, PUT, DELETE API handlers. Each handler validates input, maps it to the model, executes the database query, and returns the response.
Step 4 — Write validation logic: For each property that has rules (mandatory, unique, min/max), the developer writes validation code — either in the model or in the API handler.
Step 5 — Handle database migrations: Every time the schema changes (new property, renamed column), the developer writes a migration script to alter the existing tables without losing data.
Step 6 — Test the API: The developer uses Postman or writes unit tests to verify each endpoint returns the correct data in the correct format.
Repeat for all 4 entities.
🔴 The pain of the traditional approach • Multiple files across multiple layers — SQL files, model files, API controller files, test files. A change to one field requires edits in 4–6 places.
Context switching: a single developer must switch between SQL, backend language, API design, and test writing — each requiring a different mental mode.
Time cost: 3–4 days of developer time before a single screen can be shown to a stakeholder.
Repetition: most of this work is identical boilerplate — every entity needs the same pattern of SQL + ORM + CRUD APIs. Nothing creative, just repetitive.

The Procify Way​

✅ How Procifyreplaces the traditional schema-building process • In Klobase, all 6 traditional steps are replaced by a single tool: the data studio.
You define the entity (name, type) → add properties (name, data type, key attributes) → click Update Schema. Done.
The platform automatically generates: the database table (SQL step 1), the data access layer (ORM step 2), the REST API endpoints (step 3), basic validation from key attributes (step 4), and handles schema updates automatically (step 5).
There are no separate files to keep in sync. The data studio is the single source of truth. Everything downstream — API, data validation, mobile sync — is derived from it automatically.
Time with Klobase: the same 4 entities, all properties, schema live in the database — approximately 2 hours in this session.
The developer's time is freed for the parts that actually require thinking: business logic, UI design, user experience.

This is not an approximation. Let us make it concrete:

The Traditional Way of Building a UI​

🔴 Traditional screen development requires five separate layers • 1. HTML / JSX template — the visual structure: list container, card component, placeholder slots for each field.
2. CSS / styling — card appearance, status badge colours, spacing, responsiveness for mobile and desktop.
3. API call — GET /complaints?user={currentUser.id} to fetch complaint records from the server.
4. State management (React state, Redux, etc.) — store the fetched array, handle loading state, handle error state, trigger re-renders when data changes.
5. Data binding — map each complaint object's fields to the template slots: {complaint.complaint_desc}, {complaint.priority}.
Total: 3–5 files, 150–300 lines of code, for one list screen. Any change to one layer often requires changes to the others.

The Procify Way — The Page Wizard & Page Builder​

✅ The Page Builder replaces all five layers with a single metadata configuration • In the Page Builder you configure the screen structure. The platform reads your configuration and generates the visual rendering, handles all data fetching, manages state automatically, applies your styling choices, and wires up the data bindings.
This means: one tool, no files to keep in sync, no merge conflicts on screen structure, no state management code.
The Page Wizard (used in this session) gives you a ready-made screen in minutes. Session 2 teaches you to build the same screen step-by-step so you understand every level of the hierarchy.
Pages configured in the Page Builder render identically on both browser (web) and mobile (KloTouch) — no separate mobile codebase needed.
