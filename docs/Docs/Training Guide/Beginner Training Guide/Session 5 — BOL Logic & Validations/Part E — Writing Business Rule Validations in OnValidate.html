Part E — Writing Business Rule Validations in OnValidate

E.1 — Validation Rules for the Customer Complaints App​

Based on the BRD from Session 1, the following validations must be enforced when a complaint is saved:

Rule IDField(s)ConditionMessage
V001complaint_descEmpty or length < 10 charsComplaint description must be at least 10 characters.
V002priorityEmpty (null or blank)Priority is required. Please select Low / Medium / High / Critical.
V003planned_resolution_dateSet AND is before today's dateThe planned resolution date cannot be in the past.
V004planned_resolution_dateSet AND is before created_onThe planned resolution date cannot be before the complaint creation date.
V005s_statusAttempt to set CLOSED but role is EmployeeEmployees cannot close a complaint. Only the manager can close.

E.2 — Implementing OnValidate​

public async OnValidate(): Promise<any> {
// V001 — complaint_desc minimum length
if (!this.complaint_desc || this.complaint_desc.trim().length < 10) {
this.errors.push(new ValidationError(
this, 'complaint_desc', 'V001',
'Complaint description must be at least 10 characters.',
ErrorType.ERROR
));
}
// V002 — priority is required
if (!this.priority) {
this.errors.push(new ValidationError(
this, 'priority', 'V002',
'Priority is required.',
ErrorType.ERROR
));
}
// V003 — planned_resolution_date not in the past
if (this.planned_resolution_date) {
const today = new Date();
today.setHours(0, 0, 0, 0);
if (new Date(this.planned_resolution_date) < today) {
this.errors.push(new ValidationError(
this, 'planned_resolution_date', 'V003',
'Planned resolution date cannot be in the past.',
ErrorType.ERROR
));
}
}
// V004 — planned_resolution_date not before created_on
if (this.planned_resolution_date && this.s_created_on) {
if (new Date(this.planned_resolution_date) < new Date(this.s_created_on)) {
this.errors.push(new ValidationError(
this, 'planned_resolution_date', 'V004',
'Planned resolution date cannot be before the complaint creation date.',
ErrorType.ERROR
));
}
}
}
📘 Role Rollup Values (Training Guide Beginner — Session 1 Part A)
s_role_rollup is the numeric role hierarchy value assigned to application roles.
Owner (Employee role) → s_role_rollup = 10
Supervisor (Manager role) → s_role_rollup = 20
Reviewer (ResponsibleTeam role) → s_role_rollup = 30
Lower number = higher priority. Manager (20) overrides Employee (10).
You can also use this.txn.hasPermission('permission_id') for custom permission checks. See Permissions User Guide.

Part E — Query Rules

E.1 — What are Query Rules?

` around a create/update/delete. They are the correct place to answer two very different questions:

  1. Before the database is asked anything — “what should this user even be allowed to see?” (row-level filtering, defaulting search criteria).

  2. After the database has answered — “does the raw result need reshaping before it reaches the client?” (adding computed fields, merging data from a second query, masking sensitive values, sorting/aggregating in ways the query modeller can’t express.

Both callbacks receive an EventContext (commonly named oEvent) and give access to the query instance itself via oEvent.getObject().

E.1 — How to Create Query Rules?

Creating query rules is the same as creating entity rules, except the event type you subscribe to is one of:

Event types:

  • Before Query (beforeQ) — executes before the query is fired against the database. Anything set on the query object here becomes part of the WHERE condition.
  • After Query (afterQ) — executes after results come back from the database, before they are returned to the client. The raw result set can be read and replaced here.

Query Rule Event Reference (BOL API)

  • Event.getObject() — returns the KloQueryForRule instance being executed. Set properties on it to add filter conditions (beforeQ), or call getResults() / setResults() on it to read/replace the raw result rows (afterQ).

  • Event.getTxn() — returns the KloTransaction for the current user; use it to read $SYSTEM.roleID, call this.txn.get$User(), or check permissions.

  • Event.getEventType() — returns which event fired, e.g. BEFORE_QUERY or AFTER_QUERY. Useful if one method is wired to handle both events.

queryInstance.getResults() / setResults() — read or replace the raw JSON array of result rows in an afterQ callback. These are plain objects, not KloEntity instances — they cannot be saved back.

E.3 — Implementing before Query on q_complaints​

As we already know from the BRD document complaints page behaviour will be different based on role.

  1. In case of employee only complaints raised by him should be visible

  2. In case of manager all the complaints should be visible

  3. In case of it_team only assigned tickets should be visible

Create query folder and q_complaints.ts

public async beforeQ(oEvent: EventContext) {

let obj : any = oEvent.getObject();

let role = oEvent.getTxn().$SYSTEM.roleID;

if(role === 'EMPLOYEE'){

obj.customer_id = (await this.txn.get$User()).login_id;

obj.s_created_by = (await this.txn.get$User()).login_id; // Added for Business AI

}else if( role == "IT_TEAM"){

obj.assigned_to = (await this.txn.get$User()).login_id;

}

if(obj.description) {

obj.description = `%${obj.description}%`;

}

}

Part E.1 — Implementing after Query on q_complaints​

Scenario​

The Manager’s complaint list needs a column showing how many days a complaint has been open — days_open — without storing it on the entity (it changes every day, so persisting it would immediately go stale). This is a textbook afterQ use case: compute it once, on the way out, from data already in the result set.

Implementing afterQ​

public async afterQ(oEvent: EventContext) { let queryInstance = oEvent.getObject(); let results = await queryInstance.getResults(); let today = new Date(); let newResults = results.map((row: any) => { if (row.s_created_on) { let created = new Date(row.s_created_on); let diffMs = today.getTime() - created.getTime(); row.days_open = Math.floor(diffMs / (1000 * 60 * 60 * 24)); } else { row.days_open = 0; } return row; }); queryInstance.setResults(newResults); }

Wiring days_open into the UI​

Add days_open as a transient property (Session 5, Part D) on d_complaints so the Page Builder can bind a column to it, then add that column to s_complaints (Session 2, Part B.9.2). Because the value arrives already computed on the result row, no additional binding logic is needed on the client.
