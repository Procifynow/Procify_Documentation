Part D.1 — Team Groups: Bulk User Assignment​

What Is a Team Group?​

Assigning one test user at a time (as done in Part D) works fine for training, but it does not scale. Real projects onboard users in batches — a new hire cohort, an entire department, or a partner organisation that all needs the same app access on day one. Team Groups (labelled User collections inside the Workspace Hub screen) solve exactly this: they let you bundle a set of users once and assign the whole bundle to an application in a single step, instead of repeating the Part D steps per user.

Team Groups are of two kinds:

  • Individual Team Group — created automatically for every user the moment their account is created. Hidden by default (use the Show Individual checkbox to reveal them). Its only job is to let a newly created app be auto-assigned back to the user who created it.
  • Group Team Group — created manually by an admin, and the one you will use for real onboarding work. It holds any number of users and can be linked to one or more App Collections (App Groups) so that every user in the group inherits access to every app in the collection

Why Team Groups Matter in Practice

  • Without Team Groups, assigning 25 new employees to 3 apps means 75 manual assignment actions (Part D, repeated).
  • With a Team Group, it becomes: 1 group with 25 members, linked once to an App Collection with 3 apps.
  • Team Groups are filtered by the logged-in user’s Auth Codes and scoped to the current landscape — you will only see groups you are authorised to manage.

Part E — understanding the importance of Procify​

Every application starts the same way: someone hands a developer a requirements document and says 'build this.' The Customer complaints Application Business Requirement Document (BRD) you read in Session 1 defines exactly what data needs to be stored — 3 data objects, their fields, and their relationships. The first job as a developer is to turn those definitions into a working database schema.

Before opening any tool, it is worth understanding what that process looks like — and how much of it Procify eliminates. The rest of this part walks through the traditional process step by step, then shows exactly which steps the data studio replaces.

What Is a Schema?​

📘 Schema — The Blueprint of Your Application's Data A schema is the complete definition of the data your application stores: what tables exist, what columns each table has, what type of data each column holds, and how tables relate to each other. The schema is the foundation of every application. Without it, there is no database. Without a database, there is no data. Without data, there is no application. Building the schema is always the first development task after reading a BRD. Everything else — APIs, Pages, logic — is built on top of it. In our BRD, the schema is already defined in Section 4 (Entity Relationship Overview). The 4 entities, their properties, and their relationships are all there. Our job today is to implement that schema.

The Traditional Way of Building a Schema​

🏗 How developers build a schema without a low-code platform Step 1 — Write SQL scripts: A backend developer writes CREATE TABLE statements for each entity. For the Delivery table alone, that is 12 columns — each with its SQL data type, constraints, default values, and indexes. Step 2 — Write an ORM model: For every SQL table, the developer writes a model class in the backend language (Node.js/TypeScript, Python, Java). This class mirrors the database table and handles object-relational mapping. Step 3 — Write REST API endpoints: For each entity, the developer writes GET, POST, PUT, DELETE API handlers. Each handler validates input, maps it to the model, executes the database query, and returns the response. Step 4 — Write validation logic: For each property that has rules (mandatory, unique, min/max), the developer writes validation code — either in the model or in the API handler. Step 5 — Handle database migrations: Every time the schema changes (new property, renamed column), the developer writes a migration script to alter the existing tables without losing data. Step 6 — Test the API: The developer uses Postman or writes unit tests to verify each endpoint returns the correct data in the correct format. Repeat for all 4 entities.
🔴 The pain of the traditional approach Multiple files across multiple layers — SQL files, model files, API controller files, test files. A change to one field requires edits in 4–6 places. Context switching: a single developer must switch between SQL, backend language, API design, and test writing — each requiring a different mental mode. Time cost: 3–4 days of developer time before a single screen can be shown to a stakeholder. Repetition: most of this work is identical boilerplate — every entity needs the same pattern of SQL + ORM + CRUD APIs. Nothing creative, just repetitive.

​

The Procify Way​

✅ How Procifyreplaces the traditional schema-building process In Klobase, all 6 traditional steps are replaced by a single tool: the data studio. You define the entity (name, type) → add properties (name, data type, key attributes) → click Update Schema. Done. The platform automatically generates: the database table (SQL step 1), the data access layer (ORM step 2), the REST API endpoints (step 3), basic validation from key attributes (step 4), and handles schema updates automatically (step 5). There are no separate files to keep in sync. The data studio is the single source of truth. Everything downstream — API, data validation, mobile sync — is derived from it automatically. Time with Klobase: the same 4 entities, all properties, schema live in the database — approximately 2 hours in this session. The developer's time is freed for the parts that actually require thinking: business logic, UI design, user experience.

The Traditional Way of Building a UI​

🔴 Traditional screen development requires five separate layers 1. HTML / JSX template — the visual structure: list container, card component, placeholder slots for each field. 2. CSS / styling — card appearance, status badge colours, spacing, responsiveness for mobile and desktop. 3. API call — GET /complaints?user={currentUser.id} to fetch complaint records from the server. 4. State management (React state, Redux, etc.) — store the fetched array, handle loading state, handle error state, trigger re-renders when data changes. 5. Data binding — map each complaint object's fields to the template slots: {complaint.complaint_desc}, {complaint.priority}. Total: 3–5 files, 150–300 lines of code, for one list screen. Any change to one layer often requires changes to the others.

The Procify Way — The Page Wizard & Page Builder​

✅ The Page Builder replaces all five layers with a single metadata configuration In the Page Builder you configure the screen structure. The platform reads your configuration and generates the visual rendering, handles all data fetching, manages state automatically, applies your styling choices, and wires up the data bindings. This means: one tool, no files to keep in sync, no merge conflicts on screen structure, no state management code. The Page Wizard (used in this session) gives you a ready-made screen in minutes. Session 2 teaches you to build the same screen step-by-step so you understand every level of the hierarchy. Pages configured in the Page Builder render identically on both browser (web) and mobile (KloTouch) — no separate mobile codebase needed.

B.3 — The Page Hierarchy (UI Editor 7.0 User Guide — Sections 3.0–7.0)​

Every screen in Klobase follows a strict 5-level hierarchy. This is the most important structural concept in UI development. Each level has a mandatory naming convention prefix:

📘 Five-Level Page Hierarchy Level 1 — PAGE (prefix: p_) The root container. Holds all layouts. Created first. One page can have multiple layouts (one per device type). At runtime, the platform picks the layout based on device: screencontainerdesktop, screencontainermobile, screencontainertab, screencontainerdefault. Level 2 — PAGE LAYOUT (prefix: pl_) Sits directly under the Page. Defines HOW the page areas are arranged. screenType options: stack, tab, two_column, object_page, grid_layout, hsplitter, vsplitter. Example: pl_complaints_desk (two column layout for desktop). Level 3 — PAGE AREA (prefix: pa_) A logical sub-container inside the layout. Can itself have a screenType (tab, stack, splitter). Sections are assigned to page areas to determine WHERE they render. Example: pa_complaints (list area), pa_complaint_details (detail area). Level 4 — SECTION (prefix: s_) The rendering unit. screenType determines HOW it displays data. Types: search, cardlist, card, form, grid, tree, timeline, map, calendar. Must be assigned to a Page Area to appear in the UI. Example: s_search (search), s_complaints (grid), s_detail_header (form). Level 5 — CONTROLS Individual fields, buttons, labels, icons bound to entity properties. Added via: right-click section → New → Controls, OR drag from unused TransNode properties.
Section screenTypeRenders As
searchFilter bar with Close / Reset / Search buttons. Auto-generates the search toolbar.
cardlistList of records as card rows — one card per record. Good for mobile and compact lists.
gridTabular list with column headers and rows. Supports sort, filter, group-by per column.
formDetail form layout. Each control renders as a labelled input field.
cardSingle entity rendered as a CSS grid card. One record only.
tabUsed on Page Areas to group child sections as tabs. showTitle must be true for tab labels.
treeHierarchical tree display for nested data.

B.4 — Page Data Model (TransNodes) — Concept​

The Page Data Model defines the data available to a screen. Every section and control that displays data must be bound to a TransNode. A TransNode is a “data pipe” — it fetches entity records from the database and makes them available to sections and controls on the page.

Node TypeFetches
EntitySetA LIST of records. Use for search sections, grids, card lists. Suffix convention: _list. Example: d_complaints_list
EntityONE record (the currently selected record). Use for detail forms. Suffix convention: _detail. Example: d_complaints_detail
QueryRecords from a kloQuery with WHERE conditions, joins, sorting. Suffix convention: _query.
OtherNon-standard / custom use cases.
📘 Fold From — The Critical Link Between List and Detail When you create d_complaints_detail (Entity type) and set its “Fold From” = d_complaints_list, the platform automatically loads the selected record’s data into d_complaints_detail whenever the user clicks a row in the list. This is the mechanism that connects list → detail. Without Fold From: the detail section will always be empty. With Fold From: clicking any complaint row in the list instantly populates the detail form. TransNode naming convention (from UI Editor 7.0 Guide): EntitySet → _list suffix Entity → _detail suffix Query → _query suffix

Part A — Creating Relations Between Entities​

A.1 — What Is an Entity Relation?​

An Entity Relation tells the Klobase server how two entities are connected to each other. Without a relation defined in the BOL Editor, the platform has no way to automatically load child records when a parent record is selected — and no way to bundle the BO for save/delete operations.

There are two types of relations in Klobase:

Relation TypeWhat It Means
Primary RelationTight parent-child bond WITHIN the same Business Object (BO). A child entity is dependent on the parent. Prefixed pr_. Used for d_complaint_item, d_complaint_voices, d_complaints_attachment — all children of d_complaints.
Non-Primary (Aggregated) RelationLooser link BETWEEN BOs. Used to reference standalone master entities. Prefixed r_. Used for d_customers and d_resp_team which are independent master entities.
📘 Why Relations Matter in the UI
When a relation is defined and referenced in a TransNode in the Page Builder, the platform automatically fetches the child/linked entity records when the parent record is loaded.
Without a relation, you would have to write manual queries and wire up the data fetch yourself.
The TransNode type 'Relation' in the Page Data Model uses the relation name defined here — this is why naming the relation correctly matters.
Naming convention (from BOL Editor 7.0 User Guide — Best Practices): pr_ prefix for primary relations, r_ prefix for associated/aggregated relations. Always lowercase.

Part B — Configuring Object Types for d_complaints​

B.1 — What Is an Object Type?​

In Klobase, an Object Type (stored in the system property s_object_type) is a classification that tags each record as belonging to a specific type. Object Types serve two important purposes:

  • They enable role-based visibility: a button or field can be made visible/editable only for a specific role AND a specific object type combination. This is used for screen behavior in Session 7.
  • They allow ID Series to be object-type-specific: a different number series prefix can be applied per object type — for example, complaints created by Maventic employees might use a different prefix than those created by Procify employees.
📘 Object Type vs Object Group
Object Group is a container that groups related Object Types together. The group is used as the filter boundary. Object Type is the actual tag applied to individual records (e.g. MAVENTIC, PROCIFY). Every Object Type must belong to exactly one Object Group. For the Customer Complaints application: Object Group = company_types Object Types = MAVENTIC, PROCIFY Best Practice (BOL Editor 7.0 User Guide): Always maintain an Object Group to group types — the same group can be used in default filters based on users.

Part C — Setting Up ID Series for Auto-Numbering​

D.1 — What Is an ID Series?​

An ID Series is a platform-managed counter that automatically generates primary key values when a new record is created. Without an ID Series on complaint_id, a developer would need to generate unique IDs manually — which is error-prone and cannot produce readable, formatted numbers like CMP-00001.

ID Series TypeDescription
Auto NumberReturns an incrementing number. Combined with a Prefix pattern to produce CMP-00001, CMP-00002, etc.
GUIDReturns a 32-character UUID. Good for distributed offline scenarios. Not human-readable.
NoneNo auto-generation. The developer or rule must set the key manually.

Part C — Configuring Status and Status Groups​

C.1 — What Is Status in Klobase?​

The system property s_status represents the current state of a complaint record. The Status tab in the Data Studio lets you define the allowed values for s_status and group them into Status Groups.

Status Groups are named collections of statuses. They are used in Vienable (Session 7) to control screen behaviour: for example, the Edit button is visible only when s_status is in the OPEN_GROUP, and the Assign Team button is visible only when s_status is in the INPROCESS_GROUP.

Part A — Understanding Value Helps​

A.1 — What Is a Value Help?​

A Value Help (VH) is a platform-level component that provides a controlled list of choices for an entity property. When a VH is assigned to a property, the corresponding input field in the UI automatically renders as a dropdown (ComboBox), auto-complete field, or picker dialog (F4) — without any additional coding. The VH also validates that the entered value exists in the list when 'Is Restricted' is enabled.

📘 Three VH Types in Klobase (VH User Guide — Section 1.1)
VH Config: Values are maintained in the metadata (config) DB. App-managed, flavor-dependent. Can be overridden by child apps. Requires a build after creation/update. Use for fixed classification lists (priority, complaint_type, etc.).
VH Query: Values are fetched from a transactional or modelled query at runtime. Use for dynamic master data pickers (customer_id, responsible_team). The query determines what data appears in the picker.
VH Transaction (DEPRECATED): Older type. Internally still supported for legacy apps. New development should use VH Config or VH Query instead.

Part D — Understanding and Creating KloQueries​

D.1 — What Is a KloQuery?​

A KloQuery is the Klobase equivalent of a SQL SELECT statement. It lets you define — within the Data Studio — exactly what records to fetch, from which entity, with which filters, joins, and sort order. Unlike a Runtime Entity Query (which simply fetches all records of an entity), a Modelled Query gives you full control over the WHERE clause, JOIN entities, and sort order — and is reusable across multiple pages.

Query TypeWhen to Use
Runtime Query (Entity Query)Fetch all records of a single entity. No WHERE clause in the definition. Filters applied at runtime via the TransNode. Use for simple list screens.
Modelled Query (Dynamic Query)Define custom WHERE conditions, joins, sort order in the BOL Editor. Reusable, entity-independent. Use for role-filtered lists (My Complaints), VH Queries backed by joins, aggregated results.
Native Query (Advanced Query)Raw SQL. Database-specific. Use only for special cases not achievable with modelled queries. Avoid training.
📘 KloQuery Fields Reference (BOL Editor 7.0 User Guide — Section 3.0.2)
Return Entity: The entity whose properties appear in the result set.
Query Type: Runtime
Entities And Join: Add the root entity and any joined entities (LEFT JOIN, INNER JOIN, etc.).
Select Properties: Choose which properties from the entities appear in the result.
Parameters: Define input parameters the query accepts at runtime (e.g., user_id filter passed from the TransNode).
Where: Define filter conditions: entity.property = :parameter or entity.property = 'fixed_value'.
Sort Order: Set the default sorting column and direction (ASC / DESC).
Naming convention: Query IDs must start with q_. All lowercase.

Part E — Saved Queries​

E.1 — What Is a Saved Query?​

A Saved Query is a named combination of a base query and a specific set of pre-filled search parameters. Where a Modelled Query defines the structure, a Saved Query defines a pre-configured instance of that query — ready to execute with one click in the search bar. Saved Queries appear as quick-filter options in the search TransNode of the UI.

📘 Saved Query vs Modelled Query (Basic Training Guide — Section 2.1)
Modelled Query: The definition — entity, properties, parameters, WHERE logic. Reusable structure.
Saved Query: A named configuration of a modelled query with preset parameter values. Stored per entity.
In the UI, a Saved Query appears as a quick-filter button or dropdown in the search bar section.
Saved Queries are created from the Data Browser (Advanced Search), not directly in the query detail tab.
Naming convention for Saved Query IDs: Begin with sq_ by convention.

Part B — Entity Lifecycle Hooks​

B.1 — The Three Hook Methods​

Klobase provides three entity lifecycle hook methods that you override in the entity .ts file. These run on the server and are triggered automatically by the platform at the appropriate point in the entity's lifecycle.

MethodWhen CalledTrigger ConditionPrimary Use
onAfterCreate()After entity is created in DBOn every new entity saveSet defaults, auto-populate audit fields, initialise related records
OnValidate()During navigation / on save / validateP functionTransNode setActiveIf = 'Valid'Validate field values, enforce business rules, push errors
onDelete()After entity is deletedOn every delete operationCascade cleanup, logging, send notifications
📘 OnValidate — Important Details
OnValidate is triggered ONLY when the TransNode's 'setActiveIf' property is set to 'Valid' in the Page Builder.
If setActiveIf is not set, OnValidate does NOT fire — the platform skips validation on navigation.
Inside OnValidate, push errors using: this.errors.push(new ValidationError(this, propertyId, errorCode, message, ErrorType.ERROR));
The method must NOT return the errors array — it pushes to this.errors and the platform reads it. (PROC-24075 fixed this for proper return type.)
ErrorType.ERROR blocks save. ErrorType.WARNING allows save but shows a warning toast.
After your OnValidate runs, the platform ALSO runs its own mandatory-field validation based on key attributes — you don't need to repeat those.

Part D — Property Setters and Getters​

D.1 — What Are Setters and Getters?​

TypeScript property accessors let you intercept reads and writes of entity properties. In Klobase, setters and getters in the entity .ts file are the correct place for computed/derived field logic — not the controller.

PatternPurpose
Setter (set propertyId)Called every time the property value changes. Use to: compute a derived field when an input changes, enforce value formatting, trigger side-effects.
Getter (get propertyId)Called every time the property value is read. Use to: return a computed / formatted value instead of the raw stored value.
⚠ Critical Setter Pattern — Always Call this.s()
Inside a setter, you MUST call this.s('propertyId', new_value, 'dataType', false, false) to actually persist the new value into the entity's internal state.
Without this.s(), the new_value is accepted by TypeScript but never written to the entity data — the save will ignore your change.
Pattern: if(new_value == this.propertyId) return; // guard to avoid infinite loop
Then: this.s('propertyId', new_value, 'dataType', false, false);

D.2 — Setter: Auto-Compute actual_tat When closed_on Changes​

When a complaint is closed (closed_on is set), actual_tat should be computed as: (closed_on - created_on) in days.

public set closed_on(new_value: Date) { if (new_value == this.closed_on) return; this.s('closed_on', new_value, 'date', false, false); // Compute actual_tat when closed_on is set if (new_value && this.s_created_on) { const msPerDay = 1000 * 60 * 60 * 24; const diffMs = new Date(new_value).getTime() - new Date(this.s_created_on).getTime(); this.actual_tat = parseFloat((diffMs / msPerDay).toFixed(1)); } }

D.3 — Getter: Display complaint_id with Priority Badge​

A getter can return a formatted composite string. For example, a display_title getter that combines complaint_id and priority:

// t_ prefix = transient property (not stored in DB) // Define t_display_title as a Transient property in the BOL Editor first public get t_display_title(): string { return `${this.complaint_id} [${this.priority || 'UNSET'}]`; }
📘 Transient Properties (BOL Editor 7.0 User Guide — Entity Property Qualifier)
Transient properties (t_ prefix) are computed at runtime and NOT stored in the database.
They must still be defined as entity properties in the BOL Editor with qualifier = Transient.
Once defined, they can be added to sections and controls in the Page Builder like any other property.
The getter in the .ts file provides the value — the platform reads the getter whenever the control renders.
Use transient properties for: display labels, formatted dates, computed totals, role-based display logic.

Part E — Query Rules

E.1 — What are Query Rules?

`Query rules are similar to Entity rules but are triggered before and after a query execution rather than around a create/update/delete. They are the correct place to answer two very different questions:

  1. Before the database is asked anything — “what should this user even be allowed to see?” (row-level filtering, defaulting search criteria).
  2. After the database has answered — “does the raw result need reshaping before it reaches the client?” (adding computed fields, merging data from a second query, masking sensitive values, sorting/aggregating in ways the query modeller can’t express.

Both callbacks receive an EventContext (commonly named oEvent) and give access to the query instance itself via oEvent.getObject().

E.1 — How to Create Query Rules?

Creating query rules is the same as creating entity rules, except the event type you subscribe to is one of:

Event types:

  • Before Query (beforeQ) — executes before the query is fired against the database. Anything set on the query object here becomes part of the WHERE condition.
  • After Query (afterQ) — executes after results come back from the database, before they are returned to the client. The raw result set can be read and replaced here.

Query Rule Event Reference (BOL API)

  • Event.getObject() — returns the KloQueryForRule instance being executed. Set properties on it to add filter conditions (beforeQ), or call getResults() / setResults() on it to read/replace the raw result rows (afterQ).
  • Event.getTxn() — returns the KloTransaction for the current user; use it to read $SYSTEM.roleID, call this.txn.get$User(), or check permissions.
  • Event.getEventType() — returns which event fired, e.g. BEFORE_QUERY or AFTER_QUERY. Useful if one method is wired to handle both events.

queryInstance.getResults() / setResults() — read or replace the raw JSON array of result rows in an afterQ callback. These are plain objects, not KloEntity instances — they cannot be saved back.

Part A — Data Bindings In Depth​

Every control on a Klobase screen reads and writes data through the Transaction Model ($M). The model is a JSON model object. All bindings use the prefix $M to reference it. Without a binding, a control shows a static value or nothing at all — it is disconnected from the live data.

A.1 — The $M Model Path Structure​

The Transaction Model is organized as a tree. Each TransNode in the Page Data Model corresponds to a branch in the $M tree. The full path to any property follows this pattern:

{$M>/transNodeRelationId/propertyId}

For a list TransNode with relationId = list, the first row's complaint_desc is:

{\$M\>/list/0/complaint\_desc}

For the detail TransNode with relationId = detail:

{\$M\>/detail/complaint\_desc}

The leading / after > is mandatory. Omitting it causes a silent bind failure.

A.2 — The Four Binding Modes​

ModeWhen to UseSyntax / Where to SetExample
ValueStatic, hardcoded value — no model connection. Control always shows this literal text regardless of data.Properties tab → Value fieldtext = 'Complaint ID' — always shows that label.
PathBind to exactly ONE model property. Two-way binding by default: changes in UI write back to model.Properties tab → DSRC field{$M>/detail/complaint_desc} — shows and edits the complaint description.
PartsCombine MULTIPLE paths into one display value via a formatter function. Always one-way (read only).Properties tab → dsrc field (add each path as a part) + Formatter Function fieldParts: {$M>/detail/first_name} + {$M>/detail/last_name} → formatter returns full name string.
ExpressionInline calculated value. No formatter function needed. Supports ternary operators and comparisons. Always one-way.Properties tab → dsrc field (starts with {= ...}){= ${$M>/detail/is_escalated} === true ? 'Escalated' : 'Normal'}

⚠ Path and Parts are mutually exclusive on the same property — you cannot use both at once. If you need multiple values combined, always use Parts.

A.4 — Parts Binding with Formatter Function​

Use Parts when you need to combine or transform multiple model values into a single display string. Parts binding is one-way only — it cannot write back to the model.

Value:​

The value field will hold the value provided for the property.

Path:​

In this path field, users can only bind with exactly one property or value. This can be used if there is only one property to bind.

Parts:​

In this path field, users can bind multiple properties or values. This can be used if multiple values or properties need to be provided for binding.

(Note: If we are using formatter function, then it is mandatory to provide either parts or path value)

Formatter Functions​

Controller function name (formatter function) can be given for the field.

Type:​

In the type field, the user can provide the datatype for the control’s value.

Formatter Options:​

Formatter options define how a value is formatted and displayed in the UI.

Validation Constraint:​

Constraints are optional and define how an input value that is entered in the UI should look like. During parsing, the value is validated against these constraints. For example, an Integer type has a constraint for the maximum that is automatically validated when parsing the input values.

Example: displaying TAT status as a composite string from actual_tat and standard_tat.

// Controller function — formatTAT

public formatTAT(actual: number, standard: number): string {

if (!actual || !standard) return '—';

const diff = actual - standard;

if (diff <= 0) return `✅ On Time (${actual} days)`;

return `⚠ Overdue by ${diff} day(s) — Actual: ${actual}, SLA: ${standard}`;

}

⚠ The formatter function receives Part values in the exact order they appear in the Parts list. If you add actual_tat first and standard_tat second, the function signature must be formatTAT(actual, standard).

Part B — Expression Bindings​

Expression binding lets you write a JavaScript ternary expression directly inside a binding path string. It starts with {= and ends with }. It is evaluated live at runtime whenever the bound model values change.

B.1 — Syntax Rules​

RuleDetail
Starts with {=The expression must begin with {= (curly brace, equals). Without the =, it is treated as a plain path, not an expression.
Reference model paths with ${}Inside an expression, wrap every $M path in ${}: ${$M>/detail/s_status}. This dereferences the path to its current value.
Must return a valueThe expression must evaluate to a value matching the property type. visible expects boolean. text expects string. enabled expects boolean.
Ternary only for simple casesUse condition ? valueIfTrue : valueIfFalse. Complex multi-branch logic belongs in a formatter function, not in expression binding.
No function callsYou cannot call controller functions from expression binding. Use Parts + formatter for that.

Part C — Formatter Functions​

A formatter function is a TypeScript method in the controller file that takes one or more raw model values as input and returns a formatted display value. It is the right tool whenever expression binding would become too long, needs multi-step logic, or needs to look up external data.

C.1 — Where Formatter Functions Live​

Formatter functions are public methods on the controller class. They must be public — the framework calls them reflectively from the Page Builder binding.

export class p_complaints extends KloController {

  // Formatter functions — called from Parts binding in Page Builder

  public formatPriority(priority: string): string {

    const map: Record<string,string> = {

      'LOW': '🟢 Low', 'MEDIUM': '🟡 Medium',

      'HIGH': '🔴 High', 'VERY_HIGH': '🚨 Very High'

    };

    return map[priority] || priority || '—';

  }

}

Part B — Controller Page Lifecycle Hooks

The Klobase framework calls lifecycle hook methods on your controller class at specific points in the page's life. Understanding WHEN each fires is essential — using the wrong hook causes bugs that are hard to trace because they appear intermittently depending on navigation order.

B.1 — Hook Execution Order​

On first page load: onPageInit → onPageModelReady → onPageEnter

On forward navigation back to same page: onPageEnter (only)

On backward navigation away from page: onPageExit (source page), onPageEnter (target page)

On back-navigation that destroys the page: onPageExit → onPageDestroy

Part F — Transport: DEV to QA

F.1 — How Transport Works​

Transport is a PULL mechanism: the TARGET system (QA) asks the SOURCE system (DEV) for the latest published version. You perform ALL transport steps while logged into the QA environment, not DEV.

StageWhat Happens
SetupTransport creates entries in QA metadata tables for the application, groups, and flavors.
DownloadApplication ZIPs are pulled from DEV and extracted in the QA server's file system.
Update SchemaDatabase tables for all entities are created or altered in the QA database.
FinalisingApplication is set to ACTIVE in QA so users can log in and access it.
⚠ Important Transport Pre-requisites — verify ALL before starting 1. The application must be in RELEASED status on the DEV system. 2. Branch flavors CANNOT be transported. Create a new version, merge, then transport. 3. The QA server's config.json must have mm_klo_online_server pointing to the DEV landscape URL. 4. A host file entry for the DEV system must exist on the QA server. 5. The transport_1 app must be assigned to the developer account on the QA system. If any pre-requisite is missing, the transport will fail at Setup or Download stage. Ask the trainer to verify the QA environment config before proceeding.

F.2 — Step-by-Step: Transporting to QA​

1Log in to the QA System Open the QA environment URL in a browser (trainer provides the URL). Log in with your developer credentials. ⚠ ALL remaining steps are done on QA, not on DEV.
2Navigate to App Transport Hamburger menu (☰) → Sys Admin → App Transport. The App Transport screen lists all available applications from the connected DEV system.
3Find Your Application In the list, locate customer_complaints_<prid>. If not visible, toggle the 'Show All' button to see all available apps (not just those with pending updates).
4Click the App Row Click on customer_complaints_<prid>. A detail panel opens showing available versions from DEV and any already-installed versions in QA.
5Install As Writable Click the available version update. A dialog appears with two options: As Readable — locked, cannot edit in QA. As Writable — editable, allows continued development in QA. Click 'As Writable' (recommended for training so you can fix issues in QA if needed).
6Accept Conditions and Proceed A mandatory conditions dialog appears. For each mandatory item (⚠ icon), tick the acceptance checkbox. If prompted about shared flavor movement (on QA/PROD systems), click Proceed. Click Proceed to start the transport.
7Monitor Transport Stages The screen shows progress through: Setup → Download → Update Schema → Finalising. Wait for each stage to complete. The overall status changes to ACTIVE when done.
8Assign Users in QA After transport, the app is ACTIVE in QA but has NO users assigned. Go to Account Console → My Apps → customer_complaints_<prid>. Go to Roles & Users tab → assign: emp_<prid> → Employee role mgr_<prid> → Manager role it_<prid> → ResponsibleTeam role Your developer account → Manager role
9Verify in QA Log out of the QA developer session. Log in as emp_<prid> in QA. Verify: hamburger menu shows 'Complaints', p_complaints loads, all VH dropdowns work. Repeat with mgr_<prid> and it_<prid>.
📘 Reference / Tip Transport User Guide: Transport-_User_Guide.docx The Transport tool supports DEV → QA, QA → PROD, and DEV → DEV movement. Script Master (second tab in Transport screen) shows automated scripts maintained for the system — ask trainer if any scripts need to be run after transport.
