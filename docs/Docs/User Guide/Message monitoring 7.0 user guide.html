1.0. Message Monitor​

Middleware (Message Monitoring) is an application that is used for fetching all the information about the entries that are present in the device Info or tenant Info. We can also reprocess the failed messages present inside the error_q of the tenant.

Device Info:

When we are sending any data/action from server to device we store the message in the device info to know its information and state. In device info, every message is an outgoing message. So, the successfully sent messages are shown here. So, It goes from In queue to success.

Tenant Info:

When we are sending/fetching any data/action from server to SAP LOCAL or sending data from device to server. We store the message in tenant info to know its information and state.

All the messages from Device to Server and SAP Local to server are visible in Inbound MessagesServer Queue Monitor screen. All the messages from Server to SAP Local will be visible to the Outbound queue screen and all the messages from server to device or SAP Local to device will be visible in Device OutboundDevice Queue Monitor screen.

Purpose of Message Monitoring​

Message Monitoring is used to show information about messages (UPGRADE, DEBOARD) and the state of the message whether it's in the in-queue, Success, or failed. Every message has a state out of the three states mentioned below :

In-Queue: The message is ready for processing.

Success: The message has been processed successfully.

Failed: Message processing has failed.

We can also reprocess the Failed message. The reprocess function is only available for tenant_q.

When we are sending/fetching any data/Action from server to device or server to SAP local, we store it in terms of messages to know its information and its state.

Navigate to Message Monitoring​

Step 1: Go to the Operations MonitorSystem Monitor option

Go to the menu options and select Operations MonitorSys Monitor.

Step 2: Click on the required option

Click on either Inbound MessagesServer Queue Monitor (Tenant Info**)** or Device OutboundDevice Queue Monitor (Device Info**)** according to your requirements.

What type of data will be stored in message monitoring tables:​

It will store the messages for all the transactional data changes.

NOTE: Metadata changes will not be reflected in the message monitoring screens.

In device info, every message is sent or is in the process of being successfully sent. So, every message is outgoing and never fails. Hence, It goes from in-queue to success.

1.5.Upsert​

An Upsert operation refers to the combination of update and insert actions, where data is either updated if it exists or inserted if it doesn't.

When syncing messages, an Upsert scenario behavior typically involves checking if a message already exists in the destination system or database. If it exists, the system will update it; if it doesn't, the system will insert it as a new record.

1.5.1.Upsert Behavior in Middleware for Syncing Messages:​

  • Data Creation and Update:

    • If the data is new (does not exist in the system), a new entry will be created.

    • If the data already exists, the existing record will be updated instead of creating a new one.

  • Upsert for Root Business Objects (BOs) and Primary Relations:

    • Upsert is only applicable for Root Business Objects (BOs) and their primary relations.

    • For non-primary relations, the Upsert operation will work only if the relation is established using primary keys.

  • Parent-Child Relationship:

    • If a parent is new, but the child data related to the parent already exists, this is considered an unexpected scenario. The user must handle this manually, as it is not automatically managed by the middleware.

1.5.2.Delete Scenario Behavior:​

  1. Parent Entity Deletion:

    • If the parent entity is deleted, the child entities will only be deleted if the user explicitly sends the isdeleted flag as true in the request body for both the parent and child entities.

    • This applies to both primary and aggregate relationships.

  2. Child Entity Deletion:

    • If the child entity is deleted, only the child will be deleted. The parent entity will remain intact.

3.0. Troubleshooting failed messages​

Messages that are failed to process can be found in the error q. The error can be found in the error message. Possible reasons a message can fail are.

  1. Application logic - When an application logically rejects a request for processing the message. I.e. Adding items to a closed order. Adding shipments to a closed Delivery etc.
    Suggested solution : Find the root cause why these messages are generated. Eg. screen still allows adding items even if the status of order is closed. And fix the issue / add validation in the client side also.

  2. Application bugs - Some cases where application code has a bug, due to which an exception can be raised the message will fail. Eg. Improper null handling, wrong API parameters, typo etc.

  3. Transaction User not configured - File processing, transaction user has to be configured with required application & permissions. As all the messages are processed based on the access of the user, messages generated by files need a user to validate against. Refer to the Landscape Editor for how to configure the transaction user.

  4. Configured user doesn’t have application assigned : When messages from SAP / File processing are failing with “Access denied: user lacks permission to the required application.” error, it means, the user (SAP communication user / File processing user) does not have that flavor assigned to them.

  5. Database Deadlock / Lock Timeout Errors:
    - When the middleware encounters a transient database deadlock or lock wait timeout (e.g., "Deadlock found when trying to get lock; try restarting transaction"), messages are automatically retried up to 3 times with a 1-second delay (default values) between attempts.
    - If all retries are exhausted, the message will move to the error queue.
    - It will have an error message like - "Message <msg_id> failed after 3 retry attempts due to Lock wait timeout exceeded" or "Message <msg_id> failed after 3 retry attempts due to Deadlock found".
    - The retry settings are configurable via config.json:
    "MiddlewareRetrySettings": {
    "DeadlockRetryCount": 3,
    "RetryDelaySeconds": 1
    }

2. Device Message Flow​

2.1. Multiple Logins Can Create Active Endpoints​

When an application team logs in from multiple or random devices without properly deboarding the previous devices, those devices can continue to be considered active endpoints.

As a result, messages may continue to be generated for these endpoints even though the application team is no longer actively using them.

Platform Reference: Account Console 7.0 - User Guide — "Whenever any new user registers in the application, a new endpoint ID is created against that account... when they log in again the status becomes Active." Each login is a distinct endpoint; none are deregistered automatically on crash or app closure.

2.2 Messages Can Accumulate in the Queue​

Because these endpoints remain active, messages generated for them may not be synchronized with the device immediately. Over time, a large number of messages can accumulate in the queue.

This can give the impression that a large number of messages are stuck.

Platform Reference: Message Monitoring 7.0 - User Guide — In-Queue is defined as "all the data that are currently present in the device_q and which are not processed yet." A high In-Queue count reflects endpoints awaiting sync, not failed or lost messages.

​

2.3. Messages Are Synchronized When the Device Becomes online​

When the corresponding device comes online , the queued messages are synchronized with the device.

Once the server successfully sends the messages and receives the required acknowledgment from the client, the messages move to Success.

If the device is offline, the messages remain in the queue until the device becomes available.

Platform Reference: Message Monitoring 7.0 - User Guide — device_q entries move to device_log_q (Success) or device_error_q (Failed) only after processing; until then they remain In-Queue, consistent with holding messages for an offline device until it reconnects.

2.4 Device-Side Processing vs. Server Status​

A message can reach the device successfully, but the actual processing on the device may still fail.

From the server's perspective, the message can be marked as Success when the client acknowledges that the message was received while the device was online. Therefore, Success on the server does not necessarily mean that the message was successfully processed by the application on the device.

Platform Reference: Message Monitoring 7.0 - User Guide — "In device info, every message is sent or is in the process of being successfully sent. So, every message is outgoing and never fails. Hence, It goes from in-queue to success." This confirms Success tracks the send/acknowledgment, not on-device application processing.

2.5 Application Team Awareness​

The application team may not be aware that previously used devices are still registered as active endpoints. This can result in messages continuing to be generated and queued for those endpoints.

Note: This is a training/visibility gap rather than a platform defect. Recommend making Sections 1–4 of this topic available to application teams so "stuck message" reports can be self-diagnosed before being escalated as incidents.

2.6 Automatic Endpoint Cleanup Scheduler​

A scheduler runs every Sunday to clean up old endpoints.

Note: The scheduler currently deboards endpoints that have been inactive for more than 7 days.

Once an endpoint is deboarded, its corresponding entry is removed from the endpoint table.

PropertyValue
Class namedeboardInactiveUsers
CRON expression0 0 0 ? * SUN * (every Sunday at midnight)
Current inactivity threshold (this environment)7 days
Platform default threshold15 days — this environment has been configured below the default
Channel typeBOTH, unless restricted to DEVICE or BROWSER
Table cleaned upEndpoint's entries removed from madm_ep_apps

Platform Reference: Account Console 7.0 - User Guide — "Deboard Inactive Users": CRON Job Expression 0 0 0 ? * SUN *, class deboardInactiveUsers, parameters No_of_inactive_days {default: 15} and Channel_type {default: BOTH}; "this scheduler will deboard all the users who are inactive since given days and it will delete the entry of all deboarded endpoints from madm_ep_apps."

2.7 Scheduler Customization​

If the default 7-day cleanup period does not meet the application's requirements, the scheduler can be customized to use a different endpoint deboarding period.

To change it:

  1. Go to the job-instances page in Cockpit and locate the deboardInactiveUsers job.

  2. Open the job instance's parameters.

  3. Update No_of_inactive_days to the desired threshold.

  4. Update Channel_type if the cleanup should be restricted to a specific channel.

  5. Save. The new threshold takes effect on the job's next scheduled run (the following Sunday, per the fixed CRON expression).

Note: The CRON schedule itself (currently fixed to Sunday) is a separate setting from the inactivity threshold — changing how often the job runs, as opposed to how many inactive days it waits, would need to be confirmed as in-scope for this customization request.
