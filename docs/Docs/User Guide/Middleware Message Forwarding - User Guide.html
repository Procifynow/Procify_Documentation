Overview

The Middleware Message Forwarding feature allows you to automatically sync data changes between different flavors of your application. When data is changed in one flavor (source), it can automatically trigger message generation for users of another flavor (target), ensuring all users stay synchronized regardless of which flavor they're using.

Pre-requisites​

Application Architecture Requirements​

Multi-Flavor Setup​

✅ You must have multiple flavors (source and target flavors)

✅ Both source and target flavors must be deployed and accessible

✅ Flavors should share common entities that require message sync

Entity Design​

✅ Target Entity: Must exist with identical entity name and table name

✅ Target Entity: Must have ENDPOINT_RESOLVER event configured with proper implementation

Access and Permissions​

Administrative Access​

✅ Access to Operations Monitor application for configuration

✅ Permissions to create/modify Middleware Message Routing entries

✅ Message monitoring access for troubleshooting and monitoring

Development Environment​

✅ Private node setup with DEV landscape (for testing)

✅ Access to both source and target flavor codebases

✅ Debugging capabilities in development environment

Technical Prerequisites​

Message Processing Infrastructure​

✅ Message processing must be functional

Monitoring Tools​

✅ Message Monitoring screen access for tracking forwarded messages

✅ Queue Monitor for viewing message queues and error queues

✅ Log access for troubleshooting and debugging

Knowledge Requirements​

Development Team​

✅ Understanding of entity event implementation (ENDPOINT_RESOLVER)

✅ Familiarity with addEndpoint() method usage

✅ Knowledge of message queue and processing

✅ Experience with multi-flavor application development

Configuration Team​

✅ Understanding of flavor versioning and deployment

✅ Knowledge of landscape management (DEV/TEST/PROD)

✅ Familiarity with Operations Monitor configuration tools

How to enable the feature​

Setting Up Flavor Mapping​

To enable message forwarding, you need to configure mappings in the Mw Message Routing Screen in Operations Monitor:

Configuration Screen - Mw Message Routing

Access this screen through Operations Monitor > Middleware Message Routing

Required Fields​

Source Flavor: The flavor where changes originate

Target Flavor: The flavor that where the changes should be also be forwarded for message generation.

Is Active: Set to true to enable forwarding

Target Version: Only for DEV Specify a particular version of the target flavor. Use this for debugging purposes. In QA & Production, the latest version is used.

Configuration Steps​
  1. Open Operations Monitor application
  2. Navigate to "Middleware Message Routing"
  3. Click "Add New" to create a mapping
  4. Fill in Source Flavor and Target Flavor names
  5. Set "Is Active" to true
  6. Save the configuration

How to use the feature​

Common Use Cases​

Multi-Flavor Applications​

If your application has multiple flavors (e.g., online and offline versions) that share common entities, this feature ensures data consistency across all flavors.

Example Scenarios:​

Portal + Mobile App: Changes made in the web portal should sync to mobile app users

Hierarchical Applications: Parent flavor changes should sync to child flavor users

How Does It Work ?​

Data Change Trigger: When you create, update, or delete data in a source flavor

Automatic Detection: The system detects if forwarding is configured for that flavor in Middleware Message Routing ( Operations Monitor )

Trigger Endpoint Resolver: The ENDPOINT_RESOLVER event will be triggered in target flavor if the same entity exists.

Message Generation: Messages are generated for target flavor users based on the target flavor ENDPOINT_RESOLVER logic.

Synchronized Delivery: All related messages share the same reference ID for tracking

Entity Requirements​

Target Entity Setup​
Your target entity must have:​
  • Same entity name as source entity
  • Same table name (tb field) as source entity
  • ENDPOINT_RESOLVER event configured
  • Event implementation in the entity class file
Example Entity Event Implementation​
// In your entity class file (e.g., src/flavor/entity/your_entity.ts) async onEndpointResolver(txn, dataObj, headers) { // Your logic to determine which users/endpoints should receive messages this.addEndpoint(userList, EndpointType.User, ChannelType.Both); }

Testing in Private Node​

1. Setup Test Environment​
  • Set up your private node with DEV landscape
  • Checkout the source flavor and required target flavors.
  • If target flavor is not present in the private node, forwarding will be skipped.
  • Create test flavor mappings with specific target versions
2. Create Test Data​
  • Perform create, update, delete operations on the source entity
3. Debugging​
  • You can debug the target flavor entity event implementation by setting breakpoints in your private node.
4. Monitor Message Flow​
Messages generated during forwarding will have:​
  • Same ref_msg_id for all related messages
  • src_fv field showing source flavor version
  • dst_fv field showing target flavor version

Message Monitoring Tools​

Checking Message Forwarding Status​

Use the Message Monitoring screen to track forwarded messages and verify successful processing:

The forwarding status icon in the message monitoring screen indicates when messages have been forwarded

Understanding Forwarding Status​
  • Icon Appearance: Look for the forwarding indicator next to messages
  • Status Information: Click the icon to see detailed forwarding information

Detailed view showing forwarding status and target flavor information

Tracking Related Messages by Reference ID​

All messages from the same transaction share a reference ID for easy tracking:

Reference ID icon allows you to view all related messages from the same transaction

Using Reference ID Tracking​

  1. Locate the Reference ID icon in the message list
  2. Click to expand and view all related messages
  3. Verify both source and target flavor messages are present

Expanded view showing all messages sharing the same reference ID

Troubleshooting Failed Forwards​

When message forwarding fails, check the Error Queue for detailed information:

Error queue entry showing failed forwarding message with MSG_FORWARD type

Error Queue Analysis​
  • Message Type: Look for "MSG_FORWARD" type entries
  • Error Details: Review error messages for troubleshooting
  • Retry Options: Use message reprocessing to retry failed forwards

Behavioral Changes to Expect​

Message Generation​
  • Additional Messages: You'll see target flavor messages in device/tenant queues
  • Message Grouping: Related messages share the same reference ID
  • Cross-Flavor Sync: Changes in source flavor should trigger messages in target flavor
Error Handling​
  • Isolated Failures: If target flavor processing fails, source transaction still completes
  • Error Queue Entries: Failed forwards create entries in error queue with type MSG_FORWARD
  • Retry Capability: Failed messages forwarding can be reprocessed later. It will only retry the forwarding, not the original transaction. The dirty state and from state is preserved from the original transaction.

Understanding Message Reference IDs​

What is a Reference ID?​

The reference ID (ref_msg_id) is a unique identifier that groups all messages generated from a single transaction.

How It Works​
Original Message → ref_msg_id: "ABC123" ├── Source Flavor Message → ref_msg_id: "ABC123" ├── Target Flavor 1 Message → ref_msg_id: "ABC123" └── Target Flavor 2 Message → ref_msg_id: "ABC123"

Detecting Forwarded Messages​

In your entity event handlers, you can detect if the event was triggered by message forwarding:

async onEndpointResolver() { let headers = await this.getHeaders(); let sourceApp = headers.src_app; let currentFlavor = this.txn.$SYSTEM.flavor; if (sourceApp !== currentFlavor) { // This event was triggered by message forwarding this.info(`Message forwarded from ${sourceApp} to ${currentFlavor}`); } else { // This is a normal event execution } }

Best Practices​

Configuration Management​
  • Minimal Mappings: Only configure necessary flavor mappings
  • Environment-Specific: Use similar configurations for DEV/TEST/PROD
  • Regular Review: Periodically audit your forwarding configurations
Testing Strategy​
  • Verify End-to-End: Test complete data flow from source to target users
  • Monitor Queues: Watch queue growth during testing
  • Check Error Logs: Review error queues for any issues

Troubleshooting Common Issues​

Messages Not Forwarding​

Checklist:

  • ✅ Mapping exists in Msg Forward Mapping
  • ✅ r_is_active is set to true
  • ✅ Target entity exists with same name and table
  • ✅ Target flavor entities have ENDPOINT_RESOLVER events
  • ✅ If private node is used, make sure target flavor is assigned.
Using Message Monitoring Tools:​
  1. Check the forwarding status icon in Message Monitoring
  2. Look for error entries in Error Queue with MSG_FORWARD type
  3. Verify Reference ID grouping shows both source and target messages
  4. Review detailed forwarding information in status dialogs

Monitoring and Maintenance​

Regular Checks​
  • Queue Monitoring: Review device and tenant queue sizes
  • Error Analysis: Check error queues for failed forwards
Maintenance Tasks​
  • Error Queue Cleanup: Process and resolve failed messages
  • Configuration Updates: Modify mappings as application evolves
  • Documentation Updates: Keep mapping documentation current

Getting Help​

Support Information​
When contacting support, provide:​
  • Source and target flavor names/versions
  • Entity name and table name
  • Reference ID of problematic messages
  • Relevant error log entries
  • Current mapping configuration
