kloQuery

Overview​

kloQuery is a metamodel for fetching data from the data store, like SQL in RDBMS. kloQuery gives the ability to fetch the data seamlessly for offline and online applications. It abstracts out multiple syntax of Odata, SQL, Json etc. so that programmers can concentrate on the business logic. It gives a few short-hand optimizations like pagination, column selection and security features like authorization etc.

kloQuery is made with Query, QueryProperty, PropertyType, Select, orderby etc. It returns kloEntityset which is an array of kloEntities. E.g. consider the following SQL:

SELECT ord_id, qty AS ord_qty, ord_date FROM d_order WHERE d_order.status = ‘open’ Orderby ord_date “ASC”:

Let q = await oController.getQueryP(“d_order”);

q.setProperty(“d_order.status”, ‘open’);

q.setOrderBy([{fieldname:”d_order.ord_date” , sort_type:”ASC”}]);

Let result: kloEntitySet = await q.ExecuteP();

The above SQL needs to be represented by kloQuery. WHERE clause of SQL d_order.status is the input search criteria modelled as query property and its property type, will describe the type(string) caption and value help. Similarly, kloQuery also has OrderBy and Select, together with other constructs to hold the SQL constraints. Query objects are directly bindable in UI for user input and capable of providing label and value help. kloQuery can be represented in pre-modelled query by name and at runtime enhancing with constraints.

Types of kloQuery:

kloQuery supports multiple types of query modelling which are easy to define and use in the application. Based on the application scenario and use case, the query type has to be decided.

  • Runtime Query (single and multiple entities)

  • Meta Query (former Dynamic Query)

  • Native Query (former Advanced Query)

Queries are also used in Saved Query, User Saved Query, Initial Sync Query, and Advanced Query.

Note: Runtime Query does not need modelling. It inherits behaviour from the entity and BO definition and operates with API. Later, we will consider more control on query by modelling the kloQuery.

Query API​

For Query APIs refer to BOL Query APIs- 5.7

Operators in Query​

Adding operators to query properties while setting through API (on Query instance ) or with bindings.

Supported operators are:

Where Operators: AND, OR, NOT.

Query Operators: EQUAL, NOT EQUAL, GREATER, LESSER, GREATER_EQUAL, LESSER_EQL, LIKE, IS NULL, IS NOT NULL, IN, NOT IN.

Query without Modelling​

Runtime Query

Runtime Query does not need modelling. It inherits behaviour from the entity and BO definition and operates with API.

Get the Query instance by specifying the entity name as the returned entity. The result of executeP contains the qualified entities from the specified return entity. Using API to fill up the values you need in addition to API below information may help to use runtime query effectively.

Setting Where clause

Syntax: <query instance>[<EntityName>@<EntityProperty>_<operator>] = value

Example:

Q[‘item_number’ + QUERY_OPRATOR.GT] = 20

q[‘item_number_LT’] = 50

This will filter the results having item numbers between 20 and 50.

Runtime Query on multiple Entity within BO​

This is part of a Runtime query with a special case where you want to fetch the data from one entity extending the where clause to other entities within the BO boundary. Use the return entity name as the Query name. Based on the setProperties parameters, it decides either to query on a single entity or multiple entities. All parameters in setProperty should have a table name also if the property belongs to other than the return entity. If the table name is not mentioned, it will consider the return entity name.

All entities should be part of one BO. If all entities are not part of the same BO, it will throw an error at runtime.

getQueryP(entityName: "d_order")

@parameter: entityName: entity name(case sensitive)

@Returns: Query Instance (KloQuery)

It is not necessary to use the root entity only as a query ID. Any entity(within BO) can be used and joins could be on parent or child entities.

Example:

  • d_order

    • d_order_item

      • d_order_conditions

One can use d_order_item as the return entity and user d_order entity’s property in the setProperty function. Here, JOIN will be added for d_order in the constructed query.

Features supported:

  • Fetch data from multiple tables in a single BO.

  • Joins are decided as the entity properties used in setProperty.

All parameters are optional. If the participating/join table parameter is not passed, JOIN will not be applied.

Features not supported:

  • Filter expression

  • Group By

  • Distinct

  • SUM/COUNT/AVG

  • OR

  • SELECT( function, alias)

Authorization on Query​

Authorizations allow you to control the extent to which a user can create or change a query based on the data passed. Authorization can be defined on Property Type only. Authorization can’t be defined on object type or some other parameter. In case if you want to add/remove/change authorization on the base property type, extend the property type in a separate flavor.

Authorization is applied on the whole BO irrespective of return Entity. If authorization is defined on any child/root entity it will be applied on all the entities which are part of that BO.

When used as a string literal in a meta-model in authorization it is replaced with real value. E.g. $USER.login_id will be replaced with the currently logged-in user id. Similarly, authorization can be applied on other $VARIABLES also. For more details refer to the $VARIABLE section.

$Variable is available in Rule and Endpoint resolver but not available while processing middleware messages.

Syntax: $<Variable name>.<property id>}

Rule Execution: Authorization is applied when the query runs inside the BO Rule on the server side. In the case of client-side Rule execution authorization is not applied as client DB should have only filtered data. If any client(endpoint) is not authorised to see the data it should not get synced to the client. This means authorization is applied at the time of initial sync and data(message) push to the client.

Inherit Authorization: Authorization of parent object added automatically to the child. This means if authorization is applied based on the customer_id property type on the order Entity, the same will be applied on the child entities(up to n level) also.

Authorization is applied in Read and Create operations. As it is applied to the Read operation, the Delete operation is covered under this. Users can’t delete the data which is not allowed to be read.

Authorization is not applied while querying data in middleware message processing as the system does not know the User.

Authorization is not applied to scheduled jobs as the user configured in the job is common.

Data Archiving​

Data archiving is the process of moving data that is no longer actively used to a separate storage device for long-term retention. Archive data consists of older data that remains important to the organisation or must be retained for future reference or regulatory compliance reasons.

  • Enable Archiving: Separate tables will get created if archiving is enabled on a particular entity/BO. The table name starts with ‘v’ instead of ‘d’.

  • Archive Data: The frequency of data archiving is decided based on the business requirement. The developer has to write a background report to push the data from the main transaction table to the archive table.

  • Fetch Archived Data: take input from the user to show the archived data.

Acquiring the Entity by Entity Unique ID: Entity Unique ID is a concatenated value of the Entity name and primary key set in an alphabetic sorted Order.

<entity_name>##<pk1>##<pk2>.........

Modelling of a query​

Till now you have gone through the Runtime query where modelling is not required.

Let’s model a Query using the Data Studio. To create a query go to the entity which will be returned as a result. Provide a unique Query name. Query names should start with q as best practice. It must not start with “d, c, a or m”. Query name and entity name must not be the same hence name used as entity id or query id can not be used for others. Select Query Type as “D” or “Modelled Query”

  • Define Query property

  • Define Query Relation

  • Test Query

Query definition is broadly categorised into two sections one as “SQL Section” relevant input as definition to prepare SQL statement and the other defines the behavioural expectations. The section to define SQL needs to know participating database tables join rules, where clause, return columns, groupby etc. second section concentrates on business aspects like before query rule, after query rule, network mode, property mapping, part return, authorization, etc.

SQL Section​

Select:

SQL function (tablename.fieldname) AS alias

Can be blank, the default value is taken as returnEntityName if the table/entity name is not specified with any field.*

If the column name in the return result set does not match the return entity property name value will not be populated hence use Alias to rename it as the return entity property name. In case of multiple tables, specify the select list with the table name and alias so results can be mapped with the return entity property name. Return entity or entity property can be transient or persistent. Supported DB function can also be applied on the field

[{Function:”,Entity:”d_ord”,Property:”r_qty”,Alias:”” },{Function:””,Entity:”d_ord”,Property:”gross”,Alias:”” }..].

Alias is to match the property name with the transient entity property.

PartEntityLoad: Read selective fields of the returned entity. By default, the full return entity is returned as a result set. Add one or multiple fields here for selective return. If the entity changes, the framework will load the full entity internally with a primary key set.

Primary key fields are added by default with selective fields.

Distinct: True / False/ IF child JOIN as value. If true, distinct all (select clause parameters) is considered for the return row. The default value is false.

FROM: Can be blank, default value is taken as returnEntityName. In the case of a transient entity or even in the case of a persistent entity specifically in the case of aggregate calculation we may need to specify a different entity than the return entity.

Use Native query if you want to use multiple table names in the FROM section like in the case of parent-child relation in the same table.

JOIN: Provide a unique Query Relation ID and define the relation using Entity relation with Join type. Entity relation has the full details of both side fields to define the Join.

  • JOIN Type

  • Entity Alias Name

  • Entity Property Name

Supported Join Types:

  • Inner Join

  • Full Outer Join

  • Left Join

  • Right Join

The default value for the Join Type is “Inner Join”.

Join will be avoided if the parameter is not passed or not part of the select or Authorization or travelling path for other table fields.

Where: supported filter expression.

Add the Query property with the Entity you want to put a where condition. Following parameters as input:

  • Query Property ID

  • Entity Name

  • Entity Property ID

  • Operator: excluding formula all other operators are supported.

GroupBy / Having: Having support filter expression

OrderBy:

[{fieldname: string, sort_type?: string}]

setOrderBy([{fieldname: string, sort_type?: string}]): IKloQuery

@parameter : fieldname - return entity field(property name)

@parameter: sort_type - possible values are ‘ASC’ or ‘DESC’

Supported Operator

AND, OR, EQUAL, NOT EQUAL, GREATER, LESSER, GREATER_EQUAL, LESSER_EQL, LIKE, NOT, IS NULL, IS NOT NULL, IN, NOT IN

Supported Functions:

COUNT, SUM, MIN, MAX, AVG.

Syntax:

Supported Variables:

  • Query property name

    • Syntax- :<query_property_name>

  • Constant:

    • Syntax - “”. Provide constant value in double quotes.

  • $ variable if not a kloBroker message.

    • Syntax - ${$USER.owning_bp}

  • Parent/participating/Join Tables Property.

    • Syntax- :<tableName.fieldName>

Example:

SELECT * from d_order where customer_id = :cust_id and order_type = :”prime” order by order_date desc;

SELECT * from d_order

Inner join d_order_item on (d_order.order_id = d_order_item.order_id)

where customer_id = :cust_id and order_type = :”prime” order by order_date desc;

Filter Expression

A filter expression is a binary tree of the operator, table.fields, function, variable, entity property and const. Trees can be evaluated only as one way to construct the filter expression. Tree nodes can have an operator with left and/or right values. Value can be another node itself.

Soql Query: Holds the SQL-like string for a better understanding of what will go to DB.

Not Supported​

  • Nested queries are not supported.

  • Formula not supported (like a*b)

  • Limit not supported

Behaviour Section​

Return Entity Name: The result set will be kloEntitySet containing the instances of the named return Entity. Return entities could be Persistent or Transient.

In case if Persistent entity does not fit in as a return data set, you can create a Transient entity which has all the required entity properties as per business requirements and use this entity as a return entity. Visit the Entity section for more details on the definition of a Transient entity. This is the use case you need:

  • Return the data from different entities.

  • Additional fields to store some calculated value at runtime.

Is_across_tenant: If the query needs to be extended across tenant data. Be careful with security. By default queries are tenant-specific. This will return the data of all the tenants within a landscape.

Network mode: Normally left null or “or “Default” so it is picked as per precedence. Specify only in specific flavor as per override rules.

Return entity mapping

Pagination behaviour: Pagination is applied only if a query is executed from the UI. In case if a query is executed from any rule(Entity or Query) it will load all qualified data.

Calculated Property:

Providing getter/setter function for the calculated field:

  • Mostly used for dynamic calculations.

  • Define a query property in metadata.

  • For each query, the framework provides a <queryname>.ts class which can be used to define the getter/setter function of any property.

  • Through KloIDE, the app developer has to write a getter/setter function for the query property.

  • These functions are accessible using entity objects. <queryobject>.<propertyID>() and this.<propertyID>().

Example:

Getter:

Syntax of property getter: get<space><property name with the first letter capitalised>

public Qty1 : number;

public get Qty():number{

return this.Qty1;

}

OR

public get Qty():number{

return 20;

}

Setter:

Syntax of property getter: set<space><property name with the first letter capitalised>

public set Qty(newVal:number){

this.Qty1 = newVal;

}

**Note: **‘this’ is an instance of the current query here.

Features supported:

  • Fetch data from multiple entities(tables) across BO.

  • Join with another entity(table) supported with relation.

  • All query properties are optional.

  • Most used SQL functions and operators are supported.

Native Query​

Native query is a raw SQL query which supports all operators and functions of SQL as part of the query statement(not part of metadata). This should be used only as a last option if nothing else fits. This type of query must not be used in a product or reusable module. The native query is highly flexible but non-migratable.

Let’s write an SQL Query using the Data Studio. To create a query go to the entity which will be returned as a result. Provide a unique Query name. Query names should start with q as best practice. It must not start with “d, c, a or m”. Query name and entity name must not be the same hence name used as entity id or query id can not be used for others. Select Query Type as “Z” or “Native Query”.

  • Write SQL statement

  • Define Query property

  • Test Query

Native query working in an online case may not work in offline network mode if the query is incompatible with webSQL. It is comparatively slow because to db it is submitted as a nested query. Use only if the requirement is not fulfilled with Runtime or Modelled queries.

Authorization will be applied the same as other query types.

Example:

SELECT * from d_order where customer_id = :cust_id and order_type = :”prime” order by order_date desc;

Here cust_id is the query property you have to define. All query property values are mandatory to pass at the time of execution.

Not supported:

  • Query Relation: use Join in SQL statement.

  • Archiving

  • Date dependent features

Query Actions​

Actions are the reusable functions defined inside the TypeScript class where application developers write the business logic.

Type of Actions:

  • Regular Actions

  • Private Actions

  • Rule subscription action

  • Override Actions

  • Member Variable

Regular Query: On creation of a query, Framework provides a <queryname>_gen.ts file which contains pre delivered setters and getters of all query properties. Framework also provides a class <queryname>.ts which inherits the generated class(<queryname>_gen) and developers can write their own functions here. These are reusable functions and accessible with QueryInstance in any Controller or Rules or Middleware and returns the desired result.

Naming conventions:

  • Generated Class: <queryname>_gen.ts

  • Query Class: <queryname>.ts

  • Regular Action: public <actionName>(parameters) : <return type>{ }

  • Follow the camel casing in Action names.

File Path: flavor version >> BO >> Class.ts

Syntax to call Actions defined in Query class : <queryInstance>.<actionName(parameters)>

  • On update of Query/Query Properties the generated file will get adjusted by Framework.

  • Can add the Import in <queryname>.ts class in metadata.

  • Can not add additional imports in <queryname>_gen.ts class.

  • Define any number of Regular Actions in a class.

  • Regular Actions are always public.

  • <QueryName>.ts class extends the generated class(<QueryName>_gen). The Extends statement is generated by the framework.

  • Setting any value using ‘this’(current instance of query class) will not reflect the query properties outside the Rule/Query Class. It is locally available in the query class instance. Modified values are only valid for the current execution cycle.

  • Can call Entity/BO Util class or other Query class actions inside Query action (current and shared flavor).

  • Regular Actions of Query class are available as a help on Query instances while writing code.

*KloQuery Class: *

This is a class which exposes the limited set of actions to application. Generated class extends the kloQuery class. All actions defined in KloQuery Class are inherited to the Query class and accessible with the query instance.

Rule Subscription Actions:

Rule subscription actions are defined in the QueryClass and it receives EventContext as a parameter. The defined actions can be subscribed only against that particular Query.

Syntax: public [async] <actionName>(event: EventContext)

  • Any additional filter applied or changed or removed in the Before query rule, will not change the query properties outside the Rule.

  • To access the data in After Query Rule use ‘getResult()’

    • getResult() returns a JSON array.

    • this.getResult()[0…]

    • var rs = this.getResult();

  • Can add/delete/update the result set in Rule action. After manipulation, it expects a valid JSON array. The updated result set is returned as a JSON array. var rs = this.getResult();

    • Add: rs.push({orderID:’123’, type: ‘100’, status: ‘DRAFT’},..)

    • Additional property: can add additional property in the result set in JSON format.

    • Delete: rs.splice(0,1,...)

    • Edit: rs[0].status = ‘OPEN’

  • Any modification in the result set will not trigger any Rule.

  • Can create a new state of a query in the After Query Rule and execute the new query instead of the current/original query. The final result of the query is what the JSON array holds as a result.

  • Commit: In case you want to save anything to DB, commit has to be called explicitly.

  • Define Rule action in Metadata.

  • Multiple ‘Rule Actions’ can be defined in one Query class.

  • Rule action should be public.

  • This may return Promise<Any>. The promise should be resolved with Success or Error. If resolved with Error, the error code returns to the caller and this error results in rollback and the whole transaction will get rolled back.

  • In case any exception is thrown, behaviour is the same as promise rejection. - change in Entity action also.

  • Inside an Action if Promise is not returned then it is assumed to be a synchronous action.

  • At a time only one rule is getting executed and other Rule actions are in a waiting state.

  • Promise has to be resolved ‘Success’ before executing the next Rule. If it is a synchronous action and does not return the Promise, immediately after finishing one rule execution it moves to the next action for execution.

  • Can not change Rule action signature. Otherwise, it will be considered as ‘Regular Action’.

  • Can not subscribe to other Entity Class’s Rule subscription Action.

  • Call Regular Action in Rule- Regular actions defined in Query class <queryname>.ts can be accessed in the Query Rules class.

    • Syntax: this.<actionName>(parameters)

Subscribe Query Rules​

Rule definition steps are the same as Entity. Rules can be subscribed to a query to write the business logic. Query Rules are mainly used where add/change query filter/sorting or change query resultset to show the manipulated data on UI. Rule subscription is part of kloIDE. To subscribe to the Rules you need to provide the details below:

  • Rule ID: Select the already defined Rule ID.

  • BO Event Subscription ID: This is an auto-generated ID.

  • Event Type: You can subscribe the Rule to a query which is executed before or after query execution.

    • Before Query (BEFORE_QUERY)

      • Filter, Sorting, etc

    • After Query(AFTER_QUERY): resultsets can be modified, add or remove records in AFTER_QUERY rule.

      • Manipulate data based on business logic.

  • Channel Type: channel type decides when to trigger the Rule.

    • All

    • Endpoint/Device to Klarion Server

    • Endpoint/Device to Klarion Server---ALWAYS ON CLIENT

    • Endpoint/Device to Klarion Server---ALWAYS ON SERVER

    • Endpoint/Device to Server/Client---NETWORK CONTEXT SWITCH

    • Klarion Server to Klarion Offline Server

    • Klarion Server to Klarion Server

    • Legacy to Klarion Server

  • Sequence No(Mandatory): Decides in what sequence Rule to be executed. In case multiple Rules are subscribed, a sequence of rule execution is followed. All positive numbers(1-n) excepted. It is recommended to maintain the sequence like 10, 20, 30 and so on. So that any new Rule can be maintained in between without disturbing the other sequence.

Rules can not be executed on Runtime Queries. For more details on Rule execution refer to the Rule section.

Rule Execution: Please note that before_query rules are called only once in case of Pagination, Selective select or expand all cases also. Subsequent internal calls do not call before_execute. After_query execution may not get the correct count of records or all records or all fields. Please ensure you have considered selective select cases, pagination cases and expand all cases. After_Query will be executed after every internal call, all the data manipulation will be accepted as is to form the return entity.

Query Type to be used in an application​

As you have gone through all query types explained above all features are supported in different types of queries. Based on the feature supported programmer can decide which type will fit in what scenario.

While the selection of the type of query, you give priority in below sequence(1 is the highest priority):

  1. Runtime Query

  2. Modelled Query

  3. Native Query

Below are a few frequent use cases and query type usage:

  • Advanced Search screen: use Modelled query.

  • F4: use Runtime query

  • Initial Sync: use Modelled query.

  • Report: use dynamic query normally as input parameters are dynamic in most of the reports.

  • List Screen:

  • Details screen: Normally, Runtime Query with Entity by ID to measure performance.

Example:

loadLogisticsOnline: function (oController, order_id, TXN) {

orderQI.d_order#order_id = order_id;

orderQI.setNetWorkMode('ONLINE');

TXN.add(orderQI);

orderQI.execute(function (orderES) {

orderES[0].s_action = 'DEL_RELEASE';

orderES[0].s_status = 'RELEASED';

resolve(orderES);

});

});

});

}

Saved Query​

Saved Query is a query container that holds the predefined properties’ value for a given query. It is identified by ID, hence, it is also used in the Initial Sync.

Saved query can use dollar variables and date literals as property values. Saved query can hold all the variable values which can be set at runtime by API.

Delta Query​

Delta Query is used to update the local db periodically from the server. It asks the server to provide the data modified from the last execution till now. Results are handed over to the executor. Delta queries are internally used by cached online and by value help.
