BOL

1.1. Entity​

Do’s​

  • Use C R U D flags to control the data updation to your entity.

  • Naming conventions to be followed.

    • Entity name should start with

      • d_ for Tenent dependent and tenant independent entities.

      • t_ for transient entities.

      • c_ for config entities.

  • Use Validate BO on every change in entity to avoid runtime errors.

  • Use the sort order functionality in your entity, this will eliminate sorting in each screen.

  • Entity id should have only small letters.

Don’ts​

  • Entity’s network Mode should be blank for all entities under the flavor (Flavor network mode will be used by default). Network mode can only be overridden on exceptional cases.

    • Example : In Offline App only one page is online.

1.2. Entity Property​

Do’s​

  • Naming conventions to be followed for property id’s.

    • Property id should start with

      • t_ for transient type properties.

      • c_ for calculated type properties.

  • Make sure that every property details are filled properly, this will boost the development.

    • Mandatory: On create/update of the records from any screen, klobase will validate mandatory fields.

    • Fuzzy: If the fields marked with fuzzy exist on the screen, klobase will auto add them for fuzzy search criteria Eg: description / short text / name of the customer.

    • Default Value : On create system will auto populate these fields with the default values Eg: Priority, -- If any logic to identify the default value then it should be added in <entity name > .TS file.

    • VH: Make sure the VH field is not blank wherever VH help can be determined.

    • Text ID: Add a text ID and maintain the text in the language editor, avoid direct text / label in these fields.

    • Entity Property should have only small letters.

Note :

In case a user wants to change the property type of any property, they have to re-add the same property in their screen metadata using Page Builder (wherever applicable) from their transnode for reflecting the changes.

Don'ts​

  • Don’t create properties for system fields like s_modified_on, s_created_by, s_created_on. Instead enable created fields flag to use inbuilt system properties.

  • Don’t create / use new element ids if the same property is created under any other entity

    • Example : Order id in order header and order item can share same element id

Use the “Extend from” option if the existing property type can be used with minor changes like label changes or mandatory change.

1.3. Id Series​

Do’s​

  • Naming conventions need to be followed for the id series id’s.

    • Id should starts with

      • id_
  • Id Series should have only small letters.

1.4. Entity Relations​

Do’s​

  • Naming conventions need to be followed for relation id’s.

    • Relation name should start with

      • pr_ for primary relation

      • r_ for associated relation

  • Primary Relations: Always bundle your Bo with all children entities so that handling the data update messages would be easier.

  • Non Primary Relations: Always specify all the secondary relations also to avoid fetching data directly with queries. You can use relation fetch instead.

  • Entity Relations should have only small letters.

1.5. Entity Object Group / Object Type​

Do’s​

  • Always maintain the object group to group the types and the same can be used in default filters based on users.

  • Object types should always be binded with role and role_roll_up (for vienable).

1.6. Query​

Do’s​

  • Network Mode / DB selection should be blank for all queries under the flavor. Flavor network mode will be used by default. It can be overridden only for exceptional cases.

    • Example: In offline apps only 1 screen is online.

  • Create a query only if entity query is not sufficient for the use case.

  • Use a modeled query as it is independent of DBMS.

  • Naming conventions need to be followed for query id’s.

  • The query should have only small letters.

    • Query id should starts with

      • q_

Don'ts​

  • Don’t use native query as it is dependent on the DBMS. Use it only for special use cases.

  • Don't use different id's for query properties. Use the id same as entity property for easy trace.

1.7. Rules​

Do’s​

  • Use rules for endpoint resolvers.

  • Always use Ts files as exit handler for better readability and maintenance.

  • Rules should have only small letters.

  • Naming conventions need to be followed for rules subscriptions.

    • Should starts with

      • d2k_ for Endpoint / Device to Klarion Server

      • clnt_ for Endpoint / Device to Klarion Server - Always on client

      • srvr_ for Endpoint / Device to server / Client - NETWORK CONTEXT SWITCH

      • ncs_ for Endpoint / Device to Server / client - network context switch

      • k2d_ for Klarion Server to Klarion Offline Server

      • k2k_ for Klarion Server to Klarion Server

      • e2k _ for Legacy to Klarion Server

Don'ts​

  • Avoid using rules for create / update scenarios, we can make use of <entity_name>.ts files to handle the same.

    • Use onCreate & onUpdate hook methods of the <entity_name>.ts

1.8. Value Help​

Do’s​

  • Naming conventions need to be followed for value help id’s.

    • Vh id should start with

      • vht_ for vh transactional

      • vhq_ for query

      • vhsq_ for saved query

      • vhc_ for config

  • Value Help should have only small letters.
