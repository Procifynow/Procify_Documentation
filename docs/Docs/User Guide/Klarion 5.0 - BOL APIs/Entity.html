Entity

Data object in KloBase Datastore is known as entity. An entity has one or more named properties, each of which can have one or more values. Each entity in KloBase Datastore has a key that uniquely identifies it.

In simple words we can say Entity is a database table. In dbms we store data in the form of a table containing information about entity type like order, address etc. In an order database, a table containing information about all the orders. For example, orders have properties like customer, Amount, products, etc they are attributes which combined make table.

One entity must be part of one and only one BO.

Types of Entity:

  • Persistent Entity: Entity which physically exists/stored in database as a table. Fields in Persistent Entity could be either Persistent or Transient.

    • Persistent Entity by default Tenant Dependent can be made Tenant Independent

    • Persistent Entity by default or User Dependent can be made User Independent

  • Transient Entity: It is an in memory entity that doesn’t exist in a database. All fields in Transient Entity are Transient only. It can be constructed out of query result or by code to hold the value at runtime. Messages can’t be communicated through Middleware using Transient entity.

  • Config

  • FW only Types

    • Metadata

    • Archive

    • History

Entity Naming convention and length.

  • Entity names should use only english lower case alphabets (a-z), digits (0-9) and underscore (_) and upto 31 chars max length.

  • First char must be d/t/c based on type. Transactional (‘d’) , Transient (‘t’), Config (‘c’)

  • Following are auto generated

    • Archive entity starts with ‘a’

    • Union or archive and transactional entity starts with ‘v’

    • Status config starts with ‘s’

    • Custom Status starts with ‘u’

    • History entity starts with ‘h’

    • Framework entity starts with ‘m’

Each entity has one or more properties. Each entity property has one property type. Each property type has a domain assigned.

  • Entity

    • Entity Property (1-n)

      • Property Type (1)

        • Domain (1)

Provide a unique entity name and mark if it is a Root entity. Root entity is considered as a BO. To define an entity you need at least one entity property, It could be either transient or regular(persisted in DB).

Entity attributes:

  • Entity Name : Unique ID across all flavors.

  • Is Root : This defines the Root entity of a BO. BO Name is the same as Entity Name if this is marked TRUE.

  • Entity Type: Persistent/Transient.

  • Network mode : This is optional here and inherited from flavor this entity belongs to. You can overwrite if required.

  • BO Name : Root entity name. Entities in the same BO should have a primary relation.

  • Is metadata : This decides whether it is a meta model entity or transactional. If marked TRUE, framework creates table in metadata DB. Otherwise in transactional DB.

  • Has appvariant : Starts following the flavor behaviour. If is_metadata FALSE, by default has_appvariant is FALSE and not allowed to change.

  • Has Tenant : Entity starts following the Tenant behaviour. if TRUE, s_tenant_id field will be added in DB table at the time of the update schema.

  • Is Config : if TRUE, this is considered as config entity.

  • Has Config : Framework will provide a config entity which can further customized with configuration fields. If object type is not applicable this is an object type independent config. Config is accessible in application by using *entityInstance.config *

  • Has created fields : To know what time facts are recorded to database and by whom. if TRUE, s_created_on and s_created_by fields will be added by FW at the time of update schema. These two fields are filled by a system of entity creation.

UI: s_created_on is server time in UTC format when record created and s_created_by is the logged in user.

Message processing: Created On gets updated with server time(UTC format) if blank otherwise accept from message and Created By will be taken from message.

Background Job/Upload: Created On gets updated with server time( UTC format) when record got created. Created By is the user by which Background job scheduled.

Archive Data: accept created on/By field’s values from transaction entity as is.

  • Has modified fields : This is to record the last changed time and user. if TRUE, Modified On and Modified By fields will be added by FW at the time of update schema. System updates these fields on every create/change of entity.

Change in a BO:

  • In case if any change on root/header level only, this updates only header table modified fields.

  • In case any change is made to the child entity, this updates the parent entity also upto root.

UI: same as created fields.

Message processing:

Background Job: same as created fields.

Archive Data: accept all values from transaction entity. If an object is modified during the archiving process, then modify fields get changed accordingly.

  • Check Dirty: re-evaluate all entities for dirty before calling on update. Default value: ?

  • Has Brand : Entity is brand dependent or independent. if TRUE, s_brand field will get added by FW at the time of update schema.

  • Has Object Type : Entity follows Object Type behaviour. if TRUE, s_object_type field of type int(11) gets added by FW at the time of update schema.

  • Has Status : if TRUE, s_status and s_status_custom fields will get added by kloBase at the time of update schema. See more details in the Status section.

  • Can create/read/update/Delete: if TRUE, insert/read/update/delete is allowed in the table otherwise not allowed. Applied only on Server side. Server side Exit and MW still allows even if false.

  • Can read all : if TRUE, read all values allowed from the table otherwise not allowed. Applied only Server side. Exit and MW still allows even if false. Runtime query will not work if it is FALSE.

  • Has History: This is to maintain the changing history of an BO. If TRUE, it creates a separate blob or transactional table to maintain the history of all changes. Every change on an entity gets captured in the history table and the main transactional table holds only the latest record. Table name starts with ‘h’.

Only on root entity or full BO?

Maintain change history only for specific status?

Object type based configuration?

Is this supported offline?

  • Has Archive: This is to facilitate the data archiving. This can be enabled only on the root entity/ BO. Always complete BO gets archived.

Table name starts with ‘a’. One more table created as a view which starts with ‘v’ to fetch transaction and archive table data as union.

If the ID series is exhausted?

  • Server Side: Push data from transaction table to Archive table. Which means data will get deleted from the main table once moved to the archive table.

    • Maintain configuration based on which data to be archived.

    • Background job scheduler to push data from transactional table to Archive table. While archiving no dirty objects are allowed.

    • APIs: archive(). This API will work only on server side.

    • clearArchive() : this deletes all records from the archive table.

    • Update to offline endpoints. This deletes the entity in local DB.

    • ON_ARCHIVE event.

    • Query: by default query fetch data from transactional table(d table) but if archiving is enabled, users can explicitly mark to fetch archived data. This is a union of both transactional and archived tables.

    • IsArchived flag is returned TRUE by framework if data is from the archive table. This flag can be used by application to highlight archived data or disable edit option.

    • Do not allow the archived records to be updated. Framework throws an error if any dirty object found for archived records.

    • Value help/ Association relation for archived masters. Example:

    • Update transaction entity: this should adjust the archive and view.

      • Add/Delete new property

      • New relation/ Delete relation

  • Client Side: delete data in client DB(local) and do not send any updates to the server.

    • API: deleteLocal()

  • kloQuery has deleteLocal();

Dependency: Does not allow you to archive until the related(supplied by application. Do not follow entity relation) object gets archived. Dependency is decided based on aggregate relations. Helper function to be written by Application to check if any dependent object exists.

  • Has Time Dependent : At any given point in time, an entity has a value for each of its attributes. If the values of any attribute for an entity may change over time and you are interested to know the value of an attribute at a particular point in time, it is meaningful for entities to have properties exactly when they exist and mark the entity as time dependent. In case if you are interested only in the current value of the attribute, do not mark as time dependent.

This is to maintain the periodic(time dependent) data with valid time. If any entity is marked as time dependent, framework creates below three fields in the table. In a BO any entity can be time dependent.

  • s_valid_from(Timestamp) - Validity start date and time. Part of the primary key. Default is the current date.

  • s_valid_to(Timestamp) - Validity end date and time. Default value is 31-12-9999.

  • s_active(boolean) - the latest record will be marked as TRUE.

At a time only one entry should be active and the validity period should not overlap for two records. By default Valid from is current date but can be changed.

Past date: Config to be maintained for past date is allowed or not. Message processing(from SAP, device or to device) follows the config for the past date. If allowed it accepts the date from message or UI otherwise it changes the FROM date to current.

If first entry, except the values provided from UI or Message and mark active flag TRUE.

In case of update, modify the current existing active record’s s_valid_to accordingly(based on s_valid_from the new record). Also mark current entry active flag FALSE and new entry as TRUE. Both update and create should be in the same transaction.

Mainly this will be used for master data tables where periodic data is required. For example, pricing, user address, etc. MRP/Pricing of a product can be changed periodically.

Can not be changed based on object type or flavor. This can be defined only in owning flavor of an account.

  • Approval : In case if approval is required for a BO, at the time of creation of the BO it should not change the current record. Once it is approved, then only it gets activated. To consider this scenario, a separate blob table is maintained for ‘To Be Approved’ objects. Once final approval is done it will get moved to the main transaction table and activate. If enabled, approval flag will be provided from the framework.

    • This is applicable for time dependent and time independent both entities.

    • Configurable on object type based.

Workflow will be discussed separately later.

  • Has Attachment : If enabled, Framework allows to store the attachment against this entity object and attachment link entity becomes part of the BO.

Entity Property​

Entity Property describes the attribute/member variable in an Entity(field in the database table) and holds the value in runtime. It has a Property ID(name) and Property type. The Property Type defines the data type and behaviour of the property.

Entity Property’s attributes define the behaviour of the property. Entity properties can be added or archived only in the owning flavor of an account. Below are the parameters:

  • Entity Property ID: unique within an entity across all flavors. Can’t be changed later.

  • Property Type/Element ID: select the existing Property type or create new. This defines data type, field length, precision, etc. It can be changed only in the owning flavor of an Entity. Selection of a domain, size and property type:

    • Choose existing

    • Extend from

    • Copy and override: copy any existing property type and change the parameters. This makes a copy of all attributes except Property Type ID.

    • Create New

  • Type: Regular / Primary Key / Transient Field / Calculated Field /System Fields. / Secondory Key

  • Value Help: select already defined Value help ID. Wherever this property ID is binded in UI, VH is automatically applied. Can be overwritten in the screen field.

  • Is restricted Value: Restrict the input value within the associated VH. Tri value: None, Strict(UI and BOL), Suggestions(Only UI side). (Note: Moved this to Entity property from Property type).

  • Is Mandatory: Empty or Null values are not permitted during entity creation/update. Does not force in UI as mandatory. Non Key mandatory fields are not necessary for select.

  • Default Value: Default value will be populated immediately after creating new Entity. $ Variables can also be used.

  • ID Series: mention the ID series here if applicable for this field.

Naming convention:

  • Max length allowed for property ID is 31 char.

  • Only english lower case alphabets (a-z), digits (0-9) and underscore (_) are supported.

Entity property ID starting with ‘s_’ is reserved for systems fields by framework.

Types of Entity Property:

  • Persisted : Property which physically exists/stored in the database as a table column. Persisted Property owning Entity also has to be Persistent Entity only.

  • Transient: transient property is a runtime attribute only. Use this to hold some value at runtime. Example: query result alias value, value filled or determined in rule, from UI set and get attribute.

  • Primary key: primary key of a table. Values of set of primary key fields must be unique. If field is primary key, isNull/Nulable property will be marked as false automatically.

  • System Defined Properties: based on the relevant flags in entity definition, framework provides standard columns in a table. Field name, Data Type, Label, etc are already defined and no changes allowed here. Developers can’t add a system field.

Property Type​

Property Type is to define the behaviour of Entity Property(Database Table field) and Screen field. It is a reusable unit. Property Type has below attributes:

  • ID : Unique ID of Property Type within Landscape.

  • Domain: select Domain ID from predefined list to define the data type.

  • Length and precision of the field. Precision is applicable only for decimal data type. Specify length for decimal and ‘chr’ types.

  • Value Help: Define value help and assign it to property type. Value help will be applied to all the places wherever this Property type is used in UI or Rules. You can define restrictions(allow values only from VH list or accept manual inputs) on Entity Property.

  • Authorization

  • Text ID: maintain the Text ID here which points to the actual text(Translatable). This text is available in the screen field as tooltip/caption/placeholder/validation(error) text wherever this property type is used. It helps in maintaining the unified text across all screens. Create Text ID in editor.

  • Default UI Format:

    • Date ( Example: DDMMYYYY or DDMMMYY, ...)

    • Numeric(currency, etc)

    • Decimal

  • Min Max Value: define min and max values allowed for a numeric and string(chr) fields. This ends with an error if value is not in given range. This validation is applied in UI. In case of string min/max value is the number of chars.

  • Extends From: extend from other property types and modify one or more attribute/s.

Usage:

  • Entity property

  • Query Property

  • Screen

Extends: extend the existing property type to access the parent attributes and overwrite if needed. You can only extend one propertytype in your child propertytype. In the extended property type fill only the attributes which you want to overwrite, all other attribute values are inherited from the parent. Domain type, length, precision can not be changed in extended property type.

Extend property type if:

  • Data type, length, precision are same as these are not allowed to change in extended property type.

  • One or more properties are different from the list below:

    • Authorization

    • Value help

    • Text ID

    • UI Formatting

    • Min/Max value

How to remove an attribute value in extended property type? Set null or empty string

For example, you have created one property type called ‘customer’ and Text is provided ‘Customer Name’. But in some scenarios you want to show the text as ‘Sold To Party’, in this case extend the ‘customer’ property type and create new property type as ‘sold_to_party’ and change the text.

A extends B. B extends C. All attributes of C are extended to A if not overwritten in B.

Reuse: To define the common behaviour of multiple Entity/Query Properties, Property type can be reused across entities.

It should be reused if entity properties are logically the same.

  • Ordered Qty and Del Qty - not to use the same property type. But Ordered qty in two diff tables should share the property type.

  • Property type should be different for Vendor and Customer fields in the same or diff entity. Both should be extended from BP ID because data type should be same for all.

  • It is recommended to use the same property type for a field which is used in multiple tables as foreign key. To understand this better let’s take an example of the Material Code field which is part of Material master as a primary field but also part of other tables like Order and Logistics items.

Authorization:

Authorization is to restrict the access of data, for logged in user. Authorization on any entity of a BO is applied on the whole BO. Authorization is defined on Property Type and applied for all queries the Entities wherever that Property Type is used.

Do not apply Authorization on Query Property.

For example, logged in users should be able to see only the Orders that belong to them. Below is the Entity definition:

In case you do not want to apply the authorization at all entities or apply the authorization at only one place, then extend the base property type and create a new Property Type.

Variables Supported:

  • $Variable

  • Constants

    • Syntax: const1, const2

In case if authorization is applied on more than one property or multiple value in one property. Below is the behaviour:

  1. AND Operator: If authorization is applied on multiple properties in the same BO with different property types, all parameters will be ANDed.

    1. Example1: There are two properties in d_order entity customer and sales_person both have different property types. If authorization is applied on both, this will be ANDed.

  2. OR Operator: Used a property type with multiple entity properties in the same entity, all parameters will be ORed. (Reuse property type within entity). At the same time it will be ANDed with other parameters.

    1. Example2: There are two properties in d_order entity customer and vendor both have the same property type, in this case both parameters will be ORed.

  3. IN Operator: If Multi values qualified for one property, all values will be considered with IN operator.

    1. Example3: Authorization is set on state field in d_order entity and multiple values passed at runtime, in this case all values will be passed with IN operator.

kloRelation​

Entity relation is to allow one entity to relate with another entity qualified by entity property. Relation has a unique name within the Entity.

  • Association: An association is a structural relationship which connects one entity with another. Given an association between two entities, can navigate from one entity to the other entity and vice versa. Association relations can be across BOs. By default each relation is of type Association if it is not marked as Aggregated or Primary.

Example1:

  • d_order_item(source)

  • d_material_master(Related)

Create a relation to show the material description, LOB, or other property of material.

Example2:

  • d_order_item(source)

  • d_order(Related)

If you want to navigate from order Item to order header. Define a relation between Item as Source and Header as Related entity.

  • Aggregated Relation: Aggregation is a type of association where two entities(tables) are tightly bound. In some cases we might come across “whole-part” relationships between two Entities, in which one entity is a part of another entity. Such a relationship is known as an aggregation. An aggregation relationship can be described in simple words as "an object of one class can own or access the objects of another class." If a parent is deleted/archive, all other parts associated with it are deleted. Aggregate relations can be across BOs.

  • Primary Relation: This is a special kind of aggregate relation within BO boundary. All entities in a BO are navigable from root entity once unidirectional and only once. Below are the use cases of primary relation:

    • Message processing

    • Key mapping

    • Find Parent

Example:

  • d_order ( root entity)

    • d_order_item

      • d_order_conditions

Here d_order is the root entity and the other two are child entities in Order BO. Hence relation has to be defined between these entities.

Create a relation on d_order entity with d_order_item of type “Primary” and query property is “order_id”.

Create a relation on d_order_item entity with d_order_conditions of type “Primary” and query property are “order_id” and “order_item”.

Define Relationship:

Let’s create a relation between two entities using Procify Data Studio. To create a relation go to the source entity where you want a relation with another entity. Provide a unique Relation name. JOIN is constructed based on the defined relation.

  • Relation Name: unique within an Entity. Relation names and Property names can’t be the same. “Parent” and “Attachments” are reserved keywords.

  • Related Entity: name of Entity with relation to be defined.

  • Type of relation: Aggregate/Primary. If not selected any, by default it is association type.

  • Query Type: - To be removed from Editor UI

  • Relation Query : Select relation query ID from list.

  • Cardinality: - (0:n, 0:1, 1:1, 1:n). User has to select the correct cardinality for the relation. No defaulting in Editor. Add 0:1 cardinality. In case if 0:1 include in Join and if 0:n provide separate query in VH. No validation on 1:1 and 1:n cardinalities from BOL side.

  • Description: describe the relation here in short.

Relation Property:

  • Relation Property ID: unique within Entity.

  • Source Property ID: Variables supported- Entity property ID and constants(number, single/double quote) comma separated. Source Property ID can be used multiple times.

  • Related Property ID: it is entity property ID if query type is Runtime and query property ID if query type is Modeled. Entity Name +Property ID in case of Runtime query. Can’t repeat within one relation.

  • Related Entity property ID: new readonly column. Fetch from the selected query.

Relation can be defined between two entities:

  • Both Persistent

  • Both Transient

  • One Persistent and one Transient

Variables supported:

  • Source Property ID

    • Entity property ID

    • Constant: multi value

    • $VARIABLE

  • Target Property ID

    • Entity/Query property ID

Call fetch on relation for business logic in UI and Rules. Syntax: <relation_name>.fetch().

Rules​

A Rule is a function that is to be executed after another function has finished executing. Rules are written by Developer as per the application business logic. Rules can be subscribed with either Entity or Query.

Define the Rule:

  • Define a rule with below inputs

    • Rule ID - unique ID across all entities.

    • Class - file name

    • Mime Type: Java or JS

    • Description

  • Recommended to Define the rules on the root entity of BO.

  • Each Rule returns a promise. Promise should be resolved or rejected based on the application scenario.

Example: resolve the promise if updated successfully and reject in case of any error.

var handleEvent = function (event) {

return new Promise(function (resolve, reject) {

var order = event.getObject();

if (order.s_action === 'SO_APPROVE') {

try {

//do something

resolve();

} catch (Error) {

reject(Error);

}

});

};

Subscribe Rule:

You can subscribe to the Rule for any Entity which can be executed based on the Event type assigned. Rule subscription is part of kloIDE. To subscribe a Rule you need to provide below details.

  • Exit(Rule) ID: Select existing rule on BO, General, All or create a new rule.

  • Exit Class: file name. Defaulted from rule definition for existing rule.

  • Mime Type: Java or JS. Defaulted from rule definition for existing rule.

  • BO Event Subscription ID: auto generated?

  • Event Type:

    • Entity

      • ON_CREATE

      • CREATE_NEW_FROM_TEMPLATE : execute only if executeCreateFromTemplate() method called from application.

      • ON_UPDATE : execute only on update entity.

      • ON_DELETE : execute only on delete entity.

      • BEFORE_MAPPING

      • AFTER_MAPPING

    • Some additional Event types on Root Entity(BO)

      • ON_SUCCESS : execute only after the successful transaction of a BO.

      • ON_ERROR : execute only if the transaction failed for a BO.

      • ENDPOINT_RESOLVER : this is to get all the endpoints to push the MW message. This gets called on every create/update/delete of a BO.

  • Object Group: Thi is optional and If Object Group is not specified, it will get called for all objects of that entity.

  • Channel Type: there are different input channels to perform a transaction on an entity, channel type selection decides when to trigger the Rule.

    • All

    • Endpoint/Device to Klarion Server

    • Endpoint/Device to Klarion Server---ALWAYS ON CLIENT

    • Endpoint/Device to Klarion Server---ALWAYS ON SERVER

    • Endpoint/Device to Server/Client---NETWORK CONTEXT SWITCH

    • Klarion Server to Klarion Offline Server

    • Klarion Server to Klarion Server

    • Legacy to Klarion Server

  • Sequence No: Decides in what sequence Rule to be executed. In case multiple Rules subscribed, sequence of rule execution is followed. All positive numbers(1-n) excepted.

    • If sequence no. is the same for 2 rules : should not allow from IDE.

Same rule can be subscribed multiple times with different Channel types.

Execution sequence of rule:

If any change in DataSet of an Entity at any level of BO. All Entities which are on top as per BO definition(sequence of entities) are set to WriteSet till Root entity which we call dirty object.

  • Rule will be executed for all dirty objects one by one. Each record in an entity invokes the Rule.

  • Execution is from Leaf Entity(of BO) Rule to Root Entity Rule for all WriteSet.

    • First call all rules of Lowest level( Leaf Entity in a BO) Entity.

    • If multiple BO changes are there in one WriteSet, first execute the rules of lowest level entity in all BOs then next up… then next up

  • At the same level rule execution is as per sequence number( 1 is top priority).

  • Execute rule based on Channel Type

  • Again jump to Child entity Rule if any modification in parent entity Rule.

Same rule subscribed multiple times?

Control Transaction in rule:

  • Cancel Transaction Refresh Changeset : This cancels the full transaction and refreshes the Changeset/Writeset.

  • Stop Exit chain only for current entity Instance

  • Stop Exit chain only for current BO instance

  • Eliminate the object from writeset (refresh entity/BO using refresh(deepRefresh)) : if new entity?

  • Eliminate the BO from writeset (refresh BO)

  • Flush Changeset (commit) : intermediate commit

Require in Rule:

require is used to load the Rule file.

All the files used in this flavor come from this flavor or from the inheritance hierarchy, so any file you need to load can be required in the context of this flavor. That basically means all the required paths are relative to the current flavor and does not go out or over the flavor. So flavor or version will never be a part of the required paths.

In order to load any file which is written in compatible with require/define (amd), you can use

require([<relative path to file without extension>],function(dependency1, dependecy2...){

//code goes here.

});

The folder structure is as follows:

Flavor / Version / Js / Css / Controller / View / …

Any file u need from the same folder will have “./<filename>” and any files from another folder will have filename “../<foldername>/<filename>”

Require can take array of dependencies and the call back will have those many object loaded and resolved as part of dependencies

define([“require”,”exports”,<relative path to file without extension>],function(require,exports,dependency1, dependecy2...){

define(["require", "exports", "./H_Order"], function (require, exports, orderUtility) {

// - <ACTION> ON ORDER CANCEL

var handleEvent = function (event) {

// Updating Items once the header status is changed to cancelled.

// making cancel qty to order qty ,pending and approved to zero.

return new Promise(function (resolve, reject) {

debugger;

event.log("*****************ON UPDATE U_SO_cancel*****************");

var order = event.getObject();

if (order.s_action === 'SO_CANCEL') {

try {

order.s_status = orderUtility.STATUS.CANCELLED;

updateItem(order).then(function () {

resolve();

});

} catch (Error) {

reject(Error);

}

} else {

resolve();

}

});

};

var updateItem = function (oOrder) {

return new Promise(function (resolve, reject) {

oOrder.order_item.fetch().then(function () {

var oItem = oOrder.order_item;

for (var i = 0; i < oItem.length; i++) {

oItem[i].cancel_qty = oItem[i].order_qty;

oItem[i].pending_qty = 0;

oItem[i].approved_qty = 0;

}

resolve();

});

});

};

exports.handleEvent = handleEvent;

});
