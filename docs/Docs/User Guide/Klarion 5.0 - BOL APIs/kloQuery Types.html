kloQuery Types

kloQuery supports multiple types of query modeling which are easy to define and use in the application. Based on application scenario and use case query type has to be decided.

  • Runtime Query ( single and multiple entities)

  • Meta Query - Dynamic

  • Native Query - Advance query plain SQL

  • Saved Query

  • User Saved Query

  • Initial Sync Query

  • Delta Query

Runtime Query​

Entity itself can be used as query without any modeling. Use entity name as Query name.

  • Fetch data from a single entity(table) or multiple entities of the same BO.

  • All properties of the entity can be added as “where” conditions using setProperty().

Available methods are listed below:

setProperty(fieldName: string, value: any): IKloQuery
@parameter : fieldName - is name of query property
@parameter: value - is the value of the property
.id = value;
q.’tableName#fieldName’ = value (#,@,.)
q[tableName.fieldName] = value
Query property defines the value of where clause these properties are used as parameter in prepared statement. Formation of WHERE clause controlled by query modeling.
While setting the property in a given query you must know the exact name of the property.
To see the list of property on console use the query instance and call the “help()” method. This will print all the available properties.
Provided value must be of type as defined in query properties's property type.
For date it can accept a well formatted string representing the date. It also supports relative dates like “today +3D”.
In case if the table name is not passed it will take the return entity name by default.
All parameters passed here are case insensitive.
Example:
E.g. Query which needs to fetch all the order of customer “cust1” and query takes the customer ID as input, use the setProperty.
q.setProperty(‘d_order#customer_id’, ‘cust1’); // Pass field name with table name ‘tableName#fieldName’
Or
q.[d_order#customer_id] = ‘cust1’;

Operators in Query:​

Adding operators to query properties while setting through API (on Query instance ) or with bindings.

Supported operators are:

AND, OR, EQUAL, NOT EQUAL, GREATER, LESSER, GREATER_EQUAL, LESSER_EQL, LIKE, NOT, IS NULL, IS NOT NULL, IN, NOT IN

Syntax: <query instance>[‘QueryProperty<_><operator>’] = value

Example:

q[‘item_number_LT’] = 50

This will filter the results having item numbers between 20 and 50.

Runtime Query on multiple Entity within BO:​

This is part of Runtime query with a special case where you want to fetch the data from multiple tables within a BO boundary. Use entity name as Query name. Based on the setProperties parameters it decides either to query on single entity or multiple entities. All parameters in setProperty should have a table name also if property belongs to other than return entity. If the table name is not mentioned, it will consider the return entity name.

All entities should be part of one BO. If all entities are not part of the same BO, it will throw an error at runtime.

@parameter: entityName: entity name(case sensitive)

@Returns**:** Query Instance (KloQuery)

Authorization on Query:​

Authorization is the process of giving someone permission to do or have something. In multi-user systems, authorization defines for the system which users are allowed access to the system and what privileges of use.

Authorization can be defined on Property Type only. Authorization can’t be defined on object type or some other parameter. In case if you want to add/remove/change authorization on base property type, extend the property type in separate flavor.

Define the authorization at Entity Property Type to apply on all the queries of a BO where that particular Property Type is used in Entity Property definition. Property type can be used in multiple Entities, in this case authorization will be applied on all queries of these Entities.

For example, ‘user_id’ is a property type and this is used in ‘user’ column definition of multiple Entities(tables) like d_order, d_logistics, etc. Now all the queries where the return entity is ‘d_order’ or ‘d_logistics’, you will get the filtered result based on user logged in.

Authorization is applied on the whole BO irrespective of return Entity. If authorization is defined on any child/root entity it will be applied on all the entities which are part of that BO.

When used as string literal in meta model in authorization it is replaced with real value. E.g. ${$USER.login_id} will be replaced with currently logged in user id. Similarly authorization can be applied on other $VARAIBLES also. For more details refer $VARIABLE section.

$Variable is available in Rule and Endpoint resolver but not available while processing middleware messages.

Syntax: ${$<Variable name>.<property id>}

Rule Execution: Authorization is applied when query runs inside BO Rule on server side. In case of client side Rule execution authorization is not applied as client DB should have only filtered data. If any client(endpoint) is not authorized to see the data it should not get synced to the client. Which means authorization is applied at the time of initial sync and data(message) push to client.

Inherit Authorization: Authorization of parent object added automatically to the child. This means if authorization is applied based on customer_id property type on order Entity, the same will be applied on the child entities(upto n level) also.

Authorization is applied in Read and Create operations. As it is applied on Read operation, Delete operation is covered under this. User can’t delete the data which is not allowed to read.

Authorization is not applied while querying data in middleware message processing as the system does not know the User.

Authorization is not applied to scheduled jobs as the user configured in Job is common.

APIs to be provided to get the $variable values in non-odata call.

Authorization has to be applied on Upload data.

How to skip authorization in one particular scenario? Can be useful in debugging in development system.

Modeling of a query​

Till now you have gone through the Runtime query where modeling is not required.

Let’s model a Query using Procify Data Studio. To create a query go to the entity which will be returned as a result. Provide a unique Query name. Query names should start with q as best practice. It must not start with “d, c, a or m”. Query name and entity name must not be the same hence name used as entity id or query id can not be used for others. Select Query Type as “D” or “Modeled Query”

Query definition is broadly categorized into two sections one as “SQL Section” relevant input as definition to prepare SQL statement and other defines the behavioral expects. Section to define SQL needs to know participating database tables join rules, where clause, return columns, groupby etc. second section concentrate on business aspect like before query rule, after query rule, network mode, property mapping, part return, authorization, etc.

Filter Expression: - to be discussed.

Filter expression is binary tree of operator, table.fields, function, variable, entity property and const. Tree can be evaluated only as a one way to construct the filter expression. Tree nodes can have an operator with left and/or right values. Value can be another node itself.

Not Supported:​

  • Nested queries are not supported.

  • Formula not supported (like a*b)

  • Limit not supported

Behavior Section:​

Return Entity Name: Result set will be kloEntitySet containing the instances of named return Entity. Return entity could be Persistent or Transient.

In case if Persistent entity is not fitting in as a return data set, you can create a Transient entity which has all the required entity properties as per business requirement and use this entity as return entity. Visit Entity section for more details on definition of Transient entity. This is the use case you need:

  • Return the data from different entities.

  • Additional fields to store some calculated value at runtime.

Is_across_tenant: If query needs to be extended across tenant data. Be careful for security. By default queries are tenant specific. This will return the data of all the tenants within a landscape.

Network mode: Normally left null or “” or “Default” so it is picked as per precedence. Specify only in specific flavor as per override rules.

Return entity mapping

Pagination behavior: Pagination is applied only if query is executed from UI. In case if query is executed from any rule(Entity or Query) it will load all qualified data.

Features supported:

  • Fetch data from multiple entities(tables) across BO.

  • Join with another entity(table) supported with relation.

  • All query properties are optional.

  • Most used SQL functions and operators are supported.

Native Query​

Till now you have gone through Runtime and Modeled Query.

Native query is a row SQL query which supports all operators and functions of SQL as part of query statement(not part of metadata). This should be used only as a last option if nothing fits. This type of query must not be used in a product or reusable module. Native query is highly flexible but non migratable.

Let’s write a SQL Query using Procify Data Studio. To create a query go to the entity which will be returned as a result. Provide a unique Query name. Query names should start with q as best practice. It must not start with “d, c, a or m”. Query name and entity name must not be the same hence name used as entity id or query id can not be used for others. Select Query Type as “Z” or “Native Query”.

  • Write SQL statement

  • Define Query property

  • Test Query

Native query working in online case may not work in offline network mode if query is incompatible with webSQL. It is comparatively slow because to db it is submitted as a nested query. Use only if requirement is not fulfilling with Runtime or Modeled queries.

Authorization will be applied the same as other query types.

Example:

SELECT * from d_order where customer_id = :cust_id and order_type = :”prime” order by order_date desc;

Here cust_id is the query property you have to define. All query property values are mandatory to pass at the time of execution.

Not supported:

  • Query Relation: use Join in SQL statement.

  • Archiving

  • Date dependent features

Subscribe Query Rules​

You can subscribe the Rule to a query which is executed before or after query execution. Rule subscription is part of kloIDE. To subscribe to the Rules you need to provide the details below.

  • Rule ID:

  • Event Type:

    • Before Query (BEFORE_QUERY)

    • After Query(AFTER_QUERY)

  • Channel Type: All, D2K- Client, D2K- Server, K2K, E2K,

  • Sequence No: In case multiple Rules subscribed on one query, it will execute in a given sequence here. All positive numbers(1-n) excepted.

Rules can not be executed on Runtime Queries. For more details on Rule execution refer to the Rule section.

Skip rule execution: execution can’t be skipped. put a condition within Rule code.

Entity also had query rule? Metadata help or real?

Rules can be subscribed on query to write the business logic. Query Rules are mainly used where some calculation required on before executing the query or query resultset to show the manipulated data on UI.

Result sets can be modified, add or remove records in AFTER_QUERY rule.

Rule Execution: Please note before execution is called only once after execution in case of Pagination, selective select or expand all cases also. Subsequent internal calls do not call before_execute. After execution may not get the correct count of records or all records or all fields. Please ensure you have considered selective select case, pagination case and expand all cases. After_Query will be executed after every internal call all the data manipulation will be accepted as is to form the return entity.

How to decide in the application which query type to use?​

As you have gone through all query types explained above with all features supported in different types of queries. Based on the features supported programmer can decide which type will fit in what scenario.

While selection of type of query, you give priority in below sequence(1 is highest priority):

  1. Runtime Query

  2. Modeled Query

  3. Native Query

Below are few frequent use cases and query type usage:

  • Advance Search screen: use Modeled query.

  • F4: use Runtime query

  • Initial Sync: use Modeled query.

  • Report: use dynamic query normally as input parameters are dynamic in most of the reports.

  • List Screen:

  • Details screen: Normally Runtime Query with Entity by ID

Saved Query​

kloQuery is a parameterized query which takes the properties’ value at runtime. We may need these property values to be persisted and execute the query with the persisted value without asking application users to provide the value. Saved Query is a Query container that holds the predefined properties’ value for a given query. Saved Query is identified by ID hence … It is also used in the Initial Sync.

Saved query can use dollar variables and date literals as property values. Saved query can hold all the variable values which can be set at runtime by API.

Delta Query​

Delta Query is used to update the local db on a periodic basis from the server. It asks the server to provide the data modified from the last execution till now. Results are handed over to the executor. Delta queries are internally used by cached online and by value help.
